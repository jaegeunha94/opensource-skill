Subgraph와 Multi-agent — 상태 계약과 handoff 경계

역할 수를 늘리기 전에 입력·출력·공유 상태·도구 권한을 설계한다.

레슨 목록 · 이전 Day 9 · 빠른 참고

면접 질문과 실무 상황

고객 상담을 검색 agent와 환불 agent로 나누었습니다. 두 agent가 같은 messages에 쓰고 환불 agent가 다른 tenant의 상태를 기억합니다. 역할별 system prompt만 분리하면 해결되나요?

Day 9의 thread와 store 수명 위에서 오늘은 graph 합성과 책임 이동을 다룹니다. 면접관은 “agent가 많으면 똑똑하다” 대신 상태·권한·실패의 계약을 설명하는지 봅니다.

전제 개념

subgraph는 다른 graph의 한 node로 쓰는 graph입니다. 그 자체가 별도 모델이나 보안 sandbox라는 뜻은 아닙니다. multi-agent는 모델/도구/기억의 역할을 나눈 구조이며 subgraph는 이를 구성하는 한 방법입니다.

현재 LangGraph 문서는 공통 state key가 있으면 compiled subgraph를 node로 연결하고, schema가 다르면 wrapper로 입력·출력을 매핑하는 방식으로 구분합니다. 같은 key의 동시 업데이트는 reducer 규칙이 필요하며 messages 전체를 아무 agent에게나 공유하면 비용과 정보 노출이 늘어납니다.

답변 사고 순서

  1. 분리가 필요한 이유를 정한다: 전문 도구·독립 기억·개발 책임·병렬 작업. 단순 단계는 일반 node로 충분한지 비교한다.
  2. parent의 공통 요청 상태와 agent의 private state를 나눈다.
  3. 입력에는 허용한 최소 맥락, 출력에는 검증 가능한 결과 schema만 둔다.
  4. 공유 key와 reducer, 병렬 실패·재시도·종료 budget을 설계한다.
  5. subagent 호출과 handoff를 구분하고 제어 주체·사용자 응답 책임을 정한다.
  6. 실행 주체·tenant 권한·tool side effect를 host에서 강제한다. checkpoint와 thread를 격리하고 시험한다.

구체적 상태 계약

# 설계 의사코드: 실제 StateGraph API 튜토리얼이 아님
Parent: request_id, tenant_id, user_question, evidence, decision
Search input: allowed_query, tenant_scope, source_version
Search output: passages[{source_id, span, version}], unresolved
Refund input: verified_order_id, actor_scope, policy_version
Refund output: proposal{amount, reason}, needs_approval
# 환불 실행은 parent의 검증/승인 뒤 제한된 tool gateway가 수행

tenant_id를 모델이 임의로 쓴 값으로 바꾸지 않습니다. wrapper가 호출자의 신뢰된 범위를 전달하고 반환 결과의 source/주문이 그 범위인지 확인합니다. refund agent에게 검색 agent의 모든 messages와 비밀 도구 결과를 줄 필요는 없습니다.

패턴제어선택 조건
subagent as tool / supervisor주 agent가 전문가 결과를 받고 계속 응답최종 통합 책임을 한곳에 둘 때
handoff대화 처리 역할을 다음 agent로 이동전문 역할이 사용자와 직접 이어가야 할 때
swarm형 분산 handoff여러 역할이 정책에 따라 이동경로가 유동적이며 loop·권한·응답 책임을 검증할 때

이 패턴 이름이 특정 helper package의 필수 사용을 뜻하지 않습니다. 현재 공식 multi-agent 문서의 구조와 목표로 선택하고 버전별 API는 확인합니다. per-invocation과 per-thread persistence는 다른 수명을 가지며 같은 stateful subgraph의 동시 실행은 namespace/checkpoint 충돌도 검토합니다.

답변 예시와 trade-off

역할 prompt 분리만으로 기억과 권한이 격리되지 않습니다. parent는 요청과 승인 상태를 유지하고 검색은 근거 schema, 환불은 실행이 아닌 제안 schema로 받겠습니다. 서로 다른 state는 wrapper로 명시 매핑하고 공유 채널은 reducer를 설계하겠습니다. tenant 범위와 결제 권한은 tool gateway에서 강제하며 handoff 후 사용자 응답 책임과 종료 budget을 기록하겠습니다.

약한 답 “각 agent에 다른 이름을 줍니다”는 공유 memory와 tool 권한을 다루지 않습니다.

  • shared state는 통합이 쉽지만 결합·충돌·정보 노출이 커집니다. private state+schema는 격리되지만 변환·관측이 추가됩니다.
  • supervisor는 최종 판단이 분명하지만 병목·추가 모델 호출이 생깁니다. handoff는 역할에 깊이 맡길 수 있으나 이동·복귀·사용자 맥락 관리가 어렵습니다.
  • 병렬 agent는 지연을 줄일 수 있지만 비용·상충 결과·부분 실패 처리가 늘어납니다. 작업 의존성이 있으면 무조건 병렬화하지 않습니다.

흔한 오해와 최신 근거

subgraph namespace는 도구 실행 보안 경계가 아닙니다. 독립 state여도 같은 프로세스와 credential을 쓰면 권한이 공유됩니다. 공식 v1 안내와 release 내역을 확인했고 과거 supervisor/swarm helper를 신규 설계의 필수 표준으로 취급하지 않았습니다.

연습과 피드백

검색과 환불 제안이 병렬로 같은 decision key에 서로 다른 문자열을 씁니다. “마지막 값 사용” reducer를 두면 안전한가요?

해설 보기

업무 판단이 실행 순서에 의존해 달라질 수 있습니다. 각 결과를 별도 key/ID로 저장하고 parent 검증 node에서 근거·정책·승인을 통합하는 편이 이 사례에 맞습니다. reducer는 충돌을 없애 보이게 할 수 있지만 결정의 의미를 만들어주지 않습니다.

Follow-up과 자기 점검

handoff가 무한 반복되면? 이동 횟수·전체 시간·토큰 budget과 완료 조건을 두고 같은 미해결 원인을 추적합니다. 더 많은 agent로 해결하려 하지 않습니다.

한 agent만 실패하면? 필수 근거와 선택적 제안을 나누고 partial result를 명시합니다. 실패한 근거를 성공처럼 조립하지 않습니다.
