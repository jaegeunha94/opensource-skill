Store·Interrupt·Human-in-the-loop의 상태 경계

checkpointer·store·interrupt의 쓰임과 재개 조건을 구분한다

핵심 판단

체크포인트와 장기 기억은 목적과 수명이 다르다. 승인 대기 중인 실행을 복구 가능한 상태로 보존한다.

checkpointer는 특정 thread의 graph state와 실행 위치를 저장해 같은 작업을 이어가게 한다. store는 thread 바깥에서도 필요한 사용자/조직 데이터를 저장한다. `interrupt`는 외부 입력이 올 때까지 graph 실행을 일시 중단한다.

검토 순서

  1. 수명 분류: 현재 실행 임시 상태, thread conversation state, cross-thread memory를 분리한다.
  2. 권한 모델: thread id를 사용자 소유권과 tenant에 연결하고 임의 재개를 차단한다.
  3. 승인 payload: 사람에게 보여줄 도구·대상·인자·영향을 최소 JSON으로 전달한다.
  4. 재개 처리: 승인·수정·거부를 명시 상태로 기록하고 동일 interrupt replay를 안전하게 만든다.
  5. 보존·삭제: TTL, 개인정보 동의, 접근 감사와 thread/store 삭제 정책을 정한다.

선택 비교

선택얻는 점비용·위험
thread checkpoint대화 진행과 중단된 graph를 이어갈 수 있다.thread별 민감 정보와 checkpoint 보존량을 관리해야 한다.
cross-thread store사용자 선호·공통 지식을 여러 실행에 활용한다.tenant 분리, 출처·만료·정정 및 삭제 정책이 복잡해진다.
동기 승인 대기위험 작업 전에 명확한 통제를 둔다.사람 응답까지 실행 자원·queue와 오래된 승인 처리가 필요하다.

주의할 함정

오해: checkpoint가 있으니 node는 중단 지점에서 정확히 한 번만 다시 실행된다.

실제 경계: 재개 시 graph 단계가 재평가될 수 있다. 외부 부작용은 checkpoint 상태만으로 exactly-once가 보장되지 않으므로 idempotency·outbox·상태 확인을 사용한다.

면접에서 꺼낼 사례

결제 승인 node에서 외부 결제를 먼저 호출한 뒤 interrupt를 걸면 승인이 실행 이후에 발생한다. side effect 앞에 approval gate를 두고, 승인 후에는 idempotency key로 결제를 실행한다.

확인 질문: 사람이 승인 버튼을 눌렀지만 resume 응답이 네트워크에서 timeout됐습니다. 승인 재전송과 결제 중복을 어떻게 막습니까?
