NUMA 메모리 지역성과 tail latency

코어 수와 메모리 용량이 충분한데도 지연이 악화될 수 있다. 요청을 처리하는 CPU와 데이터가 놓인 NUMA 노드가 멀리 떨어졌는지 확인한다.

오늘의 학습 결과: NUMA 원격 메모리 접근을 측정하고 안전한 배치 실험을 설계한다

면접 질문

멀티소켓 DB 서버를 수평 확장했는데 p99가 악화됐습니다. NUMA가 원인인지 어떻게 검증하겠습니까?

실무 상황: 서버는 2소켓이고 한 프로세스가 모든 CPU에 실행된다. 메모리 할당은 첫 접근 위치에 따라 한 소켓에 편중될 수 있고, 프로파일에서 remote memory traffic이 증가했다.

왜 묻는가: NUMA를 만능 튜닝으로 다루지 않고 locality, scheduler, allocator, 병렬도에 관한 검증 가능한 가설을 세우는지 본다.

전제 개념

NUMA 서버는 CPU마다 가까운 메모리 영역이 있다. 다른 CPU 소켓의 메모리도 읽을 수 있지만 interconnect를 지나므로 더 큰 지연과 대역폭 경쟁을 만들 수 있다.

원격 접근을 무조건 금지하면 메모리 부족이나 CPU 불균형이 생길 수 있다. 데이터가 한 노드에 몰리는지, 스레드가 자주 이동하는지, 실제 지연이 바뀌는지 같이 봐야 한다.

답변 사고 순서

  1. 토폴로지 파악: `numactl --hardware`, `lscpu`로 노드·CPU·메모리 연결을 확인한다.
  2. 증거 수집: NUMA별 local/remote hit, memory bandwidth, thread migration, p99를 같은 시간축에 본다.
  3. 원인 분리: CPU affinity, allocator placement, workload shard를 하나씩 바꾸는 실험을 설계한다.
  4. 정책 선택: local 우선, interleave, worker pinning을 메모리 footprint와 병렬 작업 분포에 맞춰 비교한다.
  5. 회귀 방지: 한 소켓 과포화·메모리 부족·failover 시 편중까지 포함해 부하 검증한다.

케이스 풀이와 답변 예시

무작정 프로세스를 한 소켓에 고정하기 전에 데이터가 그 소켓의 메모리에 실제로 배치되는지 확인한다. worker 고정과 first-touch 배치를 함께 바꾸고 처리량·p99·remote access를 비교해야 인과관계를 볼 수 있다.

먼저 remote access 비율과 소켓별 메모리 사용량을 측정하고, 요청 지연이 해당 비율과 함께 움직이는지 확인하겠습니다. 그다음 대표 workload에서 worker affinity와 메모리 first-touch를 한 번에 하나씩 바꿔 비교하겠습니다. 한 노드에 메모리가 몰려 OOM 또는 대역폭 병목이 생기는지, 노드 장애 후 재배치가 가능한지도 합격 기준에 포함하겠습니다.

답변에서 드러나는 점: NUMA 상태를 가정하지 않고 토폴로지·배치·실측값으로 검증한다.

Trade-off

선택얻는 점비용·위험
Local 우선 + worker pinning원격 접근을 줄여 지연을 낮출 수 있다.핫 소켓에 CPU·메모리가 집중되고 동적 부하 균형이 약해진다.
Interleave대역폭을 여러 메모리 노드로 분산한다.대부분의 접근에서 원격 지연이 생길 수 있고 단일 스레드 응답에는 불리하다.
OS 기본 자동 배치운영이 단순하고 일반 workload에 적응한다.컨테이너·스레드 이동·first-touch 순서에 따라 예상과 다른 배치가 될 수 있다.

흔한 오해

NUMA 서버는 프로세스를 한 소켓에 고정하면 항상 빨라진다.

작업 집합이 한 노드 메모리에 안 들어가거나 병렬도가 높으면 오히려 병목을 만든다. 고정 전후를 동일 workload에서 비교하고 메모리 대역폭과 p99를 같이 본다.

예시 풀이와 피드백 보기

서비스의 지연/처리량 SLO와 소켓별 포화를 확인한다. pinning을 그대로 전체 적용하지 않고 worker shard 배치, 메모리 locality와 CPU utilization을 비교하며, 대역폭 한계인지 CPU 한정인지 프로파일링한다.
