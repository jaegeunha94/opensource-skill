컨테이너 cgroup 자원 압박과 CPU throttling 진단

Day 9의 격리·Day 11의 배치를 바탕으로, 호스트 여유 CPU와 컨테이너 CPU 예산을 구분한다.

레슨 목록 · 이전 Day 11 · 빠른 참고

면접 질문·실무 상황

노드 CPU는 40%인데 API p99가 600ms입니다. CPU limit을 올려야 하나요?

가상 서비스는 8코어 노드에서 실행되며 컨테이너의 cpu.max는 50000 100000입니다. 배포 후 worker를 2개에서 8개로 늘렸습니다. 면접관은 평균 사용률과 실행 가능 시간의 제한을 구별하는지 봅니다.

전제 개념: 사용량과 예산

CPU 0.5개 제한은 코어 반쪽에만 배치한다는 뜻이 아닙니다. 이 예에서는 100ms 기간마다 모든 worker가 합쳐 쓸 수 있는 CPU 시간이 50ms입니다. 8개가 동시에 실행하면 예산을 빨리 쓰고, 다음 기간까지 실행을 멈출 수 있습니다. 이것이 throttling입니다. 노드에 놀고 있는 코어가 있어도 해당 그룹의 예산이 소진되면 기다립니다.

커널 cgroup v2 문서의 cpu.max·cpu.stat을 읽으세요. 먼저 v1/v2와 실제 프로세스의 cgroup 경로를 확인해야 합니다. quota와 별개로 cpuset은 실행 가능한 CPU를 제한하고, 부모 cgroup 제한도 영향을 줍니다.

답변 사고 순서와 수치

  1. p99, 요청률, 배포 시각과 worker 변경을 같은 시간축에 놓습니다.
  2. 해당 cgroup의 cpu.max·cpu.stat과 부모 제한, cpuset을 읽습니다. 임의의 루트 파일이 앱의 제한이라고 가정하지 않습니다.
  3. 10초 동안 nr_periods가 100, nr_throttled가 70 늘었다면 관측 기간의 70%에서 throttling이 있었다는 신호입니다. 요청 70%가 늦었다는 뜻은 아닙니다.
  4. usage_usec 증가, CPU pressure, 큐 대기, p99를 함께 비교합니다. throttled_usec를 곧바로 벽시계 손실 비율로 해석하지 않습니다.
  5. 대표 부하에서 worker 수와 limit을 하나씩 바꿉니다. Day 11의 NUMA 배치가 같도록 유지해 제한 효과와 지역성 효과를 섞지 않습니다.

PSI는 CPU·메모리·I/O 압박으로 작업이 진행하지 못한 시간을 관측하는 신호입니다. 메모리 reclaim 때문에 느린 경우 CPU limit만 올려서는 원인을 없애지 못합니다.

답변 예시·Trade-off·오해

노드 평균 CPU만으로 판단하지 않겠습니다. 앱의 quota와 period, throttling 증가량, 큐 대기를 확인하고 worker 증설 전후를 비교합니다. 예산을 넘는 병렬 실행이 원인이면 worker를 줄이거나 limit을 조정하되, 같은 노드의 다른 서비스 p99와 총 용량도 검증하겠습니다.

약한 답변: ‘CPU가 남으니 스레드를 더 늘립니다.’ 제한 시간의 소비를 더 빠르게 할 수 있습니다. limit 상향은 burst를 받지만 이웃 서비스 격리와 비용을 약화시킵니다. worker 축소는 스케줄링 비용을 줄이지만 처리량을 제한할 수 있습니다. quota 제거는 노드 용량·동시성 제한·경쟁 상황이 검증된 경우에만 비교 후보입니다.

흔한 오해: 높은 throttling 횟수가 곧 장애 원인이다. 경미한 burst도 횟수를 늘릴 수 있습니다. 지연과의 시간상 관계 및 설정 변경 실험이 필요합니다.

연습과 피드백

cpu.max=200000 100000인 그룹에 worker 8개가 있습니다. 각 worker가 25ms CPU를 동시에 소비했다면 합계 예산과 다음 조사를 말해 보세요.

풀이 확인

8×25ms=200ms로 기간 예산을 소진합니다. 이상화된 경우 8코어에서 약 25ms 만에 쓰고 다음 기간까지 대기할 수 있습니다. 실제 스케줄링과 cpuset에 따라 달라지므로 cpu.stat 증가와 요청 지연을 확인합니다. ‘2코어니까 항상 코어 두 개에서만 돈다’는 quota와 affinity를 혼동합니다. ‘8 worker가 8배 처리량’은 예산 제한을 무시합니다.

Follow-up·자기 점검

앱 cpu.stat에서 throttling이 적다면? 부모 cgroup 제한, cpuset 경쟁, 메모리/I/O pressure와 lock 대기를 봅니다. 커널 버전별 cpu.stat.local 지원 여부도 확인합니다.

request만 늘리면 해결되나요? 스케줄링 용량 예약과 CPU 사용 한도는 다릅니다. request 조정이 노드 배치에는 영향을 줘도 기존 quota를 자동 제거하지 않습니다.
