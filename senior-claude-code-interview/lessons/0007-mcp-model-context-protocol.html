MCP 서버 통합 — 권한·신뢰·실패 경계

MCP는 모델에 도구를 연결하는 표준 경계다. 연결된 서버가 안전하다는 보증이나 사용자 권한을 대신 제공하지 않는다.

오늘의 학습 결과: host·client·server 역할과 tool 권한, 신뢰 검증 절차를 설명한다

면접 질문

개발자 PC에서 사내 MCP 서버와 외부 패키지 MCP 서버를 함께 쓰게 하려면 어떤 통제를 두겠습니까?

실무 상황: 외부 MCP 서버가 파일과 이슈 트래커 tool을 제공한다. tool 설명이 prompt injection을 포함하거나, 잘못된 인자가 삭제 작업을 실행할 수 있다.

왜 묻는가: 프로토콜 역할과 trust boundary를 이해하고 tool 호출에 대한 사용자 승인·최소 권한·감사를 설계하는지 본다.

전제 개념

MCP는 host가 client를 통해 server와 연결하고, server가 tools·resources·prompts 같은 기능을 제공하는 프로토콜이다. 모델은 기능을 호출할 수 있지만, 최종 권한 정책은 host와 tool 실행 환경에서 enforced돼야 한다.

tool schema validation은 잘못된 형식을 줄일 뿐 악의적 요청을 막지 않는다. 사용자 승인 화면, 파일/네트워크 허용범위, secret 전달, server update 출처를 별도 검토해야 한다.

답변 사고 순서

  1. 주체·경로: host, MCP client, server, 실제 tool side effect가 어디서 실행되는지 그린다.
  2. 서버 검증: 공급처·버전·해시·권한·전송 방식과 취약성 대응 owner를 확인한다.
  3. 최소 권한: 읽기와 쓰기 도구를 분리하고 workspace·domain·resource 범위를 제한한다.
  4. 승인 경계: 삭제·배포·외부 전송 같은 부작용은 실행 전 사용자 확인과 preview를 둔다.
  5. 감사·복구: 입력·승인자·결과·오류를 민감값 없이 기록하고 revoke·disconnect 절차를 만든다.

케이스 풀이와 답변 예시

이슈 조회 tool은 읽기 전용으로 허용하고, 파일 수정 tool은 현재 workspace로 제한한다. 배포·삭제는 preview와 명시적 승인 없이는 실행하지 않는 정책을 구성한다.

MCP를 권한 위임으로 취급하지 않겠습니다. 먼저 server가 제공하는 capabilities와 실제 실행 위치를 검증하고, 읽기와 쓰기 tool을 분리해 최소 권한으로 연결하겠습니다. 사용자가 승인하지 않은 파일 외부 전송이나 destructive action은 host에서 차단하고, 요청·승인·결과를 추적 가능한 감사 이벤트로 남기겠습니다. server 교체와 credential revoke, incident 격리 절차도 운영 runbook에 포함하겠습니다.

답변에서 드러나는 점: 프로토콜 편의와 tool trust를 혼동하지 않고 host에서 권한 경계를 소유한다.

Trade-off

선택얻는 점비용·위험
로컬 stdio server개발 환경과 직접 통합하기 쉽고 네트워크 노출이 적다.실행 파일·환경변수·로컬 파일 권한이 사용자 계정 권한으로 이어질 수 있다.
원격 HTTP server중앙 관리와 여러 클라이언트 공유가 쉽다.인증·TLS·tenant isolation·네트워크 접근 제어가 더 중요해진다.
매 호출 승인사용자에게 부작용을 투명하게 보인다.승인 피로가 생기므로 위험 기반 승인과 명확한 preview가 필요하다.

흔한 오해

MCP 표준 tool schema를 따르면 호출 결과와 tool이 안전하다.

표준은 상호운용성 계약이지 신뢰 인증서가 아니다. tool 구현, 권한, 입력 내용, 결과를 모두 비신뢰 경계로 다룬다.

예시 풀이와 피드백 보기

검색 데이터는 untrusted content로 표시하고, 시스템 지시와 tool policy가 이를 실행 지시로 취급하지 않게 한다. 외부 전송 tool을 allowlist에서 제외하거나 별도 승인으로 분리하고, secret은 model context/tool argument에 노출하지 않는다.
