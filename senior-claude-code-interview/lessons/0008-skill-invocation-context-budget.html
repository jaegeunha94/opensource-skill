Skills — 재사용 절차와 컨텍스트 비용의 설계

항상 필요한 저장소 규칙과 필요할 때 꺼내는 작업 절차를 분리하고, 호출 조건과 권한을 각각 검증한다.

레슨 목록 · 이전 Day 7 · 빠른 참고

면접 질문과 실무 상황

“팀이 매번 긴 프롬프트로 릴리스 검토를 요청합니다. Skills로 옮기면 정확도와 비용을 어떻게 관리하겠습니까?” 지난 MCP 레슨에서 외부 도구의 신뢰 경계를 나눴다. 오늘은 도구 연결 자체가 아니라, 그 도구와 파일을 어떤 순서로 사용하라는 재사용 절차를 다룬다.

가상 팀은 매주 결제 서비스의 변경을 검토한다. 저장소의 빌드 명령은 늘 필요하지만, 릴리스 위험 표를 만드는 절차는 릴리스 검토 요청에만 필요하다. 두 내용을 모두 항상 로드하면 작은 버그 수정에도 불필요한 절차가 따라온다.

전제 개념: 목록과 본문을 구분하기

CLAUDE.md는 작업 전반의 규칙을 전달하는 자리다. Skill은 이름·설명으로 발견되고, 호출되면 상세 지침이 들어오는 작업 단위다. 기본 설정에서는 설명 같은 메타데이터가 컨텍스트를 차지하며, 긴 본문과 보조 자료까지 매번 전부 읽히는 것은 아니다. 하지만 호출 후 읽은 긴 파일은 여전히 비용과 주의력 예산을 쓴다.

따라서 “설치했으니 비용이 0”도, “모든 Skill 본문이 항상 들어간다”도 틀리다. 설명은 언제 쓸지를 명확히 하고, 본문은 실행 순서와 완료 조건에 집중하며, 긴 예시는 실제 필요할 때 참조한다.

작고 검증 가능한 워크플로우

예를 들어 다음은 사용자가 직접 호출하는 릴리스 검토 Skill의 개념 예시다. 실제 저장소 파일을 생성하거나 릴리스하는 명령은 이번 레슨에서 실행하지 않는다.

---
name: release-review
description: 릴리스 후보의 변경과 검증 증거를 읽어 배포 위험 표를 작성한다.
disable-model-invocation: true
---
1. 요청된 후보와 비교 기준을 확인한다.
2. diff와 실제 테스트 결과를 읽는다. 누락된 결과는 미확인으로 적는다.
3. 데이터 변경, 권한 변화, rollback 가능성을 각각 판단한다.
4. 위험 | 증거 | 대응 | 남은 확인을 표로 작성한다.
5. 형식이 필요하면 references/review-format.md를 읽는다.

disable-model-invocation: true는 자동 호출을 막고 사용자의 직접 호출을 남긴다. 이 설정에서는 자동 발견용 설명도 평소 컨텍스트에서 빠진다. 반대로 user-invocable: false는 사용자가 메뉴에서 호출하는 방식을 숨기는 설정이며, 모델 호출까지 금지하는 보안 장치가 아니다. 기본 자동 호출을 쓴다면 설명에 긍정 사례와 제외 조건을 함께 적는다.

답변 사고 순서와 답변 예시

  1. 반복되는 산출물과 항상 필요한 규칙을 구별한다.
  2. 자동 호출이 필요한지, 사용자의 명시 호출이 필요한지 결정한다.
  3. 최소 본문과 상황별 참조 파일로 나누고 완료 조건을 정의한다.
  4. 권한 정책은 별도로 확인한다. 절차 문장을 안전 경계로 믿지 않는다.
  5. 정상 호출·오호출·증거 부족 사례로 평가하고 실제 읽은 파일과 토큰 사용량을 비교한다.
“빌드 명령은 저장소 규칙에 두고 릴리스 위험 검토는 Skill로 분리하겠습니다. 처음에는 수동 호출로 범위를 제한하고, 성공 기준을 증거가 있는 위험 표로 정하겠습니다. 설명만 맞았는지보다 필요한 테스트 결과를 읽었는지, 미확인을 숨기지 않았는지, 무관한 변경을 건드리지 않았는지 평가하겠습니다.”

면접관의 평가 기준: 재사용이라는 말보다 호출 범위·권한·검증을 분리하는지 본다. 약한 답변: “모든 규칙을 큰 Skill 하나에 넣고 allowed-tools로 안전하게 제한하겠습니다.” 도구 권한 부여를 제한 목록으로 혼동하고 오호출·증거 확인을 평가하지 않는 답변이다.

Trade-off와 흔한 오해

자동 호출은 요청을 짧게 하지만 유사한 요청에 과잉 적용될 수 있다. 수동 호출은 의도가 분명하지만 사용자가 절차를 기억해야 한다. 참조 파일을 너무 잘게 나누면 읽기 왕복과 필요한 정보 누락이 늘어난다. 하나의 결정에 필요한 표와 예시는 함께 두는 편이 낫다.

현재 Claude Code의 allowed-tools는 호출 동안 지정 도구의 권한을 부여하는 용도다. 그 목록 외 도구를 없애는 제한 목록이 아니다. deny/ask 규칙과 관리 정책은 별도로 작동한다. 자동 호출 여부 역시 파일 접근이나 외부 전송 허가와 다르다. Agent Skills 표준 형식과 Claude Code 전용 필드도 구별하고, 설치된 버전의 동작을 확인한다.

연습과 피드백

① “버튼 색상을 수정해줘” ② “후보 커밋의 릴리스 위험을 검토해줘” ③ “테스트 로그 없이 지금 배포해줘”를 평가 입력으로 만들자. 위 수동 Skill의 호출 여부와 검토 결과의 성공 기준을 각각 적어라.

판단 기준 확인

설정 그대로라면 세 요청 모두 모델의 자동 호출은 없다. 사용자가 직접 release-review를 호출한 경우 ②는 변경과 검증 증거를 읽어 표를 만든다. ①은 범위 불일치를 드러낸다. ③은 테스트를 통과했다고 꾸미거나 배포를 수행하는 대신 검증 증거가 없는 항목을 미확인으로 남긴다. “호출하지 않았다”와 “호출했지만 올바른 산출물을 냈다”는 서로 다른 평가 축이다.

Follow-up과 자기 점검

참조 파일을 안 읽으면? 그 파일이 꼭 필요한 조건과 확인할 산출물을 지침에 적고, 평가에서 실제 읽기 기록과 결과를 확인한다. 파일을 많이 읽었다는 사실만으로 정확하다고 판정하지 않는다.

팀 공통 Skill을 어떻게 변경하나? 버전 관리된 절차와 평가 사례를 함께 검토하고, 사용자·프로젝트 간 이름 충돌과 관리 권한 정책도 확인한다.
