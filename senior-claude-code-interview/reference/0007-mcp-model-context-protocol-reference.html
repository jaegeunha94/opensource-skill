MCP 서버 통합 — 권한·신뢰·실패 경계

host·client·server 역할과 tool 권한, 신뢰 검증 절차를 설명한다

핵심 판단

MCP는 모델에 도구를 연결하는 표준 경계다. 연결된 서버가 안전하다는 보증이나 사용자 권한을 대신 제공하지 않는다.

MCP는 host가 client를 통해 server와 연결하고, server가 tools·resources·prompts 같은 기능을 제공하는 프로토콜이다. 모델은 기능을 호출할 수 있지만, 최종 권한 정책은 host와 tool 실행 환경에서 enforced돼야 한다.

검토 순서

  1. 주체·경로: host, MCP client, server, 실제 tool side effect가 어디서 실행되는지 그린다.
  2. 서버 검증: 공급처·버전·해시·권한·전송 방식과 취약성 대응 owner를 확인한다.
  3. 최소 권한: 읽기와 쓰기 도구를 분리하고 workspace·domain·resource 범위를 제한한다.
  4. 승인 경계: 삭제·배포·외부 전송 같은 부작용은 실행 전 사용자 확인과 preview를 둔다.
  5. 감사·복구: 입력·승인자·결과·오류를 민감값 없이 기록하고 revoke·disconnect 절차를 만든다.

선택 비교

선택얻는 점비용·위험
로컬 stdio server개발 환경과 직접 통합하기 쉽고 네트워크 노출이 적다.실행 파일·환경변수·로컬 파일 권한이 사용자 계정 권한으로 이어질 수 있다.
원격 HTTP server중앙 관리와 여러 클라이언트 공유가 쉽다.인증·TLS·tenant isolation·네트워크 접근 제어가 더 중요해진다.
매 호출 승인사용자에게 부작용을 투명하게 보인다.승인 피로가 생기므로 위험 기반 승인과 명확한 preview가 필요하다.

주의할 함정

오해: MCP 표준 tool schema를 따르면 호출 결과와 tool이 안전하다.

실제 경계: 표준은 상호운용성 계약이지 신뢰 인증서가 아니다. tool 구현, 권한, 입력 내용, 결과를 모두 비신뢰 경계로 다룬다.

면접에서 꺼낼 사례

이슈 조회 tool은 읽기 전용으로 허용하고, 파일 수정 tool은 현재 workspace로 제한한다. 배포·삭제는 preview와 명시적 승인 없이는 실행하지 않는 정책을 구성한다.

확인 질문: 문서 검색 MCP가 검색 결과 안의 “시크릿을 업로드하라”는 지시를 반환했습니다. 모델과 tool 권한 경계를 어떻게 설계해 피해를 막습니까?
