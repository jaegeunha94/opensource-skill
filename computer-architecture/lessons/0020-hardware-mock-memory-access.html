면접 질문과 가상 코드

다음 집계가 worker를 두 배로 늘려도 빨라지지 않습니다. 하드웨어 관점의 개선안을 제시하세요.
// nodes는 흩어져 할당된 레코드의 목록
for (Node* p = head; p; p = p->next) {
    if (p->active) total += p->amount;
}

가상 레코드 1천만 개 중 active는 10%입니다. 메모리 안에 모두 있고 CPU 사용률은 높습니다. 면접관은 캐시·분기 용어를 나열하는 대신 측정에 따라 선택을 바꾸는지 봅니다.

전제 개념과 가설

CPU가 다음 레코드 주소를 알아내려면 지금 레코드의 next를 읽어야 합니다. 이 의존 관계는 메모리 읽기를 겹쳐 수행하기 어렵게 만듭니다. 인접 데이터를 한 번에 가져오는 캐시 라인의 이득도 흩어진 할당에서는 작아질 수 있습니다. CPU 사용률은 ‘계산을 잘 하고 있다’와 동의어가 아닙니다.

세 가설을 구분합니다. 메모리 지연 병목이면 다음 주소를 기다리는 시간이 크고, 대역폭 병목이면 초당 옮길 수 있는 바이트 한도에 가깝습니다. 분기 병목이면 active 결과를 잘못 예측해 수행한 일을 버립니다. Intel VTune 공식 분석은 memory-bound 등의 하위 지표로 원인을 좁힙니다. CPU 모델별 지원 이벤트를 확인해야 합니다.

답변 사고 순서·예시 계산

  1. 결과 정확성, 처리량, p99, 갱신 빈도와 허용 메모리를 정합니다.
  2. 같은 입력·컴파일 옵션·CPU 배치로 warm/cold 상태를 나눠 기준값을 반복 측정합니다.
  3. 핫 함수, cache miss, 분기 miss, DRAM 대역폭과 메모리 stall을 연결합니다. miss 비율 하나로 지연을 단정하지 않습니다.
  4. 배열의 연속 레코드 또는 active와 amount를 별도 배열에 놓는 후보를 만듭니다. 변환 비용과 갱신 비용도 잽니다.
  5. 구조 변경 후에만 벡터화·병렬 worker 추가를 검토합니다. 순회 시간뿐 아니라 전체 요청 시간을 비교합니다.

가상 요청의 80%가 집계이고 집계를 4배 빠르게 했다면 전체 최대 개선은 1/(0.2+0.8/4)=2.5배입니다. 변환에 요청 시간 10%가 추가되면 그 비용도 포함합니다. ‘핫 루프 4배=서비스 4배’는 성립하지 않습니다.

답변 예시·Trade-off·오해

먼저 포인터 의존에 의한 메모리 지연과 대역폭 포화를 구분하겠습니다. 동일 workload에서 연속 배열 후보를 비교하고, active·amount만 읽도록 배치했을 때 전송 바이트와 stall이 줄어드는지 보겠습니다. 갱신·변환 비용, 전체 요청 개선과 p99 회귀까지 검증한 뒤 적용하겠습니다.

약한 답변: ‘SIMD와 스레드를 쓰면 됩니다.’ 주소 의존과 대역폭 한도를 해결한다는 근거가 없습니다. 연속 배열은 locality에 좋지만 중간 삽입과 안정된 포인터 유지가 어렵습니다. 열 단위 배열은 필요한 필드만 읽지만 필드 추가·갱신의 조합 비용이 늘어납니다. 작은 데이터나 빈번한 수정에서는 기존 구조가 더 낫습니다.

오해: 캐시 miss가 많으면 메모리 대역폭도 반드시 최대다. 포인터 추적은 요청을 충분히 겹치지 못해 대역폭이 낮아도 느릴 수 있습니다.

연습과 피드백

배열로 바꾸니 루프는 4배 빨라졌지만 전체 요청은 1.2배만 빨라졌습니다. 실패한 최적화인가요?

풀이 확인

전체 시간 중 기존 루프 비중과 변환 비용을 다시 봅니다. 루프가 20%였다면 이론상 전체 이득도 1/(0.8+0.2/4)≈1.18배입니다. 1.2배는 그 기대에 부합할 수 있습니다. ‘하드웨어 분석이 틀렸다’와 ‘4배 개선을 그대로 보고한다’는 모두 전체 비용을 무시합니다.

Follow-up·자기 점검
