샌드박싱 아키텍처 — 실행 위치·마운트·탈출 경계

논리적 세션 분리 위에 실제 실행 격리를 더하고, effective policy로 예외 경로를 확인한다.

레슨 목록 · 이전 Day 8 · 빠른 참고

면접 질문과 실무 상황

“OpenClaw의 고객별 세션이 나뉘면 도구 실행도 안전하게 격리됩니까?” Day 8의 세션·agent 라우팅은 어느 대화 상태를 사용할지의 구분이었다. 오늘은 그 대화에서 실행하는 파일·명령이 어느 운영체제 환경을 볼 수 있는지 다룬다.

가상 Gateway는 호스트에 있고, 문서 요약 도구가 사용자 업로드를 처리한다. 업로드에 명령 실행을 유도하는 내용이 들어와도 호스트의 서비스 키와 다른 고객의 작업 파일을 볼 수 없게 설계해야 한다. Gateway 자체가 자동으로 컨테이너 안으로 옮겨진다고 가정하면 안 된다.

전제 개념: 네 개의 서로 다른 축

축판단할 질문
mode어떤 세션을 sandbox에 넣는가? off / non-main / all
scope환경을 누가 공유하는가? agent / session / shared
backend무엇으로 격리하는가? Docker 등 실행 구현
workspaceAccessagent workspace를 none / ro / rw 중 어떻게 노출하는가?

현재 문서에서 none은 실행 mode가 아니라 workspace 접근 설정이다. none이라도 별도의 sandbox 작업 공간에는 파일을 쓸 수 있다. non-main은 main 세션을 제외하므로 “대부분 격리”가 중요한 입력의 격리를 뜻하는지 확인해야 한다.

구체적인 정책 예시

다음은 문서 처리 세션에 적용할 설정의 설명용 일부다. 실제 구성에 합치기 전 agent별 override와 현재 backend 지원을 확인한다.

{
  "agents": {
    "defaults": {
      "sandbox": {
        "mode": "all",
        "scope": "session",
        "backend": "docker",
        "workspaceAccess": "ro",
        "docker": { "network": "none" }
      }
    }
  }
}

Docker 도구 환경은 session별로 나누고 agent workspace는 읽기 전용으로 노출한다. 그러나 읽기 전용은 비밀 정보의 읽기를 막지 않는다. 해당 workspace에 키를 넣으면 유출 경로가 남는다. 필요한 합성 문서만 노출하며, Docker socket이나 호스트의 광범위한 디렉터리를 마운트하지 않는다.

network none은 이 Docker 환경의 egress를 제한하는 설정이다. 별도 browser sidecar나 원격 backend까지 같은 정책이라고 확대 해석하지 않는다. SSH/OpenShell 같은 원격 경로는 원격 운영 환경의 접근·마운트 정책도 검토한다.

답변 사고 순서와 답변 예시

  1. 신뢰할 수 없는 입력과 보호할 호스트·다른 세션 자원을 적는다.
  2. mode와 scope를 정하고 공유로 생기는 교차 오염을 판단한다.
  3. workspace·추가 마운트·네트워크·browser 경로를 확인한다.
  4. 도구 허용 정책과 elevated 예외를 별도로 확인한다.
  5. 대상 세션의 effective policy와 무해한 격리 검증으로 기대를 확인한다.
“세션 라우팅만으로 파일 시스템 격리를 보장하지 않겠습니다. 문서 작업은 session 범위의 sandbox를 사용하고 비밀 값은 workspace 밖에 두겠습니다. 도구 allow/deny와 elevated 경로를 따로 검토한 뒤 해당 세션에서 실제 적용된 설정을 확인하겠습니다.”

면접관의 평가 기준: 논리적 세션 구분과 운영체제 접근 경계를 구별하는지 본다. 약한 답변: “세션을 나누고 Docker를 쓰면 모든 입력이 안전합니다.” 마운트·네트워크·elevated 예외와 실제 적용 정책을 빠뜨린 답변이다.

Trade-off·흔한 오해와 실제 적용 확인

session scope는 상태 간섭을 줄이지만 환경 생성 비용이 든다. agent scope는 재사용이 쉽지만 같은 agent의 여러 세션이 환경을 공유할 수 있다. shared는 더 넓은 공유이므로 고객 간 격리 요구와 맞는지 검토한다. 실행 위치를 나누어도 너무 넓은 마운트나 허용된 외부 전송은 보호 범위를 줄인다.

openclaw sandbox explain --session <key> 같은 공식 설명 기능으로 대상의 mode·scope·workspace·도구 정책을 확인한다. 일반 환경의 elevated 실행은 호스트 또는 node 실행 경로가 될 수 있다. 현재 required sandbox 정책이 적용되는 역할은 별도의 강제 규칙이 있으므로, 모든 상황에서 같은 예외가 가능하다고 단정하지 않는다.

연습과 피드백

설정이 all/session/ro인데 workspace에 API 키 파일이 있고, 호스트 Docker socket을 추가 마운트했다. 동료는 “읽기 전용이고 session마다 컨테이너가 있으니 안전하다”고 말한다. 두 위험과 수정 방향을 적어라.

판단 기준 확인

API 키는 수정하지 못해도 읽을 수 있다. 필요한 문서만 제공하고 비밀 파일은 노출 대상에서 제거한다. Docker socket은 호스트 자원 제어로 이어질 수 있어 컨테이너 경계를 크게 약화시킨다. 이 작업에 필요하지 않다면 마운트를 제거한다. 이후 effective policy와 마운트 목록, 네트워크 및 elevated 예외를 다시 확인한다.

Follow-up과 자기 점검

network none이면 모든 유출이 차단되나? 이 실행 환경의 직접 연결만으로 판단할 수 없다. 허용된 다른 도구, Gateway 반환, browser 등의 경로와 읽힌 정보가 결과에 포함되는지도 확인한다.

공유 환경을 쓰려면? 같은 신뢰 영역임을 명시하고 파일·프로세스·잔여 상태의 청소와 검증을 설계한다. 서로 다른 고객이라는 요구라면 비용 절감만으로 공유하지 않는다.
