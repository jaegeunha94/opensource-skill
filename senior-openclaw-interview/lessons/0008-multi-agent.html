OpenClaw Multi-Agent — channel routing과 session 격리

agent를 여러 개 만든다고 권한과 대화가 자동 분리되지는 않는다. 어떤 channel/account가 어느 agent와 session에 연결되는지 명시한다.

오늘의 학습 결과: multi-agent routing 규칙과 상태·도구 격리를 검증한다

면접 질문

개인 업무 bot과 고객지원 bot을 같은 OpenClaw gateway에서 운영하면서 대화와 도구 권한을 어떻게 격리하겠습니까?

실무 상황: 두 agent가 Slack과 Webchat channel을 사용한다. 개인 bot은 로컬 파일 tool을 쓰지만 고객지원 agent는 고객 데이터 조회만 허용해야 한다.

왜 묻는가: routing 우선순위·session key·workspace·credential 경계가 실제 보안과 운영 isolation을 제공하는지 본다.

전제 개념

gateway는 inbound channel/account/peer를 binding 규칙에 따라 agent로 라우팅한다. agent identity는 실행 설정을 가리키고, session key는 대화 상태의 범위를 정한다.

별도 agent 이름이나 workspace만으로 OS·credential 격리가 보장되지 않을 수 있다. 실제 process, tool sandbox, environment secret, shared state가 공유되는지 점검한다.

답변 사고 순서

  1. route table: channel·account·peer 기준 binding을 구체화하고 겹치는 규칙의 우선순위를 확인한다.
  2. session isolation: 개인/그룹/고객별 session key와 reset·retention 정책을 정의한다.
  3. 권한 차등: agent별 tool allowlist, workspace root, network, secret 접근을 최소화한다.
  4. 교차 접근 테스트: agent A session에서 agent B history/file/tool을 읽거나 호출할 수 없는지 검사한다.
  5. 운영 관측: route miss, 잘못된 agent binding, session 폭증, tool denial을 감사한다.

케이스 풀이와 답변 예시

개인 Slack account의 DM은 personal agent, 고객지원 workspace는 support agent로 binding한다. 두 agent가 같은 gateway process에 있어도 support가 personal filesystem을 볼 수 있는지는 sandbox 설정과 OS 권한으로 검증해야 한다.

먼저 channel/account/peer별 routing 표를 만들고 rule overlap과 fallback agent를 확인하겠습니다. 개인 대화와 고객 대화는 별도 session namespace와 retention을 쓰고, support agent에는 고객 조회 tool만 허용하겠습니다. workspace 경로 제한은 process-level sandbox 여부와 함께 검증하고, 같은 gateway에 등록된 agent가 credential이나 파일을 공유하지 않는다는 보장을 테스트하겠습니다. route miss와 권한 거부를 감사 가능한 이벤트로 남기겠습니다.

답변에서 드러나는 점: 라우팅 편의와 보안 격리를 별개의 계층으로 다룬다.

Trade-off

선택얻는 점비용·위험
하나의 gateway·여러 agent운영 endpoint와 관리 구성이 단순하다.process·credential·resource가 공유될 수 있어 blast radius가 크다.
agent별 별도 process/host권한·자원·장애 격리를 강하게 만들 수 있다.배포·업데이트·관측과 비용이 늘어난다.
channel 전체 binding설정이 단순하고 예측하기 쉽다.특정 peer/계정 예외의 라우팅 정밀도가 부족할 수 있다.

흔한 오해

agent마다 workspace 경로를 지정했으므로 데이터는 안전하게 격리된다.

경로 설정이 symlink·도구·shell·공유 process 권한을 제한하는지 확인해야 한다. 보안 격리는 실제 enforcement 지점으로 입증한다.

직접 풀어보기

고객지원 agent에 shell tool은 없지만 browser tool과 shared memory가 있습니다. 이 구성이 개인 agent와 안전하게 분리됐다고 말할 수 있나요?

예시 풀이와 피드백 보기

아니다. browser의 접근 범위와 shared memory의 namespace/ACL, gateway credential을 점검해야 한다. 민감한 개인/고객 데이터가 cross-agent 조회되지 않는 integration test를 둔다.

자가 피드백: 설정 항목이 실제 실행 경계를 enforced하는지 확인했는가?
