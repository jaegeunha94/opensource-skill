OpenClaw Multi-Agent — channel routing과 session 격리

multi-agent routing 규칙과 상태·도구 격리를 검증한다

핵심 판단

agent를 여러 개 만든다고 권한과 대화가 자동 분리되지는 않는다. 어떤 channel/account가 어느 agent와 session에 연결되는지 명시한다.

gateway는 inbound channel/account/peer를 binding 규칙에 따라 agent로 라우팅한다. agent identity는 실행 설정을 가리키고, session key는 대화 상태의 범위를 정한다.

검토 순서

  1. route table: channel·account·peer 기준 binding을 구체화하고 겹치는 규칙의 우선순위를 확인한다.
  2. session isolation: 개인/그룹/고객별 session key와 reset·retention 정책을 정의한다.
  3. 권한 차등: agent별 tool allowlist, workspace root, network, secret 접근을 최소화한다.
  4. 교차 접근 테스트: agent A session에서 agent B history/file/tool을 읽거나 호출할 수 없는지 검사한다.
  5. 운영 관측: route miss, 잘못된 agent binding, session 폭증, tool denial을 감사한다.

선택 비교

선택얻는 점비용·위험
하나의 gateway·여러 agent운영 endpoint와 관리 구성이 단순하다.process·credential·resource가 공유될 수 있어 blast radius가 크다.
agent별 별도 process/host권한·자원·장애 격리를 강하게 만들 수 있다.배포·업데이트·관측과 비용이 늘어난다.
channel 전체 binding설정이 단순하고 예측하기 쉽다.특정 peer/계정 예외의 라우팅 정밀도가 부족할 수 있다.

주의할 함정

오해: agent마다 workspace 경로를 지정했으므로 데이터는 안전하게 격리된다.

실제 경계: 경로 설정이 symlink·도구·shell·공유 process 권한을 제한하는지 확인해야 한다. 보안 격리는 실제 enforcement 지점으로 입증한다.

면접에서 꺼낼 사례

개인 Slack account의 DM은 personal agent, 고객지원 workspace는 support agent로 binding한다. 두 agent가 같은 gateway process에 있어도 support가 personal filesystem을 볼 수 있는지는 sandbox 설정과 OS 권한으로 검증해야 한다.

확인 질문: 고객지원 agent에 shell tool은 없지만 browser tool과 shared memory가 있습니다. 이 구성이 개인 agent와 안전하게 분리됐다고 말할 수 있나요?
