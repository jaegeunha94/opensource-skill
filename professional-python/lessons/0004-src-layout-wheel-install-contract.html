오늘 만들 결과

타입과 예외를 잘 설계해도 다른 서비스가 import할 수 없다면 재사용 계약은 완성되지 않는다. 오늘은 금액 파서를 최소 패키지로 묶는다. 배포 서비스에 업로드하지 않고 wheel을 만들고 설치하는 한 단위를 끝낸다. 의존성 잠금 전략은 다음 Day에서 다룬다.

배포 이름은 invoice-kit, Python import 이름은 invoice_kit로 정한다. 전자는 설치 도구가 다루는 distribution 이름이고 후자는 모듈 이름이다. 둘이 반드시 동일한 문자열인 것은 아니다.

전제 개념: src와 build backend

src layout은 import할 코드를 프로젝트 루트 아래가 아닌 src 아래에 둔다. 루트에서 실행한 Python이 아직 설치하지 않은 패키지를 우연히 찾아 버리는 일을 줄여 준다. 설치된 wheel로 테스트해야 누락된 파일이나 잘못된 패키지 탐색을 발견한다.

pyproject.toml의 build-system은 wheel을 만드는 도구를 선언하고, project는 배포 이름·버전·지원 Python 같은 메타데이터를 선언한다. build backend 의존성과 프로그램의 실행 의존성을 구분한다. 이 예제는 실행 시 표준 라이브러리만 필요하다.

네 파일로 만드는 설치 가능한 코드

invoice-project/

  src/invoice_kit/
    __init__.py
    money.py

pyproject.toml:

[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"

[project]
name = "invoice-kit"
version = "0.1.0"
description = "Invoice amount validation example"
requires-python = ">=3.11"

[tool.setuptools.packages.find]
where = ["src"]

src/invoice_kit/money.py:

from decimal import Decimal, InvalidOperation

class InvoiceValidationError(ValueError):
    """Invoice amount violates the domain contract."""

def parse_amount(raw: str) -> Decimal:
    try:
        amount = Decimal(raw)
    except InvalidOperation as exc:
        raise InvoiceValidationError("amount is not numeric") from exc
    if not amount.is_finite() or amount <= 0:
        raise InvoiceValidationError("amount must be finite and positive")
    return amount

src/invoice_kit/__init__.py:

from .money import InvoiceValidationError, parse_amount

__all__ = ["InvoiceValidationError", "parse_amount"]

Day 3에서 배운 원인 예외 연결을 유지했다. Decimal은 NaN과 Infinity도 표현하므로 양수 비교 전에 유한성을 검사한다. 공개 import 지점은 __init__.py로 정하고 내부 파일 배치를 호출자에게 강요하지 않는다. 통화별 소수 자리 규칙은 이 함수의 범위 밖이며 업무 요구가 생기면 별도 계약으로 추가한다.

빌드와 설치 검증의 순서

개발 환경에 build를 설치한 뒤 프로젝트 루트에서 python -m build --wheel을 실행한다. 새 가상 환경을 만들고 생성된 wheel 경로를 pip install에 전달한다. 그 후 프로젝트 밖의 빈 디렉터리에서 다음 코드를 실행한다. editable 설치는 개발에 편하지만 이 검증을 대신하지 않는다.

from decimal import Decimal
from invoice_kit import InvoiceValidationError, parse_amount

assert parse_amount("12.50") == Decimal("12.50")
for invalid in ("abc", "NaN", "Infinity", "0", "-1"):
    try:
        parse_amount(invalid)
    except InvoiceValidationError:
        pass
    else:
        raise AssertionError(f"accepted invalid amount: {invalid}")
print("installed package contract verified")

이 검증은 import 가능 여부뿐 아니라 정상 값과 오류 계약이 설치 결과에 유지되는지 확인한다. 루트에서만 성공하면 경로의 우연일 수 있다. 문제가 생기면 wheel 안의 파일과 설치 경로를 확인하고, 패키지가 빠졌는지 같은 이름의 로컬 파일을 읽었는지 구분한다.

Trade-off와 흔한 오해

src layout은 초기 설치 단계가 하나 더 필요하지만 배포 누락을 일찍 발견하게 한다. 단일 스크립트에는 과한 구조가 될 수 있고 여러 서비스가 재사용하는 코드에는 명시적 설치 계약이 도움이 된다. wheel은 설치 artifact이며 sdist는 빌드할 소스 배포다. 서로 다른 환경의 재현성과 의존성 잠금까지 wheel 하나가 모두 보장하는 것은 아니다.

버전 메타데이터를 바꿨다는 사실만으로 호환성을 판단하지 않는다. 반환 타입·예외·지원 Python 변경이 호출자에 미치는 영향을 함께 기록한다. 오늘은 예제 버전 0.1.0을 쓰며 공개 패키지 등록은 하지 않는다.

연습과 피드백

동료가 프로젝트 루트에서 import invoice_kit에 성공했다고 배포 검증을 마쳤다. 그런데 wheel에서 money.py가 빠져 있다. 무엇을 다시 확인할까? 또 parse_amount("NaN")을 거부해야 하는 이유를 설명해 보자.

확인할 답변

설치하지 않은 소스를 읽거나 editable 환경이 남아 있을 수 있다. 깨끗한 환경에 wheel만 설치하고 프로젝트 밖에서 공개 API를 import한다. artifact 파일 목록과 실제 모듈 경로를 확인한다. NaN은 숫자 객체 생성에 성공해도 유효한 청구 금액이 아니므로 finite 검사를 별도로 수행한다. 단순히 Decimal 변환 예외만 잡는 코드는 이 계약을 놓친다.
