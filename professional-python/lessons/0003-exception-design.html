예외 처리 설계 — 원인 보존과 오류 경계

예외를 더 많이 잡는 것이 견고한 코드는 아니다. 호출자가 복구할 수 있는 오류만 번역하고, 원인은 잃지 않아야 한다.

오늘의 학습 결과: 예외 계층·원인 연결·복구 책임을 작은 API에서 설계한다

면접 질문

외부 결제 API의 timeout을 도메인 예외로 감싸면서 원인과 재시도 판단을 어떻게 보존하겠습니까?

실무 상황: 결제 adapter는 HTTP 라이브러리의 예외를 그대로 노출하고 있다. 호출자는 모든 예외를 잡아 재시도해 중복 승인 위험까지 만들었다.

왜 묻는가: 모든 예외를 `Exception`으로 삼키지 않고 계층별 책임, 원인 체인, 재시도 가능성을 구분하는지 본다.

전제 개념

예외는 정상 반환값과 별도로 실패 흐름을 호출 스택 위로 전달한다. `raise NewError from exc`는 호출자가 도메인 오류를 보면서 원래 원인도 추적할 수 있게 한다.

예외 타입 이름만으로 재시도 안전성이 결정되지는 않는다. timeout은 요청이 서버에 도달했지만 응답만 늦었을 수 있어 결제 완료 여부가 불명확하다.

답변 사고 순서

  1. 소유권: 어떤 계층이 원시 라이브러리 예외를 알고, 어떤 계층이 사용자 의미를 정하는지 나눈다.
  2. 분류: 입력 오류, 일시적 의존성 장애, 영구 거부, 취소를 별도 유형으로 표현한다.
  3. 번역: adapter 경계에서 `raise PaymentUnavailable(...) from exc`처럼 원인을 연결한다.
  4. 복구 계약: idempotency key와 상태 조회 없이 timeout을 무조건 재시도하지 않는다.
  5. 관측: 민감 정보를 제외한 오류 코드·상관 ID·의존성 정보를 기록한다.

케이스 풀이와 답변 예시

라이브러리의 `ReadTimeout`을 도메인 계층에 그대로 노출하면 구현 교체와 정책이 얽힌다. 그러나 `PaymentFailed` 하나로 뭉치면 거부와 상태 불명 timeout의 차이를 잃는다.

HTTP client 예외를 결제 adapter에서 `PaymentOutcomeUnknown`으로 번역하고 `raise ... from exc`로 원인을 보존하겠습니다. 이 오류는 단순 재시도 가능 오류와 다르게 취급하고, 같은 idempotency key로 상태 조회를 먼저 수행하겠습니다. validation 오류는 상위 API가 4xx로 바꾸고, 취소 예외는 정상 종료 제어 흐름이므로 넓은 `except Exception`으로 삼키지 않겠습니다.

답변에서 드러나는 점: 예외를 언어 문법이 아니라 실패 의미와 복구 계약으로 다룬다.

Trade-off

선택얻는 점비용·위험
라이브러리 예외 전파원래 세부 정보가 유지되고 구현이 단순하다.도메인 계층이 특정 client 라이브러리에 결합된다.
도메인 예외로 번역호출자가 의미 있는 복구 정책을 선택한다.과도한 추상화는 원인·세부 상태를 감출 수 있다.
넓은 예외 포착프로세스 밖으로 예외가 나가는 일을 줄이는 듯 보인다.버그·취소·영구 실패를 숨겨 잘못된 재시도나 성공 응답을 만든다.

흔한 오해

예외를 잡았으니 로그를 남기고 빈 결과를 반환하면 안전하다.

호출자는 실패를 성공으로 오인할 수 있다. 실제 복구가 완료된 경우만 fallback을 반환하고, 그렇지 않으면 의미 있는 예외를 다시 올려야 한다.

직접 풀어보기

`except Exception: return []`가 들어간 검색 함수에서 DB 연결 오류가 나도 200 빈 결과를 반환합니다. 호출 계약을 어떻게 바꾸겠습니까?

예시 풀이와 피드백 보기

정상적으로 결과가 없는 경우와 검색 실패를 구분한다. 연결 오류는 repository 경계에서 의미 있는 예외로 전달하고, API 경계에서 5xx/재시도 안내로 매핑한다. fallback이 필요하면 stale cache를 썼다는 메타데이터와 제한을 명시한다.

자가 피드백: 실패와 빈 성공 결과가 구별되는 계약인가? 원인이 로깅·추적에 남는가?
