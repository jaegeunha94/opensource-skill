먼저 잡을 개념

예외는 호출자에게 복구 판단을 전달하는 API다. 원인을 보존하면서 공개 경계에서 안정된 오류로 변환한다.

낯선 용어를 바로 외우기보다 “무엇이 입력이고, 어떤 조건을 보존하며, 비용은 어디서 생기는가?”를 먼저 묻는다. 이 관점은 예외 처리 설계를 업무 코드와 서비스 동작에 연결해 준다.

작은 예시

예외는 호출자에게 복구 판단을 전달하는 API다. 원인을 보존하면서 공개 경계에서 안정된 오류로 변환한다.

  1. 요구를 한 문장으로 적는다: 예외 처리 설계에서 성공/실패를 어떻게 구분할까?
  2. 정상 경로와 경계 조건을 나눈다. 입력이 없거나, 중복되거나, 늦거나, 예상보다 커지는 경우를 포함한다.
  3. 관측 가능한 결과를 고른다. 값/예외/지연/자원 사용 중 무엇으로 동작을 확인할까?
  4. 가장 단순한 해결책을 먼저 적고, 규모가 커질 때 바뀌는 지점을 표시한다.

실무 적용

예를 들어 예외 처리 설계 작업을 코드 리뷰에서 설명한다고 하자. 전제 조건, 선택한 경계, 실패 시 복구, 측정 방법을 차례로 말하면 다른 사람이 변경을 안전하게 검토할 수 있다.

  • 선택의 기준: 입력 크기와 호출 빈도, 실패의 영향 범위를 먼저 확인한다.
  • 검증: 정상 입력뿐 아니라 경계 값과 실패 경로를 포함한다.
  • 기록: 대안과 보류한 위험, 운영자가 볼 신호를 짧게 남긴다.

주의: 예외를 광범위하게 잡고 무시하면 원인과 취소 신호까지 삼킬 수 있다. 경계에서 좁게 변환하고 원인을 보존한다.
