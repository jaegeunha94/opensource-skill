Feature Flag — 점진 노출과 제거 수명주기

코드 배포·사용자 노출·데이터 변화·flag 제거를 다른 결정으로 관리한다.

레슨 목록 · 이전 Day 11 · 빠른 참고

면접 질문과 실무 상황

Day 11에서 expand-contract로 DB 호환 창을 만들었습니다. 새 결제 경로를 5%에 노출한 뒤 flag를 끄면 모든 문제가 되돌아갑니까? 사용자가 매 요청마다 다른 경로를 타고, 1년 된 flag도 남아 있습니다.

면접관은 on/off 버튼보다 안정적인 노출 단위·중단 신호·데이터 경계·제거 책임을 봅니다.

전제 개념

배포는 코드를 서버에 놓는 일이고 노출은 어떤 사용자에게 어떤 경로를 선택할지 정하는 일입니다. flag는 이 시점을 분리할 수 있습니다. 하지만 새 경로가 이미 만든 주문·외부 결제는 off로 사라지지 않습니다.

cohort는 같은 처리를 받는 사용자/tenant 집합입니다. 매 요청마다 무작위로 정하면 같은 사용자의 흐름이 섞여 디버깅·일관성이 나빠집니다. 일정한 key와 flag별 salt로 같은 사용자의 배정을 유지하는 것이 일반적인 선택입니다. 다만 SDK·전략별 stickiness 동작은 확인해야 합니다.

답변 사고 순서

  1. flag 목적·owner·생성일·제거 목표·기본값을 기록한다. 임시 release와 장기 kill switch를 구분한다.
  2. 노출 단위를 user/tenant 등으로 정하고 전체 업무 흐름에서 동일한 판정을 사용한다.
  3. 코드는 먼저 배포하고 off 경로·on 경로·신구 데이터 호환성을 검증한다.
  4. 내부 → 제한 cohort → 확대 순서와 오류율·결제 중복·지연의 stop condition을 정한다.
  5. 판정 설정이 오래되거나 서비스가 끊길 때 fallback과 갱신 지연을 명시한다.
  6. 안정화 뒤 남길 경로로 코드를 정리하고 구버전 소비가 끝난 뒤 flag를 archive한다.

구체적 노출 계약과 예시

# 개념 의사코드: 공식 SDK의 hashing과 설정 전달은 별도 확인
bucket = stable_hash(flag_id, tenant_id) % 10000
use_new_payment = bucket < 500  # tenant 기준 약 5%

5% tenant가 5% 요청·매출을 뜻하지는 않습니다. 큰 tenant 하나가 트래픽 대부분을 차지할 수 있으므로 실제 노출 요청 수·결제 금액·오류를 함께 봅니다. 결제 API의 flag 판정과 연결된 worker가 같은 계약을 따르는지도 확인합니다.

상태책임다음 조건
off 기본owner, 호환 테스트신 경로 기능·데이터 검증
제한 cohorton-call, 노출별 지표관측량·기간·guardrail 충족
전체 onrelease ownerrollback 창 종료, 남길 경로 확정
cleanup코드 ownerflag 참조·구 경로·옛 worker 제거 확인 뒤 archive

flag 평가 결과와 적용 설정 버전을 추적합니다. 끈 순간 모든 프로세스가 바뀐다고 가정하지 않습니다. 민감 정보나 전체 사용자 ID를 무분별하게 지표 label로 넣지 않습니다.

답변 예시와 trade-off

tenant 단위의 안정적인 cohort로 결제 흐름과 worker의 판정을 맞추겠습니다. 코드 배포와 노출을 나누고 중복 결제·오류·지연을 노출별로 관측하겠습니다. off는 새 진입을 막는 완화 조치이며 이미 발생한 결제는 정합성·보상 절차로 다루겠습니다. 전체 on 뒤에도 flag owner와 제거 기한을 유지하고 구버전 참조가 사라진 뒤 설정을 정리하겠습니다.

약한 답 “오류가 나면 flag off로 rollback합니다”는 전파 지연과 데이터·외부 부작용을 생략합니다.

  • tenant cohort는 조직 경험을 일관되게 만들지만 요청 비율이 불균등합니다. user cohort는 표본이 고르게 나뉠 수 있으나 조직 내부 협업 기능이 섞일 수 있습니다.
  • 원격 판정은 제어가 빠르지만 의존성과 지연이 늘 수 있습니다. 로컬 캐시는 빠르지만 설정이 늦게 반영됩니다.
  • flag를 오래 유지하면 비상 제어에 유용할 수 있으나 경로 조합·테스트·인지 비용이 증가합니다. 영구 목적은 별도 이유와 테스트를 둡니다.

흔한 오해

release flag는 권한 검사의 대체가 아닙니다. 프런트에서 숨겨도 서버 인가가 필요합니다. SDK가 장애 때 “안전한 기본값”을 자동 고른다는 말도 위험합니다. 새 경로/구 경로 중 어떤 상태가 안전한지는 데이터와 기능 계약에 달려 있습니다.

연습과 피드백

코드에 flag 평가가 남아 있는 상태에서 flag 설정을 삭제했습니다. SDK 기본값은 false이고 서비스는 새 경로 데이터만 읽을 수 있습니다. 어떤 순서가 더 안전했나요?

해설 보기

남길 신 경로를 상수화/직접 호출하는 코드로 배포하고, 모든 서버·worker·구버전의 참조 제거를 확인한 뒤 archive해야 합니다. 설정 삭제를 먼저 하면 fallback으로 구 경로가 살아날 수 있습니다. “전체 on”과 “제거 준비 완료”를 구분한 답이 좋습니다.

Follow-up과 자기 점검

on/off 조합이 너무 많으면? 상호 배타성과 의존성을 설계하고 실제 지원 조합만 제한합니다. 핵심 조합·부작용 경계를 테스트하며 임시 flag를 빨리 제거합니다.

kill switch는 언제 제거하나? 비상 운영 목적이 계속 유효하면 장기 관리할 수 있습니다. ownership·정기 훈련·기본값 계약은 계속 필요합니다.
