배포 중 데이터베이스 호환성과 롤백 경계

DB migration의 배포 순서, 관측 지표, 안전한 contract 시점을 설명한다

핵심 판단

애플리케이션 artifact는 롤백할 수 있어도 데이터 변환은 같은 방식으로 되돌릴 수 없다. 배포 안전성은 버전 간 호환 창에 달려 있다.

배포 중에는 여러 버전의 코드가 동시에 실행될 수 있다. Expand 단계는 구 코드가 계속 동작하는 새 DB 구조를 먼저 추가하고, Contract는 모든 구 코드 사용이 끝난 후 오래된 구조를 제거한다.

검토 순서

  1. 변경 분류: additive인지 destructive인지, DDL lock·rewrite·index build 비용을 조사한다.
  2. 확장 배포: 구 코드와 호환되는 schema를 먼저 배포하고 lock wait·replication lag를 본다.
  3. 코드 전개: 새 컬럼을 dual-read/write 또는 feature flag로 단계적으로 사용한다.
  4. 데이터 검증: backfill 누락·중복·오류율과 read parity를 확인한다.
  5. contract 승인: 구 버전·rollback 창·consumer가 없고 복구 대안이 검증된 후 제거한다.

선택 비교

선택얻는 점비용·위험
한 번에 schema+code 변경적은 배포 단계로 빠르게 끝난다.rolling deploy 중 호환되지 않는 인스턴스가 생기고 rollback이 어려워진다.
Expand-Contract호환 기간을 두고 영향 범위를 작게 관찰한다.dual path와 임시 컬럼·flag를 일정 기간 운영해야 한다.
온라인 인덱스/낮은 lock DDL가용성을 유지하며 변경할 수 있다.엔진·버전별 제한과 추가 I/O·복제 부하가 남는다.

주의할 함정

오해: 자동 롤백이 있으면 DB migration도 안전하게 되돌릴 수 있다.

실제 경계: 데이터 쓰기와 외부 부작용은 되감기 어려울 수 있다. rollback은 앱 동작 복구일 뿐이며, 역변환·보상·forward fix를 사전에 정해야 한다.

면접에서 꺼낼 사례

새 기능 출시를 feature flag로 분리하면 코드 배포와 사용자 노출 시점을 분리할 수 있다. 하지만 flag off가 destructive schema 변경을 되돌리지는 않으므로 DB 호환 설계가 여전히 필요하다.

확인 질문: 신버전이 새 컬럼에만 쓰기 시작한 후 p99 오류로 자동 롤백이 발동했습니다. 구버전이 누락 필드를 어떻게 처리할지와 다음 배포 전략을 말해 보세요.

근거와 복습

PostgreSQL 공식 문서 — ALTER TABLE — DDL별 lock 조건과 대형 테이블 변경 위험을 확인한다.
