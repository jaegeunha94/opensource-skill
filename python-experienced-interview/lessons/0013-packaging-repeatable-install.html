면접 질문·상황

개발자 노트북은 성공하는데 CI와 Docker에서 import가 실패합니다. pip freeze를 공유하면 끝인가요?

가상 Python 서비스는 저장소 루트에서만 테스트했고 editable install을 사용합니다. 새 배포에서 패키지 파일이 빠졌고 transitive dependency가 달라졌습니다. 면접관은 소스 트리·배포 파일·설치 환경을 구별하는지 봅니다.

전제 개념

pyproject.toml의 build-system은 wheel 같은 배포 파일을 만드는 도구, project의 dependencies는 설치될 패키지가 실행에 필요로 하는 의존성입니다. 둘의 수명과 용도가 다릅니다. 버전 범위 선언은 호환 가능 조건이지 모든 환경에서 같은 버전을 고르는 약속은 아닙니다. 정확한 형태는 PyPA 공식 가이드가 기준입니다.

venv는 프로젝트별 설치 공간을 분리하지만 해석 결과를 고정하지 않습니다. lock 또는 완전히 고정된 설치 목록은 선택된 직접·간접 버전을 기록합니다. Python 버전·OS·CPU와 환경 marker가 다르면 설치 후보나 wheel이 달라질 수 있습니다. 해시 검증은 artifact 동일성을 높이지만 모든 플랫폼에서 동작함을 증명하지 않습니다.

답변 사고 순서·예제

  1. Python 실행 파일·버전, 현재 경로, 설치 버전, import한 파일 경로를 비교합니다.
  2. 로컬 소스가 sys.path에서 먼저 선택되는지 확인합니다. src layout은 우연히 소스를 import하는 위험을 줄이는 선택입니다.
  3. 빌드 입력과 runtime 의존성을 나누고 팀의 lock 도구·지원 플랫폼을 정합니다. Poetry를 쓴다면 그 lock 형식·명령은 해당 버전 공식 문서로 확인합니다.
  4. CI에서는 wheel을 만들고 깨끗한 venv에서 그 wheel을 설치합니다. 저장소 밖에서 import·테스트해 누락을 발견합니다.
  5. 배포에는 검증한 artifact를 그대로 승격합니다. 설치 결과·hash·Python/플랫폼을 기록해 rollback을 재현합니다.
[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"

[project]
name = "interview-demo"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = ["httpx>=0.27,<1"]

이 선언만으로는 모든 개발자가 같은 httpx 버전을 설치하지 않습니다. 빌드 도구 범위도 별도 재현성 관리가 필요합니다. pip repeatable installs의 pinning·hash·wheel 보관 방법을 비교하세요.

답변 예시·Trade-off·오해

개발 소스와 설치 wheel의 차이를 먼저 재현하겠습니다. src layout으로 로컬 루트 import를 줄이고, clean venv에 빌드한 wheel을 설치해 저장소 밖에서 검증합니다. 서비스는 직접·간접 버전을 잠그고 target 플랫폼별 설치를 검증합니다. 공개 라이브러리는 지원 범위를 선언하고 여러 의존성 조합을 테스트하겠습니다.

약한 답변: ‘pip freeze면 재현됩니다.’ 설치된 전체 환경을 보여줄 뿐 프로젝트의 필요한 입력·Python·플랫폼·artifact까지 보장하지 않습니다. 서비스의 exact pin은 재현에 좋지만 보안·버그 수정 갱신 작업이 필요합니다. 라이브러리의 너무 좁은 pin은 소비 프로젝트와 충돌할 수 있어 호환 범위·테스트 행렬을 검토합니다. editable install은 개발이 빠르지만 배포 누락을 가릴 수 있습니다.

오해: 최신 버전은 항상 안전하다. 변경 내용을 검토하고 lock 갱신 diff·설치·테스트·rollback을 같은 절차로 수행해야 합니다.

연습과 피드백

Linux wheel 테스트는 성공했습니다. macOS 개발자가 같은 lock을 설치하지 못합니다. lock 손상이라고 결론 내리기 전에 무엇을 비교합니까?

풀이 확인

Python 버전·CPU·OS, marker, 제공 wheel과 소스 빌드 의존성을 확인합니다. 특정 플랫폼 전용 artifact일 수 있습니다. ‘venv를 지우면 항상 해결’은 지원되지 않는 wheel 문제를 못 고칩니다. ‘lock을 버리고 최신 설치’는 실패 원인을 감추고 검증한 조합을 잃습니다.

Follow-up·자기 점검

빌드는 됐는데 resource 파일이 없다면? wheel 내용과 package data 설정을 확인합니다. 소스 checkout에서는 존재하지만 배포 파일에는 빠질 수 있습니다.

취약한 간접 의존성을 발견하면? dependency tree와 상위 패키지의 범위를 확인하고, 새 lock diff·지원 플랫폼·회귀를 검증합니다. 강제 버전 override의 호환성 비용도 설명합니다.
