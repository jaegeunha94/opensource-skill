Python 디버깅과 프로파일링 — 가설을 측정으로 좁히기

프로파일러를 실행하는 것보다 중요한 일은 무엇을 측정할지 정하는 것이다. 사용자 증상에서 병목 범주를 좁혀간다.

오늘의 학습 결과: CPU·대기·할당 병목을 구분하고 안전한 개선 실험을 설계한다

면접 질문

배포 뒤 API p95가 2배가 됐습니다. Python 프로파일링을 어떤 순서로 시작하겠습니까?

실무 상황: CPU 사용률은 높지 않은데 요청 지연이 증가했고, 로그에는 DB timeout과 JSON 직렬화가 함께 보인다. 로컬 단일 입력 테스트에서는 재현되지 않는다.

왜 묻는가: 증상·분포·프로파일러의 한계를 이해하고 운영 데이터와 재현 환경을 연결하는지 본다.

전제 개념

wall time은 함수가 시작해 끝날 때까지 걸린 시간이고, CPU time은 CPU에서 실제 실행된 시간이다. 둘 차이가 크면 I/O 대기, lock 대기, 스케줄링을 의심할 수 있다.

결정론적 profiler는 함수 호출 비용 분석에 편하지만 계측 오버헤드가 있다. sampling profiler는 운영에 더 적합할 수 있지만 짧은 이벤트를 놓치거나 통계 오차가 있다.

답변 사고 순서

  1. 회귀 범위: 버전·endpoint·입력 크기·tenant·리전별 p50/p95/p99와 오류율을 비교한다.
  2. 대기 분리: trace에서 DB, 외부 HTTP, lock, serialization 시간을 분해한다.
  3. 프로파일 선택: CPU가 원인이면 sampling/cProfile, 메모리 증가면 allocation snapshot, 대기면 trace를 사용한다.
  4. 재현·가설: 대표 입력과 동시성을 보존한 staging load를 만들고 가장 큰 비용 하나를 겨냥한다.
  5. 전후 비교: 동일 데이터로 p95, throughput, allocation, 오류율을 비교하고 변화 원인을 설명한다.

케이스 풀이와 답변 예시

APM trace에서 900ms 중 650ms가 DB 대기라면 Python CPU 최적화는 핵심 원인이 아니다. 반대로 DB 시간은 동일하고 `json.dumps`의 CPU 시간이 증가했다면 payload 크기·중복 변환을 조사한다.

먼저 배포 전후의 endpoint별 latency 분포와 trace span을 비교해 회귀가 어디서 생겼는지 좁히겠습니다. CPU 사용률이 낮고 DB span이 늘었다면 쿼리·pool wait를 우선 확인하고, CPU가 특정 함수에 집중되면 sampling profile로 호출 stack을 보겠습니다. 프로파일 결과 하나를 원인으로 단정하지 않고 대표 payload와 concurrency를 가진 부하에서 한 변경씩 비교하겠습니다.

답변에서 드러나는 점: 도구 목록보다 진단 순서와 증거 연결을 설명한다.

Trade-off

선택얻는 점비용·위험
cProfile함수별 호출 수·누적 CPU 시간을 쉽게 본다.deterministic instrumentation 오버헤드가 크고 전체 시스템의 대기 시간을 설명하지 못할 수 있다.
Sampling profiler운영에 가까운 낮은 오버헤드로 stack 분포를 본다.짧은 함수나 희귀 경로는 표본에서 누락될 수 있다.
Trace/APM요청의 DB·HTTP·애플리케이션 경계를 한 흐름으로 본다.sampling·계측 누락·카디널리티와 민감 정보 정책을 관리해야 한다.

흔한 오해

프로파일에서 가장 오래 보이는 함수만 최적화하면 된다.

누적 시간은 하위 함수 비용을 포함할 수 있다. 호출 수, 실제 self time, 동시성, 대표 입력과 전체 SLO를 함께 보고 최적화 가능성을 확인한다.
