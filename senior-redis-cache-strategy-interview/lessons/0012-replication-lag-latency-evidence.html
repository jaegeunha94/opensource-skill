Redis Replication과 Latency — 지연의 분모와 복제 보장

복제 차이를 시간 지연으로 오해하지 않고, client·서버·복제 지연을 구분한다.

레슨 목록 · 이전 Day 11 · 빠른 참고

면접 질문과 실무 상황

primary에 세션을 쓴 직후 replica에서 읽으니 사라졌다는 오류가 납니다. API p99도 올랐지만 SLOWLOG는 비어 있습니다. 복제와 latency를 어떻게 나눠 진단합니까?

Day 11의 왕복 비용·원자성에서 한 단계 나아가, 다른 인스턴스에 쓰기가 언제 보이는지와 어디서 시간이 드는지 봅니다.

전제 개념

Redis 기본 복제는 비동기입니다. primary의 성공 응답 시점에 모든 replica가 해당 상태를 읽게 된다고 보장하지 않습니다. replication offset은 같은 복제 이력 안에서 처리한 스트림의 바이트 위치입니다. 차이 10MB는 10초가 아닙니다.

부분 재동기화는 연결이 끊긴 동안의 누락분을 backlog에서 받는 방식입니다. 이력/보관 범위가 안 맞으면 전체 재동기화가 필요할 수 있습니다. SLOWLOG는 명령 실행 비용을 기록하며 client 네트워크·연결 풀 대기 전체를 기록하지 않습니다.

답변 사고 순서

  1. 쓰기/읽기 대상·요청 시점·read-your-write 필요성을 확인한다.
  2. 같은 replication ID에서 primary/replica offset·link 상태·동기화 진행을 비교한다.
  3. offset 차이와 증가율을 함께 보되 변동하는 쓰기율로 시간을 단정하지 않는다.
  4. client pool wait·RTT·서버 실행·큰 응답·event-loop/host 지연을 분리한다.
  5. 전체 sync·fork·persistence·긴 Lua·큰 key 작업과 p99 시간대를 비교한다.
  6. primary 읽기·WAIT 등 선택의 보장 범위와 failover 손실을 설명하고 재시험한다.

구체적 명령과 판단

# 격리된 테스트 대상에서만 실행. 접속 인증은 기존 안전한 설정 사용.
redis-cli INFO replication
redis-cli SLOWLOG GET 10
redis-cli LATENCY LATEST

LATENCY LATEST의 이벤트가 없을 때는 latency monitor 설정과 threshold를 확인해야 합니다. “관측 없음”과 “지연 없음”은 다릅니다. WAIT 1 100은 같은 client 연결의 앞선 쓰기를 replica 한 개가 확인할 때까지 최대 100ms 기다리는 요구이며 반환 개수를 확인해야 합니다. 특정 읽기 replica·강한 일관성·디스크 내구성·failover 무손실을 모두 보장하는 명령이 아닙니다.

가상 관측: 앱 pool 대기 70ms, 왕복 12ms, 명령 실행 0.2ms라면 먼저 pool과 연결/네트워크를 봅니다. SLOWLOG가 비어 있는 것은 이 가설과 양립합니다. 세션 직후 조회는 replica 지연 허용이 어렵다면 primary로 보내거나 더 강한 상태 저장 계약을 선택합니다.

답변 예시와 trade-off

쓰기 성공과 replica 가시성을 분리하겠습니다. 세션 확인 경로는 primary 읽기로 보완하고, offset은 같은 복제 이력에서만 비교하겠습니다. API 지연은 pool wait와 RTT·서버 실행을 따로 측정하겠습니다. WAIT를 써도 반환 replica 수를 확인해야 하고 failover 무손실로 과장하지 않겠습니다. sync·persistence 시점과 host 지연도 p99에 연결해 보겠습니다.

약한 답 “SLOWLOG에 없으므로 Redis 문제는 아닙니다”는 서버 실행 밖의 지연과 관측 설정을 놓칩니다.

  • replica 읽기는 primary 부하를 줄이지만 stale read가 있습니다. primary 읽기는 read-after-write에 유리하지만 부하·가용성 비용이 있습니다.
  • WAIT는 확인된 복제본 수를 늘릴 수 있지만 추가 지연과 timeout 처리 비용이 있습니다. 강한 일관성 시스템으로 바뀌지는 않습니다.
  • 큰 backlog는 짧은 단절 후 full sync를 줄일 수 있으나 메모리를 사용합니다. 실제 쓰기량·단절 시간과 맞춥니다.

흔한 오해

offset 차이가 줄었다고 요청 p99가 반드시 회복하지는 않습니다. 복제와 client latency는 서로 다른 신호입니다. 반대로 primary 영속성을 끄고 replica만 믿으면 primary의 빈 데이터 재시작이 복제본에 전파되는 위험도 있습니다.

연습과 피드백

replica A가 WAIT에 응답했지만 앱은 replica B에서 읽었습니다. 오래된 값이 나올 수 있나요? offset 차이 2MB를 “2초 지연”이라고 써도 될까요?

해설 보기

가능합니다. 확인한 replica 수가 특정 B의 최신 읽기를 뜻하지 않습니다. 2MB는 같은 이력의 바이트 차이이며 시간 단위가 아닙니다. client 대상과 복제 이력, 실제 적용 시점 관측이 필요합니다. 보장 주체를 명시한 답이 좋습니다.

Follow-up과 자기 점검

failover 뒤 offset을 비교하면? replication ID와 이전 이력 인정 범위를 확인해야 합니다. 숫자만 비교하지 않습니다.

관측 도구를 켜도 되나요? 수집 overhead·명령/데이터 노출·보관을 제한하고 짧은 진단부터 시작합니다.
