Redis Pipelining·Lua·Transaction — round trip과 원자성

network RTT·원자성·script 비용 기준으로 Redis 명령을 선택한다

핵심 판단

pipelining은 왕복 횟수를 줄이고 Lua는 서버에서 여러 명령을 실행한다. 둘은 같은 종류의 최적화가 아니다.

pipelining은 여러 command를 응답을 기다리지 않고 보내 RTT 비용을 줄인다. Lua script는 서버에서 읽기·계산·쓰기를 연속 실행해 중간에 다른 command가 끼지 않게 한다. MULTI/EXEC는 command 묶음 실행을 제공하지만 일반적인 rollback transaction과는 다르다.

검토 순서

  1. 병목 측정: client RTT, command server time, payload 크기와 connection pool wait를 나눈다.
  2. 의미 확인: 명령 간 중간 상태가 다른 client에 보여도 되는지, 원자적 check-update가 필요한지 정한다.
  3. 전략 선택: 독립 명령은 pipeline, 조건부 read-modify-write는 Lua 또는 적합한 atomic primitive를 검토한다.
  4. 제한 설계: pipeline batch 크기와 script 실행 시간을 제한하고 timeout/retry semantics를 정한다.
  5. 비용 검증: p99, Redis event-loop latency, memory, network bytes와 failover behavior를 비교한다.

선택 비교

선택얻는 점비용·위험
PipeliningRTT를 줄이고 throughput을 높인다.응답 전 조건 분기와 원자적 read-modify-write를 제공하지 않는다.
Lua script읽기·계산·쓰기를 Redis 안에서 원자적으로 수행한다.오래 실행되면 Redis command 처리 전체를 지연시킬 수 있다.
MULTI/EXEC명령 묶음 경계를 만들고 watch 기반 optimistic 흐름이 가능하다.SQL식 rollback이 아니며 WATCH conflict 재시도 부하가 있다.

주의할 함정

오해: pipeline으로 여러 명령을 보냈으니 그 작업은 원자적이다.

실제 경계: 다른 client command가 처리되는 시점과 조건부 실행은 별개다. 중간 불변식이 보여도 되는지 확인하고 atomic script/transaction primitive를 선택한다.

면접에서 꺼낼 사례

rate limit은 `INCR` 뒤 첫 요청이면 `EXPIRE` 해야 한다. 두 command가 분리돼 expire가 누락되면 key가 영구히 남을 수 있으므로 Lua나 원자 명령 조합이 적절한지 검토한다.
