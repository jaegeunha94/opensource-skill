에이전트 간 handoff — 상태·권한·복구 계약

위임 입력·출력 스키마와 재시작 가능한 조정 흐름을 만든다

핵심 판단

에이전트를 늘리는 것보다 handoff 계약을 명확히 하는 것이 중요하다. 다음 에이전트가 무엇을 알고 어떤 행동을 할 수 있는지 제한한다.

handoff는 단순히 대화 내용을 복사하는 것이 아니라 작업 소유권과 상태를 다른 실행 주체에 넘기는 경계다. 입력 스키마, 기대 산출물, 제한된 tool permission이 필요하다.

검토 순서

  1. 분해 가능성: 작업 간 dependency와 공유 파일·상태를 그려 병렬로 안전한 부분만 분리한다.
  2. handoff schema: 목표, 관련 파일, 불변조건, 근거 링크, 제한, 완료 판정을 구조화한다.
  3. 격리: agent별 tool allowlist와 worktree/파일 경계를 두고 credential은 최소화한다.
  4. 조정·검증: 중간 결과를 검증자에게 전달하고 실패·timeout·부분 완료 상태를 기록한다.
  5. 복구: idempotent task id, checkpoint, 취소 전파, 재실행/사람 승격 조건을 정한다.

선택 비교

선택얻는 점비용·위험
단일 agent 순차 실행상태와 책임이 명확하고 충돌이 적다.독립 작업의 latency와 컨텍스트 한계가 커질 수 있다.
다중 agent 병렬 실행독립적인 조사·검토의 wall time을 줄일 수 있다.handoff 비용, 불일치, 중복 작업, 파일 충돌과 비용이 증가한다.
공유 대화 전체 전달배경 정보를 넓게 제공한다.불필요한 토큰·민감 데이터 노출·지시 혼선을 늘린다.

주의할 함정

오해: agent 수가 많을수록 작업은 더 빠르고 정확하다.

실제 경계: 병렬화 이득은 독립성에서 나오고, 결과 통합·검증 비용이 이를 넘어설 수 있다. 정확성은 권한 제한과 검증 계약이 만든다.

면접에서 꺼낼 사례

조사 agent는 읽기 전용으로 영향 파일과 근거를 반환하고, 구현 agent는 지정한 파일 범위에서만 수정한다. 마지막 reviewer가 계획·diff·요구사항을 대조한 뒤 병합 여부를 판단한다.

확인 질문: 두 agent가 같은 `auth.py`를 수정할 계획을 냈습니다. 실행을 어떻게 재구성하고 결과를 통합하겠습니까?
