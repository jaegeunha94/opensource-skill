Streaming과 Structured Output — 미완료 조각과 실행 경계

첫 조각을 빨리 보여주는 흐름과 검증된 도구 실행을 분리한다.

레슨 목록 · 이전 Day 8 · 빠른 참고

면접 질문과 실무 상황

환불 도구 인자를 스트리밍하며 {"amount": 10이 도착하자 실행했습니다. 다음 조각은 00}였습니다. 빠른 응답을 위해 먼저 실행하는 것이 괜찮을까요?

Day 8의 위임 결과 계약을 오늘은 조각 단위 전송에 적용합니다. 면접관은 사용자에게 보인 진행과 실제 완료·검증·외부 부작용의 시점을 분리하는지 봅니다.

전제 개념

SSE는 서버가 하나의 HTTP 응답 안에서 event를 순차로 보내는 방식입니다. 네트워크 chunk, SSE event, 모델 content block은 서로 같은 경계가 아닙니다. 임의 TCP 조각을 곧바로 JSON 하나라고 parse하면 실패할 수 있습니다.

structured output은 요구 schema 형태를 맞추는 기능입니다. schema가 맞아도 금액·대상·권한·업무 상태가 틀릴 수 있습니다. partial JSON은 완성된 객체가 아니고, 정상 종료를 확인하지 않은 결과는 최종 답이 아닐 수 있습니다.

답변 사고 순서

  1. 텍스트 preview, 도구 인자 조립, 최종 상태, 실행 원장을 분리한다.
  2. event를 block index/tool call ID별로 조립하고 최대 byte·시간·queue 크기를 제한한다.
  3. block 종료와 message 종료·stop reason·refusal/error를 확인한다.
  4. 완전한 인자를 schema와 업무 규칙으로 검증한 뒤 권한/필요 승인을 확인한다.
  5. 멱등 key로 도구를 실행하고 성공 결과가 확인된 뒤 사용자에게 완료를 알린다.
  6. 연결 단절·취소·재접속은 preview 복구와 외부 실행 상태 확인을 따로 처리한다.

구체적 상태 기계

Receiving → BlockComplete → MessageAccepted
          → SchemaValid → Authorized → Executing → Confirmed
Receiving → Disconnected / Truncated / Error   # 실행하지 않음
Executing → UnknownOutcome                    # 외부 상태 조회

가상 입력 조각 {"amount": 10 + 00,"currency":"KRW"}는 합쳐서 1000원을 뜻합니다. preview에서 보인 10으로 금액을 확정하면 안 됩니다. UI는 “요청 준비 중” 같은 명시적 진행 상태를 보여주고 완료 상태는 실행 확인에서만 나옵니다.

현재 Anthropic fine-grained 문서는 tool별 eager_input_streaming을 설명하며 partial/invalid JSON과 max_tokens 중단 처리를 요구합니다. 이전 beta header만을 신규 예시의 기본값으로 복사하지 않습니다. 일반 streaming 문서의 block index로 조각을 모으고, 한 block 종료를 전체 message 성공으로 혼동하지 않습니다.

답변 예시와 trade-off

첫 조각은 진행 표시로만 사용하고 환불 실행은 완전한 인자와 정상적인 종료를 확인한 뒤 하겠습니다. schema 외에 금액·통화·주문 소유권·승인을 검증하고 멱등 key로 실행하겠습니다. 연결이 끊기면 생성 미완료와 이미 실행된 도구의 결과 불명을 분리해서 복구하겠습니다. TTFT뿐 아니라 최종 완료·실패·취소 지연을 측정하겠습니다.

약한 답 “JSON이 parse되면 즉시 실행합니다”는 후속 수정·stop reason·업무 검증을 놓칩니다.

  • 즉시 text 표시와 fine-grained 인자 전송은 체감 지연을 줄이지만 조립·중단·민감 내용 노출 관리가 늘어납니다.
  • 완료 뒤 전체 표시하면 안정적이나 대기 시간이 길게 느껴집니다. 고위험 결과는 보수적으로, 일반 설명은 preview로 나눌 수 있습니다.
  • 느린 client를 무한 buffering하면 서버 메모리가 증가합니다. bounded queue·backpressure·취소는 안정적이지만 재접속 경험을 설계해야 합니다.

흔한 오해

HTTP 200은 stream 전체 성공을 보장하지 않습니다. 중간 error와 정상 종료 유무를 검사해야 합니다. 클라이언트 연결을 끊었다고 이미 시작한 외부 결제까지 취소되었다고 말해서도 안 됩니다. SSE 재접속 기능이 특정 생성 API의 자동 resume/replay 지원을 뜻하지 않습니다.

연습과 피드백

JSON 객체가 완성됐지만 최종 stop reason이 max_tokens이고 승인 필드가 아직 없었습니다. 한편 다른 시도는 환불 실행 뒤 연결이 끊겼습니다. 두 시도를 어떻게 처리합니까?

해설 보기

첫 시도는 완결 조건·필수 업무 정보가 없으므로 실행하지 않고 오류/재생성으로 처리합니다. 둘째는 같은 key로 외부 환불 상태를 확인해 성공/실패/불명을 해소합니다. 무조건 전체 재시도하면 중복 환불 위험이 있습니다. 생성 완료와 실행 완료의 경계를 분리한 답이 좋습니다.

Follow-up과 자기 점검

여러 tool block이 섞이면? index/ID별 버퍼와 상태를 유지하고 의존성이 있는 실행은 검증된 순서로 진행합니다.

TTFT가 줄었는데 고객 불만이 늘면? 최종 완료 시간·중간 수정·실패율·preview 의미를 함께 봅니다. 빨리 나온 틀린 확정 문구는 품질 개선이 아닙니다.
