ETag와 조건부 요청 — 캐시와 동시 수정의 경계

ETag는 단순한 캐시 문자열이 아니다. GET 재검증과 쓰기 전 조건 검사에서 서로 다른 장애를 막는다.

오늘의 학습 결과: If-None-Match와 If-Match의 용도를 구별한다

면접 질문

정적 보고서의 다운로드 비용을 줄이면서 두 사용자의 동시 수정으로 덮어쓰는 일을 막으려면 ETag를 어떻게 쓰겠습니까?

실무 상황: 보고서는 자주 읽고 가끔 수정된다. 여러 CDN과 브라우저가 캐시하고, 동일 문서를 편집하는 사용자가 동시에 저장할 수 있다.

왜 묻는가: validator의 strong/weak 의미와 304·412 응답, 캐시 일관성을 정확히 말하는지 평가한다.

전제 개념

ETag는 representation에 붙는 validator다. GET에 `If-None-Match`를 보내면 변경 여부를 재검증하고, 쓰기에 `If-Match`를 보내면 읽은 버전이 아직 현재인지 확인할 수 있다.

weak ETag는 의미상 동등한 representation에 쓸 수 있지만 byte-for-byte 동일성이 필요한 range/strong comparison의 조건과 다르다. 사용자별 응답을 공유 캐시에 넣을 때는 개인 정보 분리를 먼저 해야 한다.

답변 사고 순서

  1. representation 정의: 압축·언어·권한별 변형이 같은 validator를 공유해도 되는지 정한다.
  2. 읽기 재검증: If-None-Match가 일치하면 body 없이 304와 적절한 cache metadata를 반환한다.
  3. 쓰기 보호: 수정 요청의 If-Match를 원자적으로 비교하고 낡은 버전이면 412로 거부한다.
  4. 생성 전략: 내용 hash, DB version, weak/strong 선택을 표현 변형과 비용에 맞춘다.
  5. 경계 검증: CDN cache key, Vary, private/no-store, 동시 업데이트 테스트를 확인한다.

케이스 풀이와 답변 예시

사용자 A와 B가 version 7을 읽었다. A가 If-Match version 7로 수정해 version 8을 만들면, B의 같은 조건부 수정은 412로 실패해야 하고 최신 버전을 다시 읽도록 안내해야 한다.

캐시 재검증에는 `If-None-Match`를 사용해 같은 representation이면 304로 body 전송을 줄이겠습니다. 수정에는 strong validator를 `If-Match`로 보내고 서버에서 version 비교와 업데이트를 원자적으로 처리하겠습니다. 현재 버전과 다르면 412를 반환해 클라이언트가 최신 데이터를 병합하도록 하겠습니다. 압축이나 언어별 representation은 validator와 `Vary`가 정확히 구분되는지도 확인하겠습니다.

답변에서 드러나는 점: GET 효율과 write concurrency를 별도의 조건부 요청 계약으로 설명한다.

Trade-off

선택얻는 점비용·위험
내용 hash ETagrepresentation에 대한 강한 식별이 가능하다.큰 응답의 hash 계산과 압축/변형별 계산 비용이 든다.
DB version ETag생성 비용이 낮고 lost update 방지에 쓰기 좋다.실제 전송 representation이 바뀌어도 version 갱신이 누락되면 잘못된 validator가 된다.
Last-Modified쉽고 사람이 읽을 수 있는 시각 기준이다.초 단위 정밀도와 시계/동일 초 수정에서 충돌할 수 있다.

흔한 오해

ETag가 있으면 브라우저와 CDN이 알아서 최신 값을 유지한다.

ETag는 validator일 뿐 cacheability·freshness·privacy 정책을 대체하지 않는다. Cache-Control과 Vary, 인증 응답 분리를 함께 설정해야 한다.

직접 풀어보기

클라이언트가 version 12를 읽었는데 서버는 이미 13입니다. `If-None-Match`로 PUT을 보냈다면 무엇이 잘못됐고 어떤 응답이 적절합니까?

예시 풀이와 피드백 보기

PUT의 lost update 보호에는 `If-Match: version-12`를 사용해야 한다. version mismatch는 412 Precondition Failed로 거부하고, 클라이언트가 현재 representation을 다시 읽게 한다.
