Compression — 전송량·CPU·캐시 표현의 경계

Day 9 ETag의 표현 구분을 압축 변형에 적용하고, 압축이 이득인 요청을 수치로 고른다.

면접 질문과 실무 상황

gzip을 켜자 전송량은 줄었는데 API p99가 나빠졌습니다. Brotli로 바꾸면 해결될까요?

가상 API는 1MB JSON 보고서를 초당 500회 동적으로 생성합니다. 압축 후 200KB가 되지만 요청당 CPU 8ms가 추가됩니다. 면접관은 압축률만 말하는지, CPU·큐 대기·캐시 변형을 함께 판단하는지 봅니다.

전제 개념

압축은 같은 정보를 더 적은 바이트로 표현하고 수신자가 원래 정보로 복원하는 작업입니다. Content-Type: application/json은 내용의 종류, Content-Encoding: gzip은 전송 표현에 적용한 코딩입니다. 클라이언트가 받을 수 있는 코딩은 Accept-Encoding으로 알립니다. RFC 9110 §8.4에서 이 구분을 확인하세요.

압축 변형을 응답 선택에 사용한다면 Vary: Accept-Encoding 또는 같은 효과의 CDN 캐시 키가 필요합니다. gzip을 못 읽는 클라이언트에게 저장된 gzip 표현을 주면 바이트는 적어도 응답이 잘못됩니다. Day 9의 strong ETag도 서로 다른 바이트 표현을 구분해야 합니다.

답변 사고 순서와 사례

  1. 느려진 구간을 서버 압축 CPU, 큐 대기, 네트워크 전송, 수신자 해제로 나눕니다.
  2. 대표 payload 크기·압축률·CPU 시간·p95/p99를 같은 트래픽에서 비교합니다.
  3. 미압축 1MB→0.2MB이면 0.8MB 절감입니다. 10MB/s 링크에서 순수 전송 시간 약 80ms가 줄지만, 충분히 빠른 링크에서는 이득이 작아집니다.
  4. 500회/s×8ms는 초당 CPU 4초, 즉 약 4코어 상당의 추가 CPU 작업입니다. 남은 용량을 넘으면 큐 지연이 전송 이득을 없앱니다.
  5. 정적 파일은 빌드 때 gzip/br 변형을 만들고, 동적 JSON은 최소 크기와 압축 수준을 측정해 고릅니다. JPEG처럼 이미 압축된 형식은 이득이 작을 수 있습니다.

Nginx gzip 모듈의 최소 길이·코딩 협상·Vary 옵션을 실제 경계별로 확인합니다. ‘Brotli면 항상 빠르다’는 결론은 압축 수준과 동적/사전 압축 구분을 빠뜨립니다.

답변 예시·Trade-off·오해

p99 악화가 압축 CPU와 큐 대기에서 발생했는지 먼저 보겠습니다. 대형 보고서는 전송 절감이 크므로 사전 생성·엣지 캐시를 검토하고, 동적 응답은 크기별 임계값과 압축 수준을 제한하겠습니다. Vary와 표현별 ETag를 검증하며 CPU·대역폭·클라이언트 해제 비용을 함께 비교하겠습니다.

약한 답변: ‘br의 압축률이 좋으니 모두 br로 보냅니다.’ 코딩 지원과 생성 비용이 빠졌습니다. 사전 압축은 요청 CPU를 줄이지만 빌드 시간·저장 공간·무효화 관리가 늘고, 동적 압축은 최신 내용을 바로 제공하지만 피크 CPU를 소비합니다. 작은 응답의 압축 제외는 CPU를 아끼지만 전송량을 늘립니다.

흔한 오해: Content-Encoding을 붙이면 프록시가 알아서 압축한다. 헤더는 실제 바이트에 맞아야 합니다. 서로 다른 경계가 중복 압축하거나 코딩 헤더만 제거하면 디코딩이 실패합니다.

연습과 피드백

동적 응답 1000회/s에 압축 CPU 5ms가 추가됩니다. 여유 CPU는 2코어입니다. 대역폭 절감만 보고 전면 적용해도 됩니까?

풀이 확인

추가 CPU는 약 5코어 상당이므로 여유 2코어를 넘습니다. 코딩 수준을 낮추거나 큰 응답에만 적용하고, 사전 생성·캐시로 압축 횟수를 줄인 뒤 다시 부하를 측정합니다. ‘서버 평균 CPU가 낮으니 괜찮다’는 버스트와 큐를 놓치고, ‘압축을 항상 끈다’는 느린 링크의 큰 이득을 놓칩니다.

Follow-up과 자기 점검

gzip과 identity가 같은 strong ETag여도 되나요? 코딩된 바이트가 다르므로 표현별 validator를 구분합니다. 의미상 동등성만 나타내려면 weak validator의 허용 범위를 별도로 검토합니다.

민감값과 사용자 입력을 같은 응답에 압축하면? 응답 길이를 반복 관찰하는 압축 side-channel의 조건을 위협 모델에 포함합니다. 해당 응답에서 압축 제외·입력과 비밀 분리 같은 완화를 검토합니다. Nginx 문서의 BREACH 경고를 읽으세요.
