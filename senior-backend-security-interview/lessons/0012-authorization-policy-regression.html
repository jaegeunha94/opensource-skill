보안 회귀 테스트 — 인가 정책과 모든 실행 경로 검증

허용·거부 정책을 테스트 행렬로 옮기고, HTTP와 비동기 경로의 동일한 경계를 검증한다.

면접 질문과 실무 상황

Day 11에서는 tenant 범위 조회로 타 고객 객체 접근을 막았습니다. 새로 추가된 CSV 내보내기 worker가 객체 ID만 받아 tenant 검사를 생략했습니다. 기존 API 인가 테스트는 모두 통과합니다. 어떻게 회귀를 막겠습니까?

면접의 초점은 테스트 개수가 아니라 정책과 실제 실행 경로의 연결입니다. 로그인 성공을 자원 접근 허용으로 착각하지 않아야 합니다.

전제 개념

인증은 누구인지 확인하는 일, 인가는 그 주체가 그 자원에 그 행동을 해도 되는지 결정하는 일입니다. 정책은 주체·자원·행동·맥락에 대한 규칙입니다. 예를 들어 “같은 tenant의 editor만 미잠금 문서를 수정할 수 있다”에는 tenant, 역할, 잠금 상태가 모두 필요합니다.

정책 함수 단위 테스트는 규칙을 확인합니다. 통합 테스트는 요청·worker·DB까지 실제 경로가 그 규칙을 사용하는지 확인합니다. mock으로 항상 allow를 반환하면 가장 중요한 경계를 검사하지 못합니다. OWASP는 기본 거부, 요청마다의 권한 확인과 인가 테스트를 권고합니다.

답변 사고 순서

  1. 자원과 행동 목록을 만든다: 읽기·수정·삭제·목록·검색·bulk export·worker.
  2. 허용 규칙과 거부 규칙을 명시한다. 권한 철회와 잠금 상태 변화도 포함한다.
  3. 정책 행렬을 경계값으로 만든다: 같은/다른 tenant, editor/viewer, 잠금/미잠금.
  4. 직접 요청과 간접 작업을 실제 정책·범위 조회로 실행한다. 큐 입력은 권한의 증거로 믿지 않는다.
  5. HTTP 코드뿐 아니라 DB 변경·CSV 내용·외부 전송 등 부작용이 없음을 확인한다.
  6. 거부된 사유는 내부 감사에 남기고, 외부에는 자원 존재 여부가 불필요하게 드러나지 않게 일관된 응답 정책을 적용한다.

테스트 행렬과 구체적 예시

주체/맥락행동예상과 확인
T1 editor, T1 미잠금 문서수정허용, 변경 내용 일치
T1 viewer, T1 문서수정거부, 원문·버전 그대로
T1 editor, T2 문서읽기·export거부, 본문·파일·큐 결과에 T2 정보 없음
작업 예약 뒤 역할 철회worker export실행 시점 정책에 따라 거부, 발송 없음
# 프레임워크 독립적인 테스트 의사코드
job = request_export(actor=T1_editor, document=T1_doc)
revoke_export_permission(T1_editor)
run_worker(job)
assert no_file_was_published(job)
assert audit_reason(job) == "permission_revoked"

예약 시점 권한을 고정할지 실행 시점에 재확인할지는 제품 정책입니다. 이 사례는 민감 문서의 권한 철회가 실행 전에 반영되어야 한다고 가정합니다. worker는 신뢰된 작업 메타데이터에서 주체와 범위를 읽고 정책을 다시 확인합니다. 사용자 제공 tenant 값을 그대로 신뢰하지 않습니다.

답변 예시와 trade-off

API와 worker가 공유하는 인가 경계를 정하겠습니다. 정상 요청 한 개뿐 아니라 다른 tenant 객체, viewer의 수정, 예약 뒤 권한 철회를 테스트하겠습니다. 거부 응답과 함께 데이터 변경·파일 공개·메일 전송이 없음을 확인하고, bulk 경로에서도 각 객체의 범위를 검증하겠습니다. 정책 변경은 행렬을 먼저 리뷰하고 회귀 테스트로 고정하겠습니다.

약한 답 “모든 endpoint에 로그인 decorator를 붙입니다”는 자원별 권한과 비동기 실행을 놓칩니다.

  • 중앙 정책 함수는 일관성을 높이지만 호출 누락이 가능합니다. 실제 진입 경로 테스트와 경계 설계를 함께 둡니다.
  • 실행 때 재확인은 철회를 빠르게 반영하지만 정책 서비스 장애가 작업 실패로 이어질 수 있습니다. 민감 작업은 기본 거부·안전한 재시도를 우선합니다.
  • 모든 조합을 열거하면 비용이 큽니다. 핵심 정책 경계와 과거 결함 사례를 고정하고, 생성 기반 테스트로 범위를 넓힙니다.

흔한 오해

403만 확인하면 안전하다는 오해가 있습니다. 거부하기 전에 부작용이 발생했을 수도 있습니다. UUID가 추측하기 어렵다는 사실도 인가를 대신하지 않습니다. 숨긴 UI 버튼은 서버 정책의 증거가 아닙니다.

연습과 즉시 피드백

bulk export 요청에 T1 문서 9개와 T2 문서 1개가 섞였습니다. 정책은 “하나라도 불허면 전체 거부”입니다. 어떤 assertion이 빠지면 결함을 놓칠까요?

해설과 대안 비교

상태 코드 외에 export job 미생성, 파일 미공개, T2 내용 미포함, 외부 발송 미발생을 확인합니다. 이미 작업을 등록했다면 취소 상태와 worker의 재검증까지 검사해야 합니다. 허용된 9개만 내보내는 방식은 다른 제품 정책이므로 이 요구의 정답이 아닙니다. 정책별 부작용을 먼저 명시한 답이 좋습니다.

Follow-up과 자기 점검

admin은 모든 tenant에 접근 가능한가? 이름만으로 결정하지 않습니다. 승인된 업무 범위·감사·만료 조건을 명시하고 예외 정책도 테스트합니다.

인가 판단 뒤 자원 소유자가 바뀐다면? 검사와 사용 사이 상태 변화입니다. 트랜잭션 안의 범위 제한 쓰기, 버전 검사 등으로 현재 조건을 확인하고 실패 시 재판단합니다.
