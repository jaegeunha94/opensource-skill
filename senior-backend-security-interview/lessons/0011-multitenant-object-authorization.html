멀티테넌트 인가 — 객체 경계에서 IDOR 막기

로그인 여부는 객체 접근 허가가 아니다. 요청자가 어떤 조직에 속하며 그 객체를 어떤 동작으로 사용할 수 있는지 매 요청에서 확인한다.

오늘의 학습 결과: tenant 식별과 object authorization의 강제 위치·테스트를 설계한다

면접 질문

다중 tenant SaaS에서 `/invoices/{id}` API의 IDOR를 어떻게 예방하고 탐지하겠습니까?

실무 상황: 사용자는 여러 조직에 속할 수 있고, invoice id는 UUID다. API는 인증은 하지만 조회 쿼리가 `WHERE id = ?`만 사용한다.

왜 묻는가: UUID를 보안 경계로 오해하지 않고 인증 주체·tenant context·객체 관계를 연결하는지 본다.

전제 개념

인증은 ‘누구인가’를 확인하고, 인가는 ‘이 주체가 이 객체에 이 작업을 할 수 있는가’를 판단한다. 객체 id를 추측하기 어렵게 만들어도 인가 누락은 막지 못한다.

tenant id를 request body에서 그대로 믿으면 공격자가 다른 tenant를 지정할 수 있다. 신뢰 가능한 인증 context에서 tenant membership을 확인하고 모든 data access 경로에 scope를 적용해야 한다.

답변 사고 순서

  1. 주체 확정: 검증된 token/session에서 user id와 활성 tenant를 얻고 membership·role을 확인한다.
  2. 객체 범위: 조회·수정·다운로드·삭제마다 tenant와 관계를 결합해 대상 객체를 찾는다.
  3. 권한 세분화: role만 보지 말고 객체 소유·상태·작업 유형과 업무 정책을 평가한다.
  4. 다층 강제: repository query, DB constraint/RLS, service policy가 같은 tenant 경계를 지키게 한다.
  5. 음성 테스트: tenant A 토큰으로 tenant B 객체의 모든 HTTP method와 background job 경로를 시도한다.

케이스 풀이와 답변 예시

핸들러에서 invoice를 전역 조회한 뒤 별도 if 문으로 tenant를 비교하면 새 endpoint나 export job에서 검사가 빠질 수 있다. 기본 조회 API 자체가 tenant scope를 강제하도록 만든다.

tenant는 body의 값이 아니라 인증 context의 활성 membership으로 정하겠습니다. repository에서 `tenant_id = principal.tenant_id AND id = :invoice_id`로 조회해 객체 존재 여부도 같은 범위에서 확인하고, 수정에는 상태 전이를 포함한 조건부 업데이트를 사용하겠습니다. DB RLS를 추가 방어로 쓰더라도 pool connection의 session context 누출을 검증하고, tenant 간 접근 거부를 API·worker·export 테스트에 포함하겠습니다.

답변에서 드러나는 점: 한 곳의 if 문이 아니라 데이터 접근 경계와 모든 실행 경로에 일관된 정책을 둔다.

Trade-off

선택얻는 점비용·위험
애플리케이션 scope query정책을 이해하기 쉽고 도메인별 예외를 표현하기 좋다.새 repository 경로에서 scope 조건이 누락될 위험이 있다.
DB Row-Level Security쿼리 누락을 DB에서 막는 방어층이 된다.connection pool의 role/session context 관리와 운영 디버깅이 복잡해진다.
복합 tenant/object key관계 제약과 tenant 범위를 스키마에 드러낸다.기존 스키마·join·외부 API 변경 비용이 발생한다.

흔한 오해

객체 ID가 UUID면 다른 tenant의 리소스를 안전하게 숨길 수 있다.

불투명한 ID는 열거를 어렵게 할 뿐 접근 통제는 아니다. 유출·로그·링크 공유를 고려해 모든 객체 작업에서 권한을 확인해야 한다.

직접 풀어보기

다운로드는 인가 검사를 하지만 CSV export worker는 `invoice_id` 목록만 받아 전역 조회합니다. 어떤 경계와 테스트를 추가하겠습니까?

예시 풀이와 피드백 보기

worker가 검증된 tenant/principal context와 작업 권한을 전달받고 tenant-scoped query를 사용한다. export 생성 시점과 다운로드 시점 모두 접근권한 및 만료 정책을 확인하고, 교차 tenant ID를 포함한 비동기 테스트를 둔다.
