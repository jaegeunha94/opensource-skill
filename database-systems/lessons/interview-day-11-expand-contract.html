무중단 스키마 변경 — Expand·Migrate·Contract

DB 변경은 롤백 버튼만으로 되돌아가지 않는다. 구·신 버전이 같은 스키마를 함께 쓰는 시간대를 설계해야 한다.

오늘의 학습 결과: 호환 가능한 단계와 데이터 backfill·제거의 안전 조건을 정의한다

면접 질문

대형 주문 테이블의 `customer_name`을 정규화된 `customer_id` 참조로 교체하면서 배포 중단을 피하려면 어떻게 하겠습니까?

실무 상황: 테이블은 수십억 행이고 여러 애플리케이션 버전이 동시에 서비스된다. 쓰기 트래픽이 높고 DDL이 큰 lock을 잡으면 지연이 급증한다.

왜 묻는가: DDL 문법보다 배포 순서, 호환성, backfill 재개, 검증 및 제거 조건을 설계하는지 본다.

전제 개념

Expand-Contract는 새 구조를 먼저 추가해 구·신 코드가 함께 동작하게 하고, 데이터를 옮기고, 사용이 끝난 뒤 오래된 구조를 제거하는 방식이다. 애플리케이션과 DB를 한 순간에 함께 바꿀 수 없다는 전제가 핵심이다.

컬럼 추가도 DB 버전·기본값·제약·테이블 크기에 따라 lock이나 rewrite를 만들 수 있다. “짧은 DDL이니 안전하다”로 단정하지 말고 사용하는 엔진의 동작을 확인해야 한다.

답변 사고 순서

  1. 호환성 표: 구버전/신버전 앱이 각 스키마에서 읽고 쓸 수 있는 조합을 적는다.
  2. Expand: 새 nullable 컬럼과 인덱스를 안전한 방식으로 추가하고 lock 대기 시간을 감시한다.
  3. Dual write: 전환기 동안 구·신 표현을 함께 기록하되, 실패 원자성과 재시도 동작을 정한다.
  4. Backfill: 작은 keyset batch로 재개 가능하게 복사하고, replica lag와 DB 부하에 따라 속도를 제한한다.
  5. 검증·전환: 불일치 샘플, row count, shadow read를 비교한 뒤 읽기 경로를 전환한다.
  6. Contract: 구버전 인스턴스와 롤백 가능 기간이 사라진 것을 확인한 후 제약·구 컬럼을 제거한다.

케이스 풀이와 답변 예시

처음부터 NOT NULL과 새 외래키를 한 번에 걸기보다 nullable 추가 → 배치 backfill → 누락 검증 → 새 코드 사용 → 구 코드 제거 → 제약 강화 순으로 쪼갠다.

먼저 배포 중 공존할 코드 버전의 read/write 행렬을 만들겠습니다. 새 컬럼을 추가하고 구버전과 호환되는 dual-write를 배포한 뒤, checkpoint가 있는 작은 batch로 backfill하겠습니다. 새 컬럼 누락과 값 불일치가 0이고 replica lag가 기준 안에 있을 때 read를 전환하고, 구버전 인스턴스와 롤백 창이 끝난 뒤에만 구 컬럼을 제거하겠습니다.

답변에서 드러나는 점: 순서를 명확히 하고 각 단계의 진입 조건과 중단 지표를 제시한다.

Trade-off

선택얻는 점비용·위험
동기 dual-write두 필드가 즉시 같이 갱신된다.한쪽 실패 시 부분 성공 위험이 있어 트랜잭션 또는 보상 설계가 필요하다.
비동기 backfill부하를 조절하고 중단·재개하기 쉽다.전환 전까지 데이터 지연과 불일치 검증을 운영해야 한다.
단일 큰 UPDATE구현이 짧고 완료 시점이 명확하다.긴 lock, WAL 폭증, replica lag와 rollback 비용을 만들 수 있다.

흔한 오해

배포는 롤백하면 되고 DB 변경도 이전 상태로 쉽게 돌릴 수 있다.

새 형식으로 쓰인 데이터는 구 코드가 해석하지 못할 수 있다. Contract는 롤백 창이 닫힌 뒤에 수행하며, 데이터 변환의 역방향 가능성을 따로 평가해야 한다.

직접 풀어보기

배치 backfill 중 primary 부하는 괜찮지만 replica lag가 90초로 늘었습니다. 어떤 조치와 재개 기준을 정할까요?

예시 풀이와 피드백 보기

batch 크기/속도를 줄이거나 중단하고 lag가 회복되는지 관찰한다. checkpoint로 재개하며, primary 지표만으로 안전을 선언하지 않는다. 승인된 lag SLO 아래에서 일정 시간 유지될 때 점진적으로 재개한다.
