복제 지연과 read-your-writes 보장 설계

Day 7 복제를 정의 암기에서 벗어나, 자기 쓰기를 읽을 때의 라우팅 계약과 timeout으로 구체화한다.

레슨 목록 · 이전 Day 11 · 빠른 참고

면접 질문·상황

주문 생성은 성공했는데 다음 조회에서 ‘주문 없음’이 나옵니다. replica를 더 늘리면 해결됩니까?

가상 서비스는 primary에 주문을 쓰고 GET은 무작위 replica로 보냅니다. backfill 중 한 replica의 재생 지연이 3초입니다. 면접관은 복제 처리 단계와 사용자가 요구하는 일관성을 연결하는지 봅니다.

전제 개념

복제는 primary의 변경 기록을 replica가 받아 자기 데이터에 적용하는 과정입니다. 기록을 받았다, 디스크에 저장했다, 쿼리에 보이도록 재생했다는 서로 다릅니다. read-your-writes는 한 사용자가 완료한 쓰기를 그 사용자의 다음 읽기가 반영해야 한다는 계약입니다. 모든 사용자의 모든 읽기를 최신 상태로 만드는 계약보다 범위가 좁습니다.

PostgreSQL의 WAL 위치인 LSN은 로그의 순서상 위치입니다. 동기 복제 문서에서 remote_write·on·remote_apply의 대기 수준을 구분하세요. 동기 복제라는 말만으로 모든 replica에 즉시 읽기 가시성이 생긴다고 단정할 수 없습니다.

답변 사고 순서·구체적 설계

  1. 쓰기 commit이 성공했는지, 같은 주문·tenant·사용자·조회 시점을 비교합니다. 캐시도 읽기 경로에 있으면 따로 확인합니다.
  2. 요구사항을 ‘주문한 본인은 즉시 조회’와 ‘통계는 수초 지연 허용’으로 나눕니다.
  3. 단순한 정책은 주문 생성 후 해당 세션의 중요 조회를 primary에 보냅니다. 고정 3초 pinning은 lag가 더 길어지면 실패하므로 엄밀한 보장이 아닙니다.
  4. 위치 기반 정책은 같은 클러스터 이력에서 성공한 쓰기 이후의 안전한 WAL 위치를 토큰으로 전달합니다. 선택한 replica의 replay LSN이 토큰 이상일 때 읽고, 아닐 때 제한된 시간만 기다립니다.
  5. timeout이면 primary로 우회하거나 ‘조회 준비 중’ 상태를 계약에 따라 반환합니다. 기다리는 동안 얻은 오래된 트랜잭션 snapshot은 갱신해야 하므로, 재생 확인 후 새 조회 snapshot을 사용합니다.

예: 토큰 위치 1200, replica A replay 1180, B replay 1210이라면 같은 이력의 B가 후보입니다. 실제 LSN은 이 가상 정수처럼 단순 숫자가 아니며 pg_last_wal_replay_lsn() 등의 타입·비교 함수를 사용합니다. failover 뒤에는 이전 이력 토큰을 무조건 비교하지 않고 클러스터·epoch 계약을 검증합니다.

답변 예시·Trade-off

replica 증설은 용량을 늘리지만 자기 쓰기 가시성은 보장하지 않습니다. 우선 주문 직후 조회는 primary에 보내겠습니다. 읽기 부하가 커지면 쓰기 위치 토큰과 replica replay 확인을 도입하고 짧은 대기 후 primary fallback을 둡니다. lag와 fallback 비율, primary 여유 용량을 감시하겠습니다.

primary 읽기는 단순하고 최신 경로가 명확하지만 읽기 확장 효과가 줄어듭니다. 토큰 대기는 replica를 활용하지만 라우터·snapshot·failover 처리가 복잡해집니다. remote_apply 대기는 특정 동기 standby의 가시성을 강화할 수 있지만 commit 지연과 가용성 비용이 큽니다.

약한 답변·오해: ‘replica 하나에 세션을 고정하면 최신입니다.’ 같은 서버를 계속 읽어도 그 서버가 쓰기를 아직 적용하지 않았다면 값은 낡습니다. lag가 0처럼 표시돼도 지표의 측정 시점과 특정 쓰기의 반영 여부는 별도로 확인합니다.

연습·즉시 피드백

쓰기 토큰은 1500, 선택 replica 재생 위치는 1470입니다. 대기 예산 100ms가 지났고 primary 읽기는 허용됩니다. 404와 primary fallback 중 무엇을 고르겠습니까?

풀이 확인

해당 계약에서는 primary fallback을 고릅니다. 404는 replica가 뒤처진 것을 주문이 없다는 사실로 오해하게 만듭니다. 무제한 대기는 API deadline을 깨뜨립니다. fallback을 결정했어도 primary 과부하 위험이 있으므로 동시성 제한과 fallback 비율 경보가 필요합니다.

Follow-up·자기 점검

replica가 토큰을 넘었는데 여전히 낡은 값을 읽는다면? 이전 snapshot, 앱/CDN 캐시, 다른 shard·tenant 라우팅을 확인합니다. 로그 재생만으로 전체 경로 최신성이 증명되지 않습니다.

primary 장애 때는? 토큰이 새 primary의 이력에 포함됐는지 검증하고, 보장 불가능하면 명시적 재조회·대기 정책을 적용합니다. 성공했던 쓰기가 비동기 failover로 유실될 가능성도 RPO와 함께 설명합니다.
