무중단 스키마 변경 — Expand·Migrate·Contract

호환 가능한 단계와 데이터 backfill·제거의 안전 조건을 정의한다

핵심 판단

DB 변경은 롤백 버튼만으로 되돌아가지 않는다. 구·신 버전이 같은 스키마를 함께 쓰는 시간대를 설계해야 한다.

Expand-Contract는 새 구조를 먼저 추가해 구·신 코드가 함께 동작하게 하고, 데이터를 옮기고, 사용이 끝난 뒤 오래된 구조를 제거하는 방식이다. 애플리케이션과 DB를 한 순간에 함께 바꿀 수 없다는 전제가 핵심이다.

검토 순서

  1. 호환성 표: 구버전/신버전 앱이 각 스키마에서 읽고 쓸 수 있는 조합을 적는다.
  2. Expand: 새 nullable 컬럼과 인덱스를 안전한 방식으로 추가하고 lock 대기 시간을 감시한다.
  3. Dual write: 전환기 동안 구·신 표현을 함께 기록하되, 실패 원자성과 재시도 동작을 정한다.
  4. Backfill: 작은 keyset batch로 재개 가능하게 복사하고, replica lag와 DB 부하에 따라 속도를 제한한다.
  5. 검증·전환: 불일치 샘플, row count, shadow read를 비교한 뒤 읽기 경로를 전환한다.
  6. Contract: 구버전 인스턴스와 롤백 가능 기간이 사라진 것을 확인한 후 제약·구 컬럼을 제거한다.

선택 비교

선택얻는 점비용·위험
동기 dual-write두 필드가 즉시 같이 갱신된다.한쪽 실패 시 부분 성공 위험이 있어 트랜잭션 또는 보상 설계가 필요하다.
비동기 backfill부하를 조절하고 중단·재개하기 쉽다.전환 전까지 데이터 지연과 불일치 검증을 운영해야 한다.
단일 큰 UPDATE구현이 짧고 완료 시점이 명확하다.긴 lock, WAL 폭증, replica lag와 rollback 비용을 만들 수 있다.

주의할 함정

오해: 배포는 롤백하면 되고 DB 변경도 이전 상태로 쉽게 돌릴 수 있다.

실제 경계: 새 형식으로 쓰인 데이터는 구 코드가 해석하지 못할 수 있다. Contract는 롤백 창이 닫힌 뒤에 수행하며, 데이터 변환의 역방향 가능성을 따로 평가해야 한다.

면접에서 꺼낼 사례

처음부터 NOT NULL과 새 외래키를 한 번에 걸기보다 nullable 추가 → 배치 backfill → 누락 검증 → 새 코드 사용 → 구 코드 제거 → 제약 강화 순으로 쪼갠다.

확인 질문: 배치 backfill 중 primary 부하는 괜찮지만 replica lag가 90초로 늘었습니다. 어떤 조치와 재개 기준을 정할까요?

근거와 복습
