백엔드 신뢰성 — deadline, 재시도, 차단과 부하 제어

timeout, retry, circuit breaker를 각각 켜는 것만으로 안정성이 생기지 않는다. 남은 요청 예산과 재시도 부하를 함께 설계한다.

오늘의 학습 결과: 요청 deadline과 멱등성 기준으로 재시도·차단 정책을 제시한다

면접 질문

결제 조회 서비스의 downstream p99가 900ms로 뛰고 재시도가 요청량을 두 배로 만들었습니다. 무엇을 바꾸겠습니까?

실무 상황: API의 전체 SLO는 1.2초다. gateway 300ms, DB와 외부 결제 조회가 병렬 호출되며 client timeout은 각 hop마다 독립적으로 1초로 설정돼 있다.

왜 묻는가: hop마다 timeout을 더하는 실수를 피하고, deadline 전파·재시도 안전성·load shedding을 일관되게 설명하는지 본다.

전제 개념

timeout은 오래 기다리지 않게 하고, retry는 일시 실패를 다시 시도하며, circuit breaker는 실패 중인 의존성 호출을 잠시 줄인다. rate limit은 들어오는 작업량을 용량에 맞춘다.

사용자 요청에 남은 시간이 200ms인데 downstream에 1초 timeout을 주면 이미 끝난 요청이 서버 자원을 계속 쓴다. retry를 여러 계층에서 동시에 하면 호출 수가 곱셈처럼 늘 수 있다.

답변 사고 순서

  1. 예산 계산: 전체 deadline을 gateway·내부 처리·의존성별로 나누고 deadline을 context에 전파한다.
  2. 오류 분류: connect 실패, 429, timeout, validation/영구 오류의 재시도 가능성을 구분한다.
  3. 멱등성 확인: 쓰기 요청은 idempotency key나 deduplication 없이 자동 재시도하지 않는다.
  4. 부하 완화: bounded retry + exponential backoff/jitter, breaker, concurrency limit을 조합한다.
  5. 운영 검증: retry rate, queue age, in-flight, dependency error와 사용자 성공률을 함께 관찰한다.

케이스 풀이와 답변 예시

전체 1.2초 중 gateway가 300ms를 소비한다면 의존성 경로에는 남은 시간을 고려한 deadline만 줘야 한다. 외부 read를 재시도하더라도 재시도 횟수는 한 계층에서 소유하고 지수 backoff와 jitter를 적용한다.

먼저 gateway를 포함한 end-to-end deadline을 한 번 정의하고 downstream 호출에 남은 시간을 전달하겠습니다. retry는 timeout·일시적 5xx처럼 복구 가능한 read에 한정하고 최대 1회 또는 명확한 예산으로 제한하겠습니다. 쓰기 요청은 idempotency가 확인되기 전 재시도하지 않습니다. breaker와 동시 요청 상한으로 새 호출을 줄이고, retry rate와 queue age가 임계치를 넘으면 비핵심 기능부터 shed하겠습니다.

답변에서 드러나는 점: 회복 패턴을 독립적으로 늘어놓지 않고 공통 deadline과 부하 예산으로 결합한다.

Trade-off

선택얻는 점비용·위험
Retry짧은 transient 오류의 성공률을 올린다.장애 시 추가 부하와 tail latency, 중복 쓰기 위험을 만든다.
Circuit breaker실패 의존성에 대한 대기와 연쇄 장애를 줄인다.임계치가 부정확하면 일시 오류에도 정상 복구 요청을 차단한다.
Rate/concurrency limit서비스 용량을 보호하고 과부하를 조기에 거부한다.적절한 tenant·우선순위별 quota와 429 처리 계약이 필요하다.

흔한 오해

GET이니까 timeout 뒤에 언제나 안전하게 재시도해도 된다.

HTTP method뿐 아니라 실제 API 부작용, 서버가 요청을 처리했는지, 인증·청구 동작을 확인해야 한다. 클라이언트가 응답을 못 받았다는 사실은 서버 미실행을 뜻하지 않는다.

직접 풀어보기

gateway, service A, service B가 각각 2회 retry를 설정했습니다. 한 사용자 요청이 B에 몇 번 도달할 수 있는지 최악 호출 수를 계산하고 정책을 다시 배치해 보세요.

예시 풀이와 피드백 보기

계층별 재시도가 곱해져 B 호출이 최대 3×3 등으로 증가할 수 있다(각 retry count가 추가 시도 수인지 확인). 재시도 소유자를 한 계층으로 제한하고 상위 deadline을 전파한다.
