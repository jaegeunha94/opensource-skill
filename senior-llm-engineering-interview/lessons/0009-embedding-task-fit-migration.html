Embedding과 검색 판단 — 도메인 평가와 교체 비용

임베딩을 지식 저장이나 권한 판단으로 과장하지 않고 task-fit으로 선택한다.

레슨 목록 · 이전 Day 8 · 빠른 참고

면접 질문과 실무 상황

한국어 사내 규정 검색에서 최신 고득점 embedding 모델로 바꾸자는 제안이 있습니다. 품질은 좋아질까요? 주문 번호 조회도 embedding으로 처리하겠습니까?

Day 8의 입력 modality 판단에 이어 오늘은 “생성 전에 무엇을 어떻게 찾을지”를 모델 선택 문제로 다룹니다. RAG의 상세 chunk/ANN 튜닝은 별도 트랙에 두고 선택·평가·교체 비용에 집중합니다.

전제 개념

embedding은 입력을 숫자 벡터로 바꾸어 의미적으로 가까운 표현을 찾는 데 쓰입니다. 유사도는 질문에 대한 사실의 참 여부·현재성·접근 권한의 확률이 아닙니다. “환불 가능”과 “환불 불가”처럼 같은 주제의 반대 문장도 가까울 수 있습니다.

주문 번호는 정확한 키 조회가 맞고, 표현이 다른 정책 질문은 semantic 검색이 도움될 수 있습니다. 제품 품번·희귀 용어는 lexical 검색과 비교합니다. 비공개·최신 지식에는 검색이 필요할 수 있지만 단순 문장 형식 변환마다 RAG가 필수인 것은 아닙니다.

답변 사고 순서

  1. 정확 ID·단어 일치·의미 질의·생성만 필요한 작업을 나눈다.
  2. 도메인·언어·긴 입력·부정/예외 조건의 gold query와 hard negative를 만든다.
  3. 모델의 query/document prompt·normalization·dimension·지원 길이를 확인한다.
  4. 같은 평가셋에서 기존 모델과 후보를 비교하고 retrieval 오류가 최종 답에 주는 영향을 확인한다.
  5. 재임베딩·저장·index·추론·운영 비용과 데이터 전송 정책을 계산한다.
  6. 새 vector 공간의 index를 따로 만들고 shadow/canary 후 교체한다. 같은 dimension이라는 이유로 섞지 않는다.

구체적 평가와 비용 예시

가상 후보 A는 한국어 Recall@10 0.82, 질의 지연 20ms; B는 0.88, 65ms입니다. 예외 조건 질문은 A 0.78, B 0.70입니다. 평균만 보면 B가 좋아도 핵심 정책군에는 회귀가 있습니다. 최종 답의 조건 정확성까지 확인해야 합니다.

벡터 1천만 개, 768차원 float32의 순수 벡터 payload는 10,000,000 × 768 × 4 = 30,720,000,000 bytes, 약 30.72GB입니다. 이는 decimal GB이며 index·metadata·복제·캐시는 별도입니다. 차원 두 배면 이 payload는 두 배지만 품질도 두 배가 되는 것은 아닙니다.

Sentence Transformers 현재 문서는 asymmetric 검색에서 query와 document의 역할을 구분합니다. 설치 버전·모델 prompt·backend 변경도 결과를 바꿀 수 있어 “모델 이름이 같으니 같은 벡터”라고 보장하지 않습니다. 최신 release를 확인하고 artifact·설정 hash와 평가 결과를 함께 보존합니다.

답변 예시와 trade-off

주문 번호는 키 조회로, 규정의 의미 질의는 embedding/lexical 검색 비교로 나누겠습니다. 한국어·예외·도메인 용어의 자체 gold셋에서 후보를 평가하고 query/document 설정을 고정하겠습니다. B는 평균 recall이 높아도 예외군이 악화되어 바로 교체하지 않겠습니다. 재임베딩과 이중 index 비용을 계산하고 별도 공간에서 검증한 뒤 canary로 이동하겠습니다.

약한 답 “리더보드 1위 모델을 쓰면 됩니다”는 domain·언어·입력 규칙·migration을 생략합니다.

  • 큰 모델/차원은 표현력을 늘릴 수 있지만 저장·추론·재색인 비용이 큽니다. 작은 모델은 싸고 빠르지만 도메인 분별력을 확인해야 합니다.
  • managed API는 운영을 줄이지만 데이터 전송·비용·변경 정책에 의존합니다. self-host는 통제력이 크지만 GPU/CPU·배치·업그레이드 책임이 있습니다.
  • 모든 corpus를 재임베딩하면 새 공간이 일관되지만 비용이 큽니다. 점진 이전은 비용을 나누나 공간별 검색과 통합을 설계해야 합니다.

흔한 오해

같은 차원의 서로 다른 모델 벡터는 일반적으로 호환되지 않습니다. cosine 0.9도 권한·최신성·정답 보장이 아닙니다. embedding 모델 교체로 원문에 없는 지식을 만들 수는 없습니다.

연습과 피드백

모델 A와 B가 둘 다 768차원입니다. B로 질의를 임베딩하고 A의 문서를 그대로 검색했습니다. 오류가 나지 않으므로 migration 성공인가요?

해설 보기

형식만 맞고 의미 공간은 맞지 않을 수 있습니다. B 문서와 B query의 검증된 조합을 별도 index에서 평가해야 합니다. API 성공률과 retrieval correctness를 분리한 답이 좋습니다. 호환을 명시적으로 학습/보장한 모델 조합이라면 그 근거와 도메인 검증이 필요합니다.

Follow-up과 자기 점검

차원 축소는 언제 하나? 해당 모델이 지원하는 축소/표현 방식을 확인하고 품질·비용을 다시 측정합니다. 임의로 앞 256개를 자르는 것이 언제나 안전하지 않습니다.

embedding 없이 LLM에 전체 문서를 주면? 작은 corpus에는 단순한 대안일 수 있습니다. 최신성·권한·입력 비용·길이별 품질과 비교합니다.
