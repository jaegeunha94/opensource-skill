DR 리허설 — 복구 검증 자동화와 사용자 전환 조건

복원 작업 성공과 서비스 복구 성공을 구분하고 RTO·RPO를 실제 증거로 확인한다.

레슨 목록 · 이전 Day 11 · 빠른 참고

면접 질문과 실무 상황

Day 11에서 RTO 30분·RPO 5분의 DR 전략을 정했습니다. 백업 복원 API는 성공했지만 앱이 복원 DB에 연결하지 못합니다. “복구 성공”으로 보고해도 될까요? 무엇을 자동 검증하겠습니까?

면접관은 리소스 상태 대신 사용자 기능·데이터 정합성·전환과 정리까지 보는지 평가합니다.

전제 개념

RTO는 허용하는 복구 시간, RPO는 허용하는 데이터 손실 구간입니다. 이번 사례에서는 장애 시작부터 고객이 정상 주문할 때까지를 RTO로 정의합니다. 복원 job 실행 시간만 재면 탐지·판단·연결 설정·검증·트래픽 전환을 놓칩니다.

복원은 데이터나 자원을 다시 만드는 작업입니다. 검증은 그 결과가 요구를 만족하는지 확인하는 작업입니다. 데이터 행 수가 같아도 잘못된 결제 상태나 연결되지 않는 KMS·IAM·네트워크 때문에 서비스를 쓸 수 없을 수 있습니다.

답변 사고 순서

  1. 복구 성공의 사용자 기능과 시계 시작·종료, RPO 기준 데이터를 합의한다.
  2. 격리된 대상과 권한·KMS·네트워크·복원 metadata를 준비한다. 고객 메일/결제 side effect는 차단한다.
  3. 지원 자원은 AWS Backup restore testing 계획으로 정기 복원한다. 자원별 지원과 복원 조건은 현재 문서로 확인한다.
  4. 완료 이벤트 뒤 제한된 검증을 실행해 데이터·앱·의존성을 확인하고 검증 결과를 별도로 기록한다.
  5. 격리 시험의 성공과 실제 장애 전환 가능성을 구분한다. 전환·원래 리전 쓰기 차단·failback은 별도 리허설한다.
  6. 검증 종료 뒤 자원·잔여 연결·비용·감사 기록의 정리를 확인한다.

구체적 검증 계획

가상 리허설 시간: 장애 판단 3분, 복원 12분, 앱 구성 4분, 검증 6분, 전환 3분이면 총 28분입니다. 동시에 진행 가능한 단계가 없다면 30분 목표의 여유는 2분뿐입니다. 단계별 분포도 보고 최악의 지연을 시험해야 합니다.

검증 층구체적 확인합격 기준의 예
데이터 시점장애 전 외부에 기록한 마지막 주문 marker와 복원 결과 비교복구된 마지막 연속 확정 시점이 목표 RPO 안
정합성주문·결제 참조와 상태 전이, 중복 ID고아 참조·중복 확정 없음
앱 경로격리 앱의 로그인·주문 조회·가상 주문 작성요구 권한·연결·암복호화 통과, 외부 결제 없음
전환쓰기 주체 하나 유지, 연결 재생성, 트래픽 이동split brain 없음, 정의된 RTO 안 기능 복구

행 수 비교는 일부 손상 탐지에 유용하지만 RPO를 증명하지 않습니다. marker는 DB 안에만 두면 DB와 함께 잃을 수 있으므로 독립된 증거와 연결합니다. 합성 주문은 검증 대상에서만 실행합니다.

답변 예시와 trade-off

복원 job 성공은 첫 단계로 보고, 격리 앱의 연결·권한·KMS·주문 불변조건을 별도 검증하겠습니다. 외부 marker로 복구 시점을 확인하고 고객 부작용은 차단하겠습니다. 자동 시험 결과와 단계별 시간을 기록하되 실제 전환·쓰기 차단까지 시험하지 않았다면 RTO 전체를 증명했다고 보고하지 않겠습니다.

약한 답 “백업 성공률 100%를 확인합니다”는 복원 가능성과 서비스 사용 가능성을 구분하지 못합니다.

  • 매번 전체 데이터 검증은 확신을 높이지만 시간·비용이 큽니다. 핵심 불변조건·샘플·주기적 전체 검증을 나눕니다.
  • 격리 시험은 고객 영향이 낮지만 운영 DNS·실제 부하 차이가 있습니다. 정기 전환 훈련을 보완적으로 둡니다.
  • 복구 목표를 짧게 잡으면 standby 비용이 커집니다. 사용자 영향과 비용을 함께 합의합니다.

흔한 오해와 현재 자료 확인

백업의 성공·Multi-AZ·다중 리전 중 어느 하나도 DR의 모든 실패를 자동 해결하지 않습니다. AWS Backup의 검증은 선택적으로 붙이는 단계이며, 지원 자원과 cleanup 조건을 확인해야 합니다. 기존 미션의 “Well-Architected 5개 기둥” 표현과 달리 현재 공식 프레임워크는 지속가능성을 포함한 6개 기둥입니다. 오늘은 신뢰성에 집중하되 보안·비용·운영 우수성·성능·지속가능성의 영향도 함께 검토합니다.

연습과 피드백

복원 20분, 검증 8분으로 보고했는데 장애 판단 5분과 DNS/연결 전환 4분이 빠졌습니다. RTO 30분을 통과했나요? RPO 5분은 이 숫자로 판단할 수 있나요?

계산과 해설

순차 실행 가정에서는 총 37분이라 실패입니다. RPO는 시간 소요가 아니라 복원된 데이터의 시점·확정 이력으로 판단하므로 알 수 없습니다. 복원만 빠르게 만드는 대신 단계별 지연과 병렬 가능성을 찾아 재시험해야 합니다.

Follow-up과 자기 점검

복원된 DB는 정상인데 검증 Lambda가 실패했다면? 실제 실패인지 검증 권한·네트워크 실패인지 분리합니다. 검증 실패를 자동 합격으로 처리하지 않습니다.

자동 정리가 누락되면? 테스트 자원의 소유·만료·비용을 추적하고 서비스별 정리 조건과 예외를 확인합니다. 운영 자원과 시험 자원을 구분하는 metadata가 필요합니다.

근거 자료와 복습

  • AWS Backup — Restore testing validation — 완료 이벤트 이후 사용자 정의 검증과 결과 처리
  • AWS — Well-Architected Framework — 현재 6개 기둥의 아키텍처 검토 관점
