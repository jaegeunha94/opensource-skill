재해 복구 전략 — RTO·RPO에서 복구 리허설까지

다중 리전이라는 말만으로 재해 복구가 되지 않는다. 복구 시점과 허용 손실, 실제 전환 시간을 합의하고 훈련해야 한다.

오늘의 학습 결과: 워크로드별 DR 전략과 복구 검증 기준을 고른다

면접 질문

주문 서비스에 RTO 30분, RPO 5분 목표가 주어졌습니다. 어떤 DR 구성을 고르고 어떻게 증명하겠습니까?

실무 상황: 주 리전 전체 장애를 가정한다. 주문 DB에는 cross-region replica가 있고, 앱 인프라는 IaC로 생성 가능하지만 DR 리전은 평소 compute를 실행하지 않는다.

왜 묻는가: backup 존재와 복구 가능성을 구분하고 DNS·데이터 승격·용량·보안 설정을 끝까지 검증하는지 평가한다.

전제 개념

RTO는 서비스가 복구되기까지 허용되는 시간이고, RPO는 복구 시점에서 허용되는 데이터 손실 범위다. 선택한 DR 방식의 비용과 운영 복잡도는 목표가 낮아질수록 대체로 커진다.

복제는 삭제·암호화 손상도 따라 복사할 수 있어 백업을 대체하지 않는다. 같은 계정·권한·키에 의존하면 리전 장애가 아닌 계정 장애에서 복구하지 못할 수 있다.

답변 사고 순서

  1. 업무 목표: 서비스별 RTO/RPO, 법적 데이터 위치, 최대 허용 중단과 거래 손실을 확인한다.
  2. 의존성 지도: DB, 객체, DNS, secrets/KMS, IAM, quota, 외부 결제와 데이터 경로를 추적한다.
  3. 전략 선택: backup/restore, pilot light, warm standby, active-active를 복구 목표와 비용에 맞춘다.
  4. 복구 절차: 데이터 승격, 앱 scale-up, 트래픽 이동, write fencing과 중복 처리 순서를 문서화한다.
  5. 연습·증거: 격리된 game day에서 실제 RTO/RPO, 성공률, runbook 지연을 기록하고 개선한다.

케이스 풀이와 답변 예시

RPO 5분은 replica lag가 항상 5분 이하라는 말만으로 충족되지 않는다. 장애 감지부터 마지막 확정 트랜잭션 시점까지 실제 손실을 측정하고, split-brain을 막는 writer fencing이 필요하다.

우선 주문 승인과 정산 각각의 RTO/RPO를 업무 담당자와 합의하겠습니다. 30분 복구를 위해 축소 용량으로 동작 가능한 warm standby를 후보로 두고, replica lag와 failover promotion, secrets·quota·DNS까지 DR runbook에 넣겠습니다. 별도 백업은 논리 손상 복구에 유지하고, 분기별 장애 연습에서 실제 복구시간과 누락 주문을 검증해 목표와 비교하겠습니다.

답변에서 드러나는 점: 목표를 서비스 영향으로 해석하고 복구 가능한 경로를 실행 증거로 뒷받침한다.

Trade-off

선택얻는 점비용·위험
Backup & Restore비용과 구성 복잡도가 낮다.복원·인프라 생성 시간이 길어 RTO가 커질 수 있다.
Pilot Light / Warm Standby핵심 기반과 데이터가 준비되어 복구가 빠르다.상시 비용과 scale-up·전환 자동화 검증이 필요하다.
Multi-site Active/Active지역 장애에도 트래픽을 계속 처리할 수 있다.쓰기 일관성, 중복 방지, 운영과 비용이 가장 복잡하다.

흔한 오해

cross-region replication이 있으면 데이터 백업과 복구 테스트는 불필요하다.

복제는 삭제나 손상 데이터를 복제할 수 있고, replica 승격 이후 앱·권한·트래픽이 정상 동작하는지 별도 검증해야 한다.

예시 풀이와 피드백 보기

최신 확정 시점을 확인할 수 있는 로그·복제 상태를 확보하고, 복구 가능한 후보별 예상 손실과 업무 영향을 책임자에게 제시한다. writer fencing과 split-brain 방지를 먼저 확인하고 승인된 복구 지점을 선택한다.
