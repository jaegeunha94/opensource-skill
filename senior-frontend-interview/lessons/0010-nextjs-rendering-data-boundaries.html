Next.js 서버 아키텍처 — 공개 상품과 개인 장바구니의 경계

Day 8 상태·Day 9 렌더 비용을 데이터 공개 범위와 서버/브라우저 실행 시점에 연결한다.

면접 질문·실무 상황

상품 페이지는 검색에 잘 노출하고 빠르게 보여야 하지만 장바구니는 사용자별 최신 상태여야 합니다. 전체 SSR이 정답입니까?

가상 쇼핑 화면은 상품 설명이 하루 몇 번, 재고가 초 단위, 장바구니가 요청마다 바뀝니다. 면접관은 SSR/SSG/ISR 이름보다 신선도·공개 범위·상호작용 경계를 판단하는지 봅니다.

전제 개념

서버 렌더링은 HTML을 서버에서 만드는 일이고, 그 실행 시점은 빌드 때·재생성 때·요청 때로 달라질 수 있습니다. 정적 생성은 재사용을 통해 요청 비용을 줄이고, 재검증은 허용한 신선도 안에서 갱신합니다. 요청 시 렌더는 사용자 입력을 직접 반영하지만 서버 작업과 TTFB 비용이 듭니다.

Server Component는 서버의 데이터 접근과 렌더 책임, Client Component는 state·event·브라우저 기능의 실행 경계입니다. Client Component도 첫 진입에서 HTML을 미리 만들 수 있습니다. 초기 HTML·RSC payload·클라이언트 JS의 역할은 Next.js 공식 문서에서 확인하세요. ‘서버 컴포넌트=매 요청 SSR’이나 ‘Client=HTML이 없음’은 잘못된 동일시입니다.

답변 사고 순서와 경계 표

  1. 상품 설명·재고·장바구니의 공개 여부와 허용 stale 시간을 합의합니다.
  2. 각 데이터를 언제 읽고 어디에 캐시하는지 명시합니다.
  3. 큰 페이지 전체를 use client로 바꾸는 대신 상호작용이 필요한 장바구니 버튼·수량 입력만 경계를 좁힙니다.
  4. 개인화 응답을 공유 캐시에 넣지 않고 서버에서 인가합니다. 브라우저 props에 전달하는 데이터도 공개된다고 가정합니다.
  5. 느린 데이터는 독립 로딩 경계로 분리하고 TTFB·LCP·상호작용 지연·정확성을 함께 측정합니다.
데이터가상 정책검증
상품 설명공개 데이터 재사용·명시적 재검증변경 후 전파 시간
재고짧은 허용 지연 또는 요청 조회주문 확정 때 서버 재검증
장바구니사용자별 조회·인가서로 다른 사용자 간 누출 없음

가격·재고가 화면에서 최신처럼 보여도 최종 주문 트랜잭션 검증을 대체하지 않습니다.

현재 문서에 맞춘 캐시 판단

2026-10-07 확인한 공식 문서는 현재 캐싱 안내와 Cache Components가 없는 이전 모델을 구분합니다. 프로젝트 버전·cacheComponents 설정을 확인하고 그 모델에 맞는 명시적 캐시·재검증 계약을 사용합니다. 오래된 ‘모든 fetch는 기본 캐시’나 ‘네 계층만 외우면 끝’이라는 가정으로 설계하지 않습니다.

답변 예시·Trade-off·오해

공개 상품 내용은 재사용하고 개인 장바구니는 사용자별 조회·인가 경계로 분리하겠습니다. 상호작용만 Client Component로 두고 초기 데이터는 서버에서 필요한 최소 정보만 전달합니다. 캐시 모델은 실제 버전과 설정에 맞춰 명시하며, 주문 확정 시 재고·가격을 다시 검증합니다.

약한 답변: ‘SSR이면 빠르고 안전하니 모두 SSR입니다.’ 서버 의존성 지연·캐시 누출·JS 비용은 남습니다. 정적 재사용은 빠르고 저렴하지만 신선도 관리가 필요합니다. 요청 조회는 최신 입력을 반영하지만 장애·지연의 영향을 받습니다. 클라이언트 조회는 사용자 상호작용에 유연하지만 초기 waterfall과 로딩 상태를 추가합니다.

연습·피드백

상품 설명 변경은 5분 이내 반영 허용, 장바구니는 사용자별 즉시 반영입니다. 두 데이터를 같은 URL 캐시 키로 5분 공유해도 됩니까?

풀이 확인

개인 장바구니까지 공유하면 다른 사용자의 상태를 노출할 수 있으므로 경계를 나눕니다. 상품 데이터만 공개 캐시하고 장바구니는 인가된 사용자 경로로 조회합니다. ‘짧은 TTL이면 누출이 안전’은 시간과 접근 권한을 혼동합니다. ‘모두 캐시 금지’는 공개 상품 재사용 이득을 불필요하게 잃습니다.

Follow-up·자기 점검

Server Component에서 비밀을 props로 넘기면? 전달 값은 클라이언트 payload로 노출될 수 있습니다. 서버 전용 연산을 유지하고 필요한 공개 결과만 직렬화합니다.

초기 화면은 빨라도 버튼이 늦게 반응하면? Client 경계와 JS 크기·hydration·long task를 보며 TTFB만 성과로 보고하지 않습니다.
