React 렌더링 모델 — 상태 소유권과 비용 경계

React의 재렌더링은 곧 DOM 전체를 다시 그린다는 뜻이 아니다. 변경이 전파되는 경로와 실제 commit 비용을 구분한다.

오늘의 학습 결과: 렌더 비용을 측정하고 상태·컴포넌트 경계를 재설계한다

면접 질문

대시보드에서 한 필터를 바꾸면 페이지 전체가 느려집니다. 어떤 순서로 원인을 찾고 개선하겠습니까?

실무 상황: 화면에는 차트 8개, 테이블 2개, 검색창이 있다. 필터 상태가 최상단에 있고 매 keypress마다 전체 트리의 계산이 다시 실행된다.

왜 묻는가: memo를 무조건 추가하지 않고 렌더 원인·state ownership·측정된 commit 비용을 따지는지 본다.

전제 개념

React render 단계는 다음 UI를 계산하고 commit 단계는 필요한 변경을 DOM에 반영한다. 컴포넌트 함수가 다시 호출돼도 실제 DOM 변경이 없을 수 있다.

memoization은 props가 안정적일 때 계산을 줄일 수 있지만 비교 비용과 복잡성도 있다. 우선 상태를 실제로 쓰는 가장 가까운 경계에 두고 Profiler로 병목을 확인한다.

답변 사고 순서

  1. 사용자 증상: 입력 지연, 긴 task, layout/paint, 네트워크 중 무엇이 느린지 재현한다.
  2. Profiler 측정: commit duration, render 횟수, 어떤 자식이 업데이트됐는지 확인한다.
  3. 상태 범위: 필터 입력 상태와 결과 데이터 상태를 분리하고 불필요한 상위 전파를 줄인다.
  4. 비용 최적화: 비싼 계산은 memoize 여부를 측정하고, 긴 목록은 virtualization을 검토한다.
  5. 회귀 확인: 저사양 기기와 큰 데이터에서 interaction latency·INP·메모리 변화를 비교한다.

케이스 풀이와 답변 예시

검색어 입력 중 매번 모든 차트를 새 query로 다시 호출한다면 debounce와 request cancellation이 렌더 memoization보다 큰 이득일 수 있다. 렌더와 데이터 요청 병목을 먼저 나눈다.

먼저 React Profiler와 browser performance trace로 입력 지연이 render 계산인지 네트워크·layout인지 나누겠습니다. 입력 draft는 검색 컴포넌트 가까이에 두고 submit/debounce 시 확정된 query만 결과 영역에 전달하겠습니다. chart props가 실제로 안정화될 수 있는지 확인한 뒤 memo를 적용하고, 긴 행은 virtualization을 검토하겠습니다. 저사양 기기에서 INP와 데이터 최신성, 키보드 접근성을 같이 비교하겠습니다.

답변에서 드러나는 점: React 개념을 실제 사용자 입력 지연·network request·browser rendering 단계에 연결한다.

Trade-off

선택얻는 점비용·위험
상태를 상위에 모음여러 컴포넌트가 한 source of truth를 공유한다.빈번한 업데이트가 넓은 트리와 데이터 요청을 흔들 수 있다.
상태를 아래로 분할업데이트 범위와 책임을 좁힐 수 있다.상태 동기화와 공유 로직이 복잡해질 수 있다.
memo/useMemo비싼 재계산이나 자식 렌더를 줄일 수 있다.비교 비용·stale dependency·메모리 사용으로 성능이 나빠질 수 있다.

흔한 오해

컴포넌트가 렌더되면 DOM 전체가 다시 만들어진다.

render 계산과 DOM commit은 다르다. 실제 성능 문제는 Profiler와 browser trace로 계산·commit·layout·paint를 구분해야 한다.

직접 풀어보기

React.memo를 적용했는데 차트가 계속 렌더됩니다. 확인해야 할 값과 개선 선택을 세 가지 말해 보세요.

예시 풀이와 피드백 보기

props identity(매 render 새 object/function), context 변경, local state 변경, 부모 render와 실제 commit 비용을 확인한다. props 생성 위치를 안정화하거나 state/context 경계를 좁히되 측정 후 적용한다.
