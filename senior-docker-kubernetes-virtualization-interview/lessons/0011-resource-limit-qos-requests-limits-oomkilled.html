Kubernetes 자원 경계 — requests·limits·OOMKilled 진단

requests와 limits는 같은 뜻의 두 숫자가 아니다. scheduler가 보장하는 기준과 runtime 상한을 구분한다.

오늘의 학습 결과: 메모리 OOM과 CPU throttling을 증거 기반으로 분리한다

면접 질문

메모리 limit을 올린 뒤 OOMKilled는 줄었지만 node 압박 eviction이 늘었습니다. 어떻게 진단하고 설정을 조정합니까?

실무 상황: 여러 서비스가 한 node pool에 배치된다. request는 실제 peak보다 낮고 limit은 높게 잡혀 있어 scheduler가 과밀 배치할 수 있다.

왜 묻는가: Pod 내부 limit만 조정하지 않고 node capacity·QoS·실제 working set·throttling을 설명하는지 본다.

전제 개념

request는 scheduler가 배치할 때 고려하는 자원 요청량이고 limit은 실행 중 container에 적용되는 상한이다. CPU limit 초과는 주로 throttling으로 나타나고, 메모리 limit 초과는 OOM kill로 이어질 수 있다.

Guaranteed QoS라고 모든 장애에서 보호되는 것은 아니다. node 압박과 priority, request 초과 여부, 시스템 프로세스 여유 공간을 같이 봐야 한다.

답변 사고 순서

  1. 사건 구분: container OOMKilled, Pod eviction, node OOM을 event·termination reason으로 나눈다.
  2. 실사용량: working set, RSS, heap/native memory, peak와 성장률을 수집한다.
  3. CPU 제한: CFS throttling 시간·quota와 latency를 비교해 limit이 과도한지 판단한다.
  4. 배치 밀도: node allocatable 대비 requests와 실제 사용량, DaemonSet·system reserve를 계산한다.
  5. 정책 조정: request를 관측 기반으로 잡고 limit·QoS·priority와 HPA/VPA를 함께 검증한다.

케이스 풀이와 답변 예시

limit만 키우면 container OOM은 완화될 수 있지만 node 전체의 메모리 약속이 과도해질 수 있다. Pod request가 scheduler의 판단과 실제 사용 분포를 얼마나 반영하는지부터 다시 본다.

먼저 종료 이유가 container memory cgroup OOM인지 node-pressure eviction인지 확인하겠습니다. Pod별 peak working set과 node allocatable, requests 대비 실제 사용 분포를 비교하고, CPU는 throttled seconds와 p99를 함께 봅니다. 메모리 request를 현실적으로 조정하고 시스템 reserve와 priority를 포함해 밀도를 낮추되, 제한 상향은 한 node pool canary에서 OOM·eviction·비용이 함께 개선되는지 확인한 뒤 확대하겠습니다.

답변에서 드러나는 점: Kubernetes 개념을 실제 Linux cgroup 지표와 node capacity로 연결한다.

Trade-off

선택얻는 점비용·위험
낮은 request·높은 limit평균 사용량 기준 bin packing 효율이 높다.burst 시 node 압박과 eviction 경쟁, noisy neighbor가 커진다.
request=limit자원 배치가 예측 가능하고 CPU·메모리 경계를 명확히 한다.유휴 자원을 활용하기 어렵고 메모리 burst에 취약해질 수 있다.
CPU limit 제거 또는 완화CPU burst를 허용해 throttling을 줄일 수 있다.공유 node에서 다른 workload의 CPU 기회를 침해할 수 있다.

흔한 오해

Guaranteed QoS Pod는 OOM이나 종료를 당하지 않는다.

QoS는 node resource pressure 상황에서의 우선순위와 관련될 뿐 절대 생존 보장이 아니다. 자기 limit 초과나 node 장애는 여전히 발생한다.

직접 풀어보기

Pod는 memory limit 2Gi, working set 1.6Gi인데 OOMKilled가 발생했습니다. 점검할 수집 지표와 우선 질문을 말해 보세요.
