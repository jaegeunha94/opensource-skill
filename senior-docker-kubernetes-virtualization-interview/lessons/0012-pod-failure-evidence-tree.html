운영 Troubleshooting — Pending과 CrashLoop의 증거 분리

Pod 상태를 원인으로 읽지 않고 배치·시작·실행·연결 단계로 진단한다.

레슨 목록 · 이전 Day 11 · 빠른 참고

면접 질문과 실무 상황

배포 뒤 Pod 두 개는 Pending, 두 개는 CrashLoopBackOff입니다. 재시작하고 메모리 limit을 올리면 해결됩니까?

Day 11의 자원 경계는 진단 후보 중 하나입니다. 오늘은 증거를 지우기 전에 어디에서 실패했는지 나눕니다. 면접관은 읽기 명령의 목적과 관측 뒤 다음 행동을 연결하는지 봅니다.

전제 개념

Pending은 준비가 끝나지 않은 Pod phase입니다. 스케줄링 전뿐 아니라 이미지 준비 같은 시작 단계도 확인해야 합니다. CrashLoopBackOff는 반복 종료하는 컨테이너에 재시작 간격을 늘리는 상태 표시입니다. 원인이 “backoff”가 아니라 앱 종료·설정·probe·OOM 등일 수 있습니다.

Pod phase, container state/reason, Event는 서로 다른 층의 증거입니다. Pod가 Running이어도 readiness 실패로 트래픽을 못 받을 수 있습니다. Exit code 137만으로 메모리 부족을 확정하지 말고 OOMKilled·노드 이벤트와 함께 봅니다.

답변 사고 순서와 명령

# 가상 이름. 대상 namespace와 container를 명시합니다.
kubectl get pods -n demo -o wide
kubectl describe pod api-a -n demo
kubectl logs api-b -n demo -c app --previous
kubectl logs api-b -n demo -c app
kubectl get events -n demo --sort-by=.metadata.creationTimestamp
kubectl describe node node-a
  1. 새 배포와 기존 버전의 영향·가용 replica를 비교한다. 고객 영향이 크면 안전한 이전 버전 전환을 병행한다.
  2. Pod에 nodeName이 있는지, Scheduled 조건과 Event를 본다. 미배치면 requests·taint·affinity·PVC를 점검한다.
  3. 배치됐지만 시작 못 하면 image pull·volume mount·init container·설정 참조를 확인한다.
  4. 반복 종료면 last termination reason과 --previous 로그를 현재 로그와 구분한다.
  5. probe 종료·앱 종료·OOM을 분리하고 같은 시점의 node 압박과 변경 diff를 연결한다.
  6. 실행은 정상인데 접속이 안 되면 readiness·EndpointSlice·Service selector·DNS/네트워크 경로를 따로 추적한다.

Event는 보존 기간이 제한되고 로그도 회전할 수 있습니다. 중요한 시간과 결과를 즉시 기록합니다. 명령 출력에 비밀이나 사용자 데이터가 있으면 공유 범위를 정합니다.

케이스 풀이와 답변 예시

가상 증거: Pending Event는 Insufficient cpu, CrashLoop의 이전 로그는 “필수 DATABASE_HOST 없음”, OOMKilled는 없습니다. 첫 그룹은 자원·배치 문제이고 두 번째는 설정 회귀입니다. limit 상향은 두 번째를 고치지 못합니다.

먼저 replica별로 Scheduled 여부와 종료 이유를 분리하겠습니다. 미배치 Pod는 allocatable 대비 requests와 배치 제약을 보고, CrashLoop는 이전 컨테이너 로그·설정 diff·probe 실패를 확인하겠습니다. 이 사례에서는 잘못된 설정을 호환 버전으로 되돌리고, CPU 부족은 필요한 requests를 낮추기 전에 실제 사용과 노드 용량을 검증하겠습니다. 조치 뒤 Ready 수와 사용자 오류가 함께 회복되는지 확인하겠습니다.

약한 답 “Pod를 삭제하면 새로 뜹니다”는 같은 선언 상태로 같은 실패를 반복하고 관측 증거를 잃을 수 있습니다.

Trade-off와 흔한 오해

  • 즉시 rollback은 영향 완화가 빠르지만 데이터·스키마 호환성이 필요합니다. 원인 조사와 완화를 함께 진행합니다.
  • requests 감소는 배치를 돕지만 자원 부족을 숨길 수 있습니다. 용량 증설은 비용·기동 시간이 듭니다.
  • liveness 완화는 부팅 여유를 주지만 실제 stuck 감지가 늦어집니다. 느린 시작은 startup probe와 시작 시간 분포로 다룹니다.

CrashLoop는 네트워크 문제의 이름이 아니며 Running은 서비스 정상의 증명이 아닙니다. 재시작 횟수가 줄어도 readiness와 사용자 경로를 확인해야 합니다.

연습과 피드백

Pod에는 nodeName이 있고 Waiting reason은 ImagePullBackOff입니다. 노드는 CPU 여유가 없다는 다른 경고도 있습니다. 첫 진단은 scheduler 용량입니까, 이미지 경로입니까?

해설 보기

이미 배치된 이 컨테이너의 직접 실패는 image pull입니다. Event의 이미지 이름·tag 존재·registry 인증·DNS/연결·rate limit을 확인합니다. 노드 CPU 경고는 별도 위험으로 기록하지만 미배치 문제라고 결론내리지 않습니다. 관측된 단계로 우선순위를 정한 답이 좋습니다.

Follow-up과 자기 점검

이전 로그가 없다면? 보존된 중앙 로그·termination message·Event·배포 diff를 사용하고 모르는 부분은 가설로 남깁니다.

한 노드에서만 실패한다면? node condition·runtime·디스크·CNI/CSI·registry 경로를 비교하고, 무작정 전체 배포를 재시작하지 않습니다.
