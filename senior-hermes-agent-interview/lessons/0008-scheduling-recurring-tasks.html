에이전트 예약 작업 — timezone·중복 실행·복구

매일 오전 9시 작업은 서버 시간대, DST, 재시도에 따라 한 번 이상 실행될 수 있다. 스케줄 표현보다 실행 계약이 중요하다.

오늘의 학습 결과: 예약 의미와 idempotent 실행·누락 보정 정책을 정한다

면접 질문

매일 오전 9시에 고객 리포트를 생성하고 Slack으로 보내는 agent를 중복 없이 운영하려면 어떻게 설계하겠습니까?

실무 상황: 작업은 여러 worker가 처리하고, 외부 API가 timeout될 수 있다. 일부 사용자는 다른 시간대에 있고 DST 전환일에는 현지 시간이 반복되거나 건너뛴다.

왜 묻는가: cron 문법만 말하지 않고 timezone·lease·at-least-once·외부 side effect를 설계하는지 본다.

전제 개념

scheduler는 실행 시각에 작업을 enqueue하는 역할이고 worker는 실제 작업을 수행한다. queue 전달은 보통 재시도와 함께 at-least-once가 되므로 한 작업이 두 번 실행될 수 있다.

“한 번만 실행”은 분산 환경에서 실행 시도 횟수만으로 보장하기 어렵다. 결과 저장과 외부 알림의 중복을 idempotency key 또는 transactional outbox로 통제한다.

답변 사고 순서

  1. 시간 의미: IANA timezone, local wall clock, DST gap/fold에서 실행할 규칙을 명시한다.
  2. 작업 식별: schedule id + 논리 실행 날짜로 stable run key를 만든다.
  3. 경쟁 제어: lease/lock과 만료·heartbeat를 두되 중복 실행도 견딜 idempotent handler를 만든다.
  4. side effect: 결과 저장과 Slack 발송을 outbox 또는 provider idempotency로 조정한다.
  5. 누락·재시도: catch-up, 최대 retry, poison task, 늦은 실행 알림과 수동 재실행 절차를 정의한다.

케이스 풀이와 답변 예시

UTC에 24시간 간격으로만 예약하면 사용자의 “현지 오전 9시” 요구가 DST 뒤 달라진다. 다음 실행 시각은 timezone 데이터와 정책을 기준으로 계산하고, 같은 logical date에 두 run이 생성돼도 결과가 중복 발송되지 않게 한다.

사용자별 IANA timezone과 DST 전환 정책을 먼저 명시하겠습니다. 스케줄러가 논리 날짜별 run key를 만들고 worker는 lease를 획득해도 결과 테이블의 unique key와 outbox로 중복을 막겠습니다. Slack timeout은 전달 여부가 불명확하므로 provider idempotency나 발송 상태 조회를 사용하고, 누락 작업을 자동 catch-up할 범위와 늦은 리포트 안내를 운영 정책에 넣겠습니다.

답변에서 드러나는 점: 예약·실행·전달을 분리하고 재시도 중 중복 부작용을 막는다.

Trade-off

선택얻는 점비용·위험
UTC 고정 주기계산이 단순하고 서버 간 일관성이 높다.현지 wall-clock 일정은 DST 뒤 한 시간 어긋날 수 있다.
현지 timezone 기반사용자 기대와 맞는 달력 일정이 된다.DST gap/fold와 timezone 규칙 변경을 처리해야 한다.
분산 lock만 사용동시 worker의 일반적인 중복 실행을 줄인다.lease 만료·네트워크 분할 뒤 이전 worker가 계속 side effect를 낼 수 있다.

흔한 오해

distributed lock을 쓰면 예약 작업은 정확히 한 번만 실행된다.

lock은 특정 시점의 소유권 경쟁만 줄인다. lease expiry 뒤 늦은 worker가 살아날 수 있으므로 fencing/idempotency와 결과 unique constraint가 필요하다.

직접 풀어보기

worker가 Slack 발송 후 DB에 성공 기록을 남기기 전에 죽었습니다. 다음 retry가 중복 발송하지 않게 할 방법을 설명하세요.

예시 풀이와 피드백 보기

발송 요청의 stable idempotency key/provider dedupe를 쓰거나 outbox 상태와 전달 receipt를 reconciliation한다. 외부 제공자가 dedupe를 지원하지 않으면 정확히 한 번을 약속하지 말고 중복 가능성과 보정 절차를 설계한다.
