Replay와 평가 루프 — 실행 성공과 업무 정답의 분리

원본 trajectory를 보존하고, 부작용을 통제한 재실행에서 업무 결과와 행동을 함께 평가한다.

레슨 목록 · 이전 Day 8 · 빠른 참고

면접 질문과 실무 상황

“Hermes가 처리한 고객 문의 200건을 새 모델로 다시 평가하고 싶습니다. batch와 trajectory를 어떻게 쓰겠습니까?” 지난 Day의 스케줄 중복 실행 방지처럼, 평가에서도 실제 환불이나 메시지가 다시 실행되면 문제가 생긴다. 여기서 Hermes는 모델 이름이 아니라 도구를 실행하는 agent 시스템이다.

가상 문의 하나의 목표는 ‘배송 지연을 확인해 승인된 안내 초안을 만들기’다. 실행이 오류 없이 끝났어도 다른 주문을 조회했거나 고객에게 바로 발송했다면 실패다. batch의 완료 상태와 업무 품질 점수를 분리해야 한다.

전제 개념: 기록 읽기와 다시 실행하기

Trajectory는 대화와 도구 호출·응답 등의 실행 기록이다. 원본을 읽어 행동을 채점하는 것은 새 실행이 아니다. 기록된 도구 응답을 fixture로 제공하는 offline replay와, 격리된 테스트 시스템에서 실제 도구를 다시 호출하는 rerun도 다르다. production 도구로 batch를 실행하면 실제 부작용이 발생할 수 있다.

현재 Hermes batch 기능은 입력을 여러 agent 작업으로 처리하는 기능이다. 임의의 과거 환경을 자동 복원해 같은 결과를 보장하는 장치는 아니다. 시간, 모델 설정, 도구 버전, 메모리·Skills와 외부 데이터가 달라지면 결과가 달라질 수 있다.

평가 가능한 한 건의 계약

고정하거나 기록할 것이 사례의 조건
입력·기대 결과가상 주문 ORD-DEMO-41, 지연 안내 초안, 발송 없음
도구 fixture주문 조회는 지연 상태를 반환; send_message는 테스트 차단기가 호출 시도만 기록
실행 환경모델·샘플링·도구 스키마·시각·Skill 및 메모리 snapshot 식별자
판정올바른 주문 조회, 지연 근거 포함, 개인정보 누출 없음, 발송 시도 없음
예산조회 최대 2회, 재시도 이유 기록, 시간·토큰·비용 별도 집계

send_message를 단순히 항상 성공으로 mock하면 금지된 행동을 숨길 수 있다. 호출 시도 자체를 실패 조건으로 남겨야 한다. 기록된 응답은 그 시점의 세계를 나타내며, 현재 주문 상태를 확인했다는 뜻은 아니다.

답변 사고 순서와 답변 예시

  1. 업무 기대 결과와 금지 행동을 먼저 작성한다.
  2. 원본 기록을 보존하고 개인정보·비밀 값은 평가용 사본에서 제거한다.
  3. 도구 fixture와 실제 격리 실행 중 어떤 방식을 쓸지 정한다.
  4. 환경 식별자를 고정하고 이전·신규 모델을 같은 사례로 비교한다.
  5. 최종 산출물과 전체 행동을 함께 채점한다. 실행 실패는 별도 분류한다.
  6. 회귀 사례를 검토한 뒤에만 운영 적용이나 학습 데이터 활용을 판단한다.
“우선 읽기 기반 채점으로 잘못된 주문 조회와 발송 시도를 분류하겠습니다. 새 모델 비교는 외부 부작용이 없는 fixture 환경에서 하고, 최종 안내의 정확도와 금지 도구 호출을 별도로 평가하겠습니다. batch completed 비율을 품질로 대신하지 않겠습니다.”

면접관의 평가 기준: 기록 보존과 부작용 통제, 업무 정답의 분모를 다룰 수 있는지 본다. 약한 답변: “과거 요청을 production에서 batch로 다시 돌리고 완료율이 높으면 학습에 쓰겠습니다.” 금지된 재실행과 개인정보를 고려하지 않고 실행 완료를 정답으로 취급한다.

흔한 오해: 기록 형식과 압축의 한계

공식 trajectory 문서의 ShareGPT 호환 내보내기는 conversations의 from/value 같은 정규화된 표현과 실행 메타데이터를 제공한다. 저장 시 시스템 프롬프트를 구성하는 등 원래 런타임의 모든 바이트를 그대로 보존한 기록이라고 가정할 수 없다. 비교에 필요한 환경 정보는 별도로 남긴다.

긴 기록의 요약·압축본은 검색이나 데이터셋 준비에 유용하지만, 누락된 도구 인자나 실패 경로가 평가를 바꿀 수 있다. 원본 → 버전 있는 파생 데이터 → 평가 결과의 연결을 유지한다. 기록이 존재한다는 이유로 정답 학습 데이터라고 간주하지 않고, 업무 기준과 민감 정보 검토를 통과한 사례만 후보로 삼는다.

Trade-off, 연습과 피드백

Fixture replay는 저렴하고 반복 가능하지만 실제 네트워크·동시성 문제를 재현하지 못한다. 격리된 rerun은 운영 경로에 가깝지만 테스트 데이터와 도구 관리 비용이 크다. 확률적 결과는 단 한 번의 승패보다 반복 분포와 같은 사례의 회귀를 본다.

신규 모델이 100건 모두 completed, 정답 92건, 발송 금지 위반 3건이다. 이전 모델은 completed 97건, 정답 90건, 금지 위반 0건이다. 신규 모델을 곧바로 적용할 수 있는가?

판단 기준 확인

같은 전체 100건을 분모로 정답률과 실패 유형을 보고, 완료 97건만으로 정답률을 높여 보이면 안 된다. 금지 위반 3건은 이 업무의 배포 조건을 충족하지 못한다. 원인을 분류하고 수정한 뒤 해당 사례와 주변 사례를 다시 평가한다. 품질 상승이 안전 계약 위반을 자동 상쇄하지 않는다.

Follow-up과 자기 점검

실시간 도구가 필요하면? 격리된 계정과 합성 데이터를 쓰고 호출 가능한 경로를 제한한다. production 입력을 그대로 재사용하지 않는다.

요약본만 남았다면? 기록으로 확인 가능한 항목과 복원 불가능한 항목을 나눠 신뢰 수준을 낮춘다. 없는 도구 결과를 만들어 채우지 않는다.
