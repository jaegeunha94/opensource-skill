PSI와 cgroup v2 — 자원 압박을 사용자 지연에 연결하기

사용률이 100%가 아니어도 작업은 자원 대기 때문에 멈출 수 있다. PSI는 그 대기 시간이 workload에 준 영향을 보여준다.

오늘의 학습 결과: pressure stall과 cgroup 통계를 함께 읽어 완화 우선순위를 정한다

면접 질문

API p99가 상승하지만 host CPU 사용률은 65%입니다. PSI와 cgroup을 이용해 무엇을 확인하겠습니까?

실무 상황: 한 host에서 latency-critical API와 배치 작업이 함께 돈다. 배치 시작 뒤 API p99가 오르고 system-wide CPU·memory·I/O pressure가 모두 노출된다.

왜 묻는가: load average나 사용률 하나로 병목을 단정하지 않고 pressure scope·cgroup limit·workload 영향을 나눠 보는지 본다.

전제 개념

PSI의 `some`은 일부 task가 자원을 기다린 시간 비율, `full`은 해당 자원이 없어 workload의 모든 non-idle task가 멈춘 시간 비율을 나타낸다. system-wide 경로와 cgroup별 pressure는 서로 다른 범위를 본다.

PSI 값만으로 어느 프로세스가 원인인지 직접 알 수는 없다. cgroup별 `cpu.stat`, `memory.events`, `io.stat`, PSI와 요청 trace를 같은 시간축으로 비교해야 한다.

답변 사고 순서

  1. 범위 확인: `/proc/pressure/{cpu,memory,io}`와 각 cgroup의 `*.pressure`를 비교한다.
  2. 증상 시간 정렬: PSI avg10/total 변화와 API p99, 배치 시작·cgroup 이동 시각을 맞춘다.
  3. 자원별 원인: CPU throttled periods, memory reclaim/OOM events, I/O bytes·latency를 확인한다.
  4. 완화 선택: 배치 concurrency·CPU weight·memory high/max·I/O priority·load shedding을 비교한다.
  5. 회귀 감시: 압박 감소뿐 아니라 배치 완료시간과 API SLO, OOM/eviction을 함께 관찰한다.

케이스 풀이와 답변 예시

host CPU가 65%여도 CPU PSI가 높으면 runnable task가 코어를 두고 경합할 수 있다. 반대로 CPU PSI가 낮고 memory PSI·reclaim이 오른다면 CPU를 늘리는 조치는 빗나갈 수 있다.

먼저 system PSI와 API/배치 cgroup의 pressure를 나란히 비교해 host 전체 문제인지 noisy neighbor인지 확인하겠습니다. `cpu.stat`의 throttling, `memory.events`의 high/max, `io.stat`과 storage latency를 요청 p99와 정렬하겠습니다. API cgroup에 보장된 자원과 적절한 memory protection을 주고 배치 concurrency를 낮추는 실험을 하되, 배치 SLA와 OOM 위험도 함께 보겠습니다.

답변에서 드러나는 점: PSI를 원인 식별의 끝이 아니라 scope와 cgroup 통계를 연결하는 신호로 쓴다.

Trade-off

선택얻는 점비용·위험
cgroup 자원 격리 강화latency-critical 작업의 간섭을 제한한다.유휴 자원 활용률과 batch throughput이 낮아질 수 있다.
압박 기반 load shedding장애 임계점 전에 저우선 작업을 줄인다.pressure threshold와 hysteresis를 잘못 정하면 oscillation이 생긴다.
host 용량 증설resource contention 여유를 늘린다.원인이 잘못된 limit·leak·I/O 병목이면 비용만 늘어난다.

흔한 오해

CPU 사용률이 남아 있으면 CPU는 병목이 아니다.

cgroup quota로 throttling되거나 짧은 구간 경합으로 p99가 악화될 수 있다. utilization과 PSI, quota 통계를 함께 봐야 한다.

직접 풀어보기

system memory PSI는 낮지만 특정 API cgroup `memory.pressure`와 `memory.events high`가 증가했습니다. 어떤 현상을 의심하나요?

예시 풀이와 피드백 보기

host 전체 메모리 부족이 아니라 해당 cgroup의 memory.high로 인한 reclaim/throttling을 의심한다. process working set, limit/working set, reclaim latency를 확인하고 workload별 설정을 조정한다.
