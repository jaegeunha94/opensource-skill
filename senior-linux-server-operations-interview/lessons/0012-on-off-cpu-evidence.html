eBPF/perf — 실행 시간과 대기 시간을 분리한 병목 진단

CPU 프로파일의 빈칸을 대기 스택으로 보완하고, 근거가 있는 제한된 진단을 설계한다.

면접 질문과 실무 상황

API p99가 80ms에서 600ms로 늘었지만 호스트 CPU는 35%입니다. perf에서 JSON 직렬화가 가장 넓게 보입니다. 직렬화를 최적화하겠습니까?

Day 11에서 PSI와 cgroup으로 압박 범위를 찾았습니다. 오늘은 그 안에서 요청이 무엇을 실행하거나 기다리는지를 좁힙니다. 면접관은 멋진 도구 이름보다 관측 대상·분모·검증 순서를 봅니다.

전제 개념부터

on-CPU는 스레드가 CPU에서 실행 중인 시간입니다. off-CPU는 실행하지 않는 시간으로, 잠든 시간뿐 아니라 실행 가능하지만 차례를 기다리는 시간도 포함할 수 있습니다. 요청의 경과 시간에는 둘 다 들어가지만 CPU 샘플은 실행 중인 순간만 잡습니다.

스택은 현재 함수에 도달한 호출 경로입니다. CPU flame graph의 너비는 수집된 샘플 비중이지 한 요청의 지연 비중이 아닙니다. eBPF는 커널 사건에 연결한 프로그램으로 집계를 만들 수 있지만, 낮은 오버헤드가 자동 보장되지는 않습니다. off-CPU 집계에는 정상적인 유휴 스레드도 크게 잡힐 수 있습니다.

답변 사고 순서

  1. 변경 시점·영향 엔드포인트·요청량을 맞추고, process/thread와 컨테이너 제한을 확인합니다.
  2. CPU 포화·run queue·I/O·락·외부 호출 중 가설을 세웁니다. 평균 CPU만으로 실행 대기를 배제하지 않습니다.
  3. 대상 PID, 10초 같은 수집 한도, 샘플 빈도, 파일 보관 범위를 정합니다. 프로파일 권한은 운영 정책 안에서 확보합니다.
  4. on-CPU 스택과 off-CPU/스케줄링 증거를 요청 trace의 시간대에 연결합니다. 시스템 전체의 유휴 스택을 요청 원인으로 착각하지 않습니다.
  5. 작은 변경 후 동일 부하에서 p99·처리량·CPU·대기 시간과 오류를 비교합니다.

명령과 증거 해석

아래 PID 12345는 가상 값입니다. 실제 승인된 프로세스로 바꿔야 하며 권한·커널·perf 버전과 스택 심볼 상태를 먼저 확인합니다.

perf stat -p 12345 -e task-clock,context-switches,page-faults -- sleep 10
perf record -F 49 -g -p 12345 -- sleep 10
perf report --stdio

stat는 지정 구간의 활동량을, record는 샘플 스택을 얻기 위한 선택입니다. -g만으로 모든 언어·빌드의 스택이 정확해지는 것은 아닙니다. 프레임 포인터/디버그 심볼·런타임 프로파일러 필요성을 확인합니다. 권한 오류를 없애려고 전역 보호 설정을 무작정 낮추지 않습니다.

가상 관측판단다음 증거
CPU 샘플 60% 직렬화CPU 소비의 후보; 요청 600ms의 60%라는 뜻은 아님해당 경로의 실제 CPU 시간, 요청 trace
느린 요청 구간에 futex 대기 420ms락/조건 대기 후보; futex 자체가 결함은 아님애플리케이션 락 보유자, 대기 큐, 호출 경로
DB span 450ms, 소켓 대기외부 의존성 후보DB 큐·쿼리 지연·연결 풀 대기

답변 예시와 trade-off

직렬화는 CPU 비용 후보지만 요청 지연의 주원인이라고 단정하지 않겠습니다. 느린 요청과 같은 구간의 대상 스레드를 짧게 수집해 실행·스케줄러 대기·블로킹을 분리하겠습니다. futex 경로가 두드러지면 락 보유자와 경합을 확인하고, 락 범위를 줄인 뒤 같은 부하에서 대기와 p99가 함께 줄었는지 검증하겠습니다.

약한 답변 “가장 넓은 함수부터 바꾸겠습니다”는 샘플 분모와 대기 시간을 놓칩니다.

  • 샘플 빈도를 높이면 짧은 실행 구간을 더 잘 포착할 수 있지만 CPU·파일 비용이 늘어납니다. 초기에는 낮은 빈도·짧은 구간을 택합니다.
  • 커널/eBPF 진단은 런타임 밖의 대기를 연결하기 좋지만 권한·호환성·수집 손실을 다뤄야 합니다. 앱 프로파일러는 의미가 풍부하나 커널 대기를 덜 볼 수 있습니다.
  • 호스트 전체 수집은 주변 경합을 찾지만 잡음·정보 노출 범위가 큽니다. 대상 프로세스부터 시작하고 증거에 따라 확장합니다.

흔한 오해

“off-CPU 시간이 크면 서버가 나쁘다”는 오해입니다. 작업이 없는 worker의 기다림은 정상입니다. 영향을 받은 요청 경로와 대기의 이유를 맞춰야 합니다. eBPF 집계의 누락·심볼 실패도 기록해야 결론의 범위를 설명할 수 있습니다.

연습과 피드백

worker 100개 중 90개는 유휴 상태입니다. 전체 off-CPU graph에서 epoll 대기가 95%이고, 느린 요청 10개는 같은 mutex에서 기다립니다. 무엇을 개선하고 무엇을 추가 측정할까요?

판단 후 해설 열기

유휴 epoll을 제거할 이유는 없습니다. 느린 요청의 mutex 대기·보유 시간·소유 경로를 수집하고 요청 수와 정규화해서 봅니다. mutex를 없애기 전에 보호하는 불변조건을 확인합니다. worker 수 증가는 경합을 더 키울 수도 있습니다. 이 답을 썼다면 “유휴 시간과 고객 지연의 분모를 분리했다”는 점이 강점입니다.

Follow-up과 자기 점검

CPU가 낮은데 runnable 대기가 길다면? 특정 CPU/스레드 쏠림, affinity, cgroup throttling과 호스트 경합을 확인합니다. 평균 사용률은 국소 포화를 숨깁니다.

프로파일 변경 후 개선이 없다면? 수집 구간·요청 혼합·캐시 상태를 맞추고 가설을 철회할 근거를 찾습니다. 프로파일 도구를 추가하는 것만으로 원인이 확정되지는 않습니다.
