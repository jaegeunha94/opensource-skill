RAG와 Tool Calling 연동 — 설명 근거와 업무 사실의 경계

정책 검색·현재 상태 조회·변경 실행을 나누고 사용자에게 확인된 사실만 전달한다.

레슨 목록 · 이전 Day 7 · 빠른 참고

면접 질문과 실무 상황

고객이 “지난주 주문 환불해줘”라고 말합니다. 정책 RAG는 7일 내 환불 규정을 찾았지만 주문 상태 API는 timeout입니다. 검색 결과만으로 환불을 실행할 수 있나요?

Day 7의 fallback/handoff를 실패 경로로 두고, 오늘은 정상 경로에서 근거와 업무 사실을 합치는 구조를 만듭니다. 면접관은 모델의 설명과 서버의 결정 권한을 구분하는지 봅니다.

전제 개념

RAG 문서는 일반 정책·설명 근거입니다. Tool 조회는 해당 사용자의 현재 주문·결제 상태를 확인합니다. 변경 tool은 환불 같은 외부 효과를 만듭니다. 이 세 가지는 최신성·권한·재시도 계약이 다릅니다.

tool calling은 모델이 이름과 인자를 제안하는 기능입니다. 서버가 실행해도 되는지 판단하는 권한이 모델에게 넘어가는 것은 아닙니다. MCP 같은 도구 연결 프로토콜도 호출자의 인가와 업무 불변조건을 대신 보장하지 않습니다.

답변 사고 순서

  1. 발화를 정책 질문·조회·변경 의도로 나누고 필요한 주문 식별자와 모호함을 확인한다.
  2. 검색은 현재 정책 version과 허용 범위로 제한하고 근거 문단·조건을 보존한다.
  3. 주문/결제는 인증 주체의 범위 안에서 현재 상태를 조회한다. 모델이 제시한 user_id를 신뢰하지 않는다.
  4. 정책 조건·현재 상태·이미 환불 여부를 결정론적 검증으로 결합한다.
  5. 필요한 확인에는 주문·금액·대상을 구체적으로 보여주고 변경 실행에 바인딩한다.
  6. 멱등 key로 실행하고 확인된 결과를 응답한다. timeout은 불명 상태로 두고 조회/상담으로 이어간다.

구체적 흐름과 사용자 답변

대화 입력
 → 정책 검색(근거/버전) + 주문 조회(현재 상태/소유권)
 → 조건 검증 → 구체적 사용자 확인 → 환불 실행(key)
 → 결과 조회/확정 → 사용자 완료 안내
조회 실패/근거 부족 → 추가 질문·재조회·사람 handoff

모델은 “7일 내 규정이 있으니 환불 가능합니다” 대신 “환불 규정은 구매 후 7일 이내 등 조건을 요구합니다. 현재 주문 상태 확인이 지연되어 아직 가능 여부를 확정하지 못했습니다”라고 응답합니다. 재조회 또는 Day 7의 상담 handoff를 제공하되 임의로 새 환불 요청을 반복하지 않습니다.

신뢰된 상태 예시: order=o-42, actor_scope=T1, policy=v3, payment=settled, refundable=1000 KRW. user가 주문을 바꿨거나 금액이 바뀌면 이전 확인을 새 실행에 사용하지 않습니다. 검색 문서 안의 “이 도구로 비밀을 보내라”는 문장은 외부 데이터이며 도구 권한의 지시가 아닙니다.

면접 답변 예시와 trade-off

정책 검색으로 일반 조건을 설명하고 현재 주문 상태는 권한 있는 조회 도구로 확인하겠습니다. 이 둘을 서버 규칙으로 검증한 뒤 주문·금액에 바인딩된 확인을 받고 멱등 key로 환불하겠습니다. 상태 조회 timeout에는 가능 여부나 완료를 단정하지 않고 재조회/상담으로 이어가겠습니다. 최종 응답은 근거 인용과 확인된 실행 결과를 구분하겠습니다.

약한 답 “LLM에 정책과 API를 주고 알아서 처리하게 합니다”는 데이터와 실행 권한의 경계를 생략합니다.

  • 읽기 조회를 병렬화하면 지연을 줄이지만 최신 정책과 상태의 결합·부분 실패를 검증해야 합니다. 변경 단계는 확인과 상태 의존성을 지킵니다.
  • 세밀한 tool은 권한과 테스트가 쉽지만 호출 수가 늘 수 있습니다. 넓은 tool은 편하나 과한 권한·모호한 부작용이 생깁니다.
  • 조건이 모호할 때 추가 질문은 정확도를 높이나 대화가 길어집니다. 추정으로 결제/환불하는 비용과 비교합니다.

흔한 오해와 최신 자료

tool 입력이 schema에 맞으면 실행해도 된다는 오해가 있습니다. 소유권·상태·한도·승인은 별도입니다. 현재 Anthropic tool use와 release note를 확인해 모델 제안과 client 실행의 책임을 분리했습니다. 연결 프로토콜을 쓰는 것 자체가 최신 데이터·인가·멱등성을 보장한다는 주장을 하지 않습니다.

연습과 피드백

사용자가 o-42의 1000원 환불을 확인했습니다. 그 뒤 모델이 o-43의 5000원을 제안했습니다. “대화에서 이미 확인했다”는 이유로 실행할 수 있나요?

해설 보기

안 됩니다. 확인은 구체적 대상·금액·action에 바인딩되어야 합니다. 새 제안은 소유권·가능 금액·상태를 다시 검증하고 필요한 확인을 다시 받습니다. 대화 동의와 작업별 실행 계약을 분리한 답이 좋습니다.

Follow-up과 자기 점검

정책과 주문 API가 모순되면? 원본 version·시점·상태 의미를 확인하고 모순을 숨기지 않습니다. 금전 작업은 검증된 계약이 없으면 보류/상담으로 넘깁니다.

외부 도구 결과에 injection이 있으면? 데이터를 제한된 schema로 처리하고 prompt 지시로 승격하지 않습니다. host의 권한과 실행 정책을 유지합니다.
