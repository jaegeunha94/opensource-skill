챗봇 fallback과 사람 상담 handoff

fallback은 같은 답을 다시 생성하는 동작이 아니다. 불확실성을 사용자에게 알리고 위험도에 맞는 다음 행동을 제공한다.

오늘의 학습 결과: 답변 불확실성·업무 위험·상담원 맥락을 기준으로 경로를 나눈다

면접 질문

환불 규정에 대한 근거가 검색되지 않았을 때 챗봇은 어떻게 응답하고 상담원에게 넘겨야 합니까?

실무 상황: RAG 챗봇은 주문 상태와 환불 규정을 답한다. 일부 주문은 결제사 상태가 늦게 동기화되고, 잘못된 환불 안내는 금전 피해를 만든다.

왜 묻는가: 모델 confidence 숫자 하나에 의존하지 않고 근거 존재, 작업 위험, 상담원 대기 시간을 설계하는지 본다.

전제 개념

fallback은 확신 부족, 검색 결과 부재, 도구 실패 같은 조건에서 기본 답변 경로를 바꾸는 정책이다. handoff는 사용자 대화와 필요한 상태를 사람 상담 흐름으로 넘긴다.

모델이 말한 confidence는 보정된 확률이라고 보장되지 않는다. 정답을 모를 수 있는 질문과 tool failure를 분리하고, 금액 변경 같은 고위험 작업은 자동 실행하지 않는다.

답변 사고 순서

  1. 실패 유형: 검색 무근거·낮은 답변 품질·외부 API timeout·정책상 제한을 구분한다.
  2. 위험도 평가: 환불·계정 보안·개인정보 변경은 보수적 임계값과 확인 절차를 둔다.
  3. 사용자 안내: 모르는 이유와 가능한 다음 행동을 짧고 명확하게 안내하고 무한 반복을 막는다.
  4. handoff payload: 동의한 대화 요약, 주문 식별자, 시도한 도구, 근거와 실패 유형을 상담원에게 전달한다.
  5. 완료 계약: 상담원 수락 여부, 대기 시간, 재접속, 중복 티켓과 privacy retention을 관리한다.

케이스 풀이와 답변 예시

환불 관련 답변 근거가 없고 결제 API도 timeout이면, 규정을 추측해 안내하지 않는다. 상태가 불명확하다고 밝히고 조회 재시도 또는 상담원 handoff를 제공한다.

환불 가능 여부를 확인할 공식 주문 상태와 정책 근거가 없으므로 승인 여부를 단정하지 않겠습니다. 사용자 동의를 받은 뒤 주문 번호와 이미 확인한 단계, 결제 조회 timeout을 상담원에게 넘기고, 접수 번호와 예상 대기 시간을 알려드리겠습니다. 결제 상태가 불명확한 동안 자동 환불 재요청은 막고, 상담원에게 같은 idempotency key로 상태 확인을 안내하겠습니다.

답변에서 드러나는 점: 근거·위험·중복 실행을 다루며 handoff가 사용자에게 실제로 완료되었는지 확인한다.

Trade-off

선택얻는 점비용·위험
낮은 handoff 임계값위험한 오답을 줄인다.상담원 queue 부하와 사용자의 대기 시간이 늘어난다.
높은 자동화 임계값상담원 비용을 낮추고 즉시 응답 비율을 높인다.잘못된 답변과 금전/보안 피해 가능성이 증가한다.
전체 transcript 전달상담원이 맥락을 빠르게 이해한다.불필요한 개인정보 노출과 보존 범위가 커진다.

흔한 오해

fallback 문구를 준비해 두면 hallucination 문제가 해결된다.

답변이 위험한 액션을 유발할 수 있는지와 근거 품질을 평가해야 한다. 고위험 도구는 권한·확인·idempotency 경계가 별도로 필요하다.
