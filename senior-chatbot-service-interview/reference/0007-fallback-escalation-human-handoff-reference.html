챗봇 fallback과 사람 상담 handoff

답변 불확실성·업무 위험·상담원 맥락을 기준으로 경로를 나눈다

핵심 판단

fallback은 같은 답을 다시 생성하는 동작이 아니다. 불확실성을 사용자에게 알리고 위험도에 맞는 다음 행동을 제공한다.

fallback은 확신 부족, 검색 결과 부재, 도구 실패 같은 조건에서 기본 답변 경로를 바꾸는 정책이다. handoff는 사용자 대화와 필요한 상태를 사람 상담 흐름으로 넘긴다.

검토 순서

  1. 실패 유형: 검색 무근거·낮은 답변 품질·외부 API timeout·정책상 제한을 구분한다.
  2. 위험도 평가: 환불·계정 보안·개인정보 변경은 보수적 임계값과 확인 절차를 둔다.
  3. 사용자 안내: 모르는 이유와 가능한 다음 행동을 짧고 명확하게 안내하고 무한 반복을 막는다.
  4. handoff payload: 동의한 대화 요약, 주문 식별자, 시도한 도구, 근거와 실패 유형을 상담원에게 전달한다.
  5. 완료 계약: 상담원 수락 여부, 대기 시간, 재접속, 중복 티켓과 privacy retention을 관리한다.

선택 비교

선택얻는 점비용·위험
낮은 handoff 임계값위험한 오답을 줄인다.상담원 queue 부하와 사용자의 대기 시간이 늘어난다.
높은 자동화 임계값상담원 비용을 낮추고 즉시 응답 비율을 높인다.잘못된 답변과 금전/보안 피해 가능성이 증가한다.
전체 transcript 전달상담원이 맥락을 빠르게 이해한다.불필요한 개인정보 노출과 보존 범위가 커진다.

주의할 함정

오해: fallback 문구를 준비해 두면 hallucination 문제가 해결된다.

실제 경계: 답변이 위험한 액션을 유발할 수 있는지와 근거 품질을 평가해야 한다. 고위험 도구는 권한·확인·idempotency 경계가 별도로 필요하다.

면접에서 꺼낼 사례

환불 관련 답변 근거가 없고 결제 API도 timeout이면, 규정을 추측해 안내하지 않는다. 상태가 불명확하다고 밝히고 조회 재시도 또는 상담원 handoff를 제공한다.

확인 질문: 사용자가 “상담원 연결”을 두 번 눌렀고 첫 요청은 아직 대기 중입니다. 중복 티켓과 대화 상태를 어떻게 처리합니까?
