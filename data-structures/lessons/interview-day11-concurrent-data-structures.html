동시성 자료구조와 일관성 계약

스레드 안전하다는 말만으로는 자료구조의 동작을 설명할 수 없다. 어떤 연산 조합이 원자적이어야 하는지 먼저 정한다.

오늘의 학습 결과: 선형화 가능성·락 범위·경합·읽기 일관성을 요구사항에 맞춘다

면접 질문

초당 수십만 번 갱신되는 인기 키 카운터와 전체 랭킹을 어떤 자료구조로 구현하겠습니까?

실무 상황: 추천 API가 인기 항목의 빈도와 상위 100개를 동시에 갱신·조회한다. 항목 수는 수백만이고, 상위 목록은 1초 이내 최신이면 충분하다.

왜 묻는가: 알고리즘 복잡도뿐 아니라 원자성 범위, contention, 근사 허용치를 정의하는지 평가한다.

전제 개념

자료구조의 각 메서드가 안전한 것과 여러 메서드로 이루어진 업무 동작이 원자적인 것은 다르다. 예를 들어 `get` 뒤 `put`은 각 호출이 thread-safe여도 경쟁 상태가 생길 수 있다.

전체 랭킹이 매 순간 완전히 선형화되어야 하는지, 약간 늦은 스냅샷을 허용하는지부터 정한다. 강한 일관성은 lock과 동기화 비용을 늘릴 수 있다.

답변 사고 순서

  1. 계약 정의: 키별 증가의 정확성, 중복 이벤트 처리, 랭킹의 허용 지연과 동률 규칙을 정한다.
  2. 경합 찾기: 핫키 비율과 읽기/쓰기 비율을 측정해 전역 lock 병목인지 확인한다.
  3. 구성 선택: 샤딩 카운터, 원자 연산, 스킵리스트/힙, 주기적 스냅샷을 요구에 맞게 조합한다.
  4. 정합성 경계: 중복 이벤트는 event id로 막고, snapshot 생성 시점과 재시작 후 복구를 설계한다.
  5. 비용 검증: p99, lock wait, 업데이트 손실, 메모리와 재구축 시간을 부하 실험한다.

케이스 풀이와 답변 예시

카운트 정확도는 보장하되 상위 100 목록은 1초 늦어도 되는 요구라면, 카운터 쓰기 경로와 랭킹 조회 경로를 분리할 수 있다. 모든 증가마다 전역 정렬 목록을 재계산하지 않는다.

먼저 카운트가 이벤트 중복에 대해 정확해야 하는지와 랭킹의 최대 stale 시간을 합의하겠습니다. 카운터는 키 또는 shard 단위 원자 업데이트와 중복 방지 키를 사용하고, 상위 목록은 변경 스트림을 소비해 주기적으로 유지하거나 스냅샷을 게시하겠습니다. 그 사이에 누락·재처리 시 전체 재계산으로 복구할 수 있게 하고 lock wait와 랭킹 freshness를 함께 모니터링하겠습니다.

답변에서 드러나는 점: 자료구조를 하나로 고집하지 않고 강한 일관성이 필요한 연산과 근사가 가능한 읽기를 분리한다.

Trade-off

선택얻는 점비용·위험
전역 락 + 정렬 구조단순하며 업데이트와 조회 의미가 분명하다.핫키·전체 lock contention이 처리량과 tail latency를 제한한다.
샤드별 카운터 + 병합쓰기를 병렬화하고 경합을 분산한다.상위 K 병합, 재시작, 샤드 간 스냅샷 합성 로직이 필요하다.
근사 스케치대규모 스트림에서 메모리 사용을 제한할 수 있다.오차·편향이 생겨 정확한 금액·보안 판단에 쓰기 어렵다.

흔한 오해

ConcurrentHashMap을 쓰면 그 안의 비즈니스 작업도 안전하다.

개별 메서드 보장과 복합 불변식은 다르다. check-then-act, 여러 키 갱신, 중복 메시지 처리는 별도 원자성 설계가 필요하다.

직접 풀어보기

사용자별 잔액을 `if balance >= x: balance -= x` 방식으로 차감합니다. thread-safe map이어도 두 동시 요청이 둘 다 통과하는 이유와 해결 경계를 설명해 보세요.

예시 풀이와 피드백 보기

읽기와 쓰기가 하나의 원자 연산이 아니기 때문이다. 키별 compare-and-set/transaction 또는 계좌별 lock을 사용하고, DB가 영속 원장이라면 조건부 UPDATE와 affected-row 검사로 최종 불변식을 보장한다.
