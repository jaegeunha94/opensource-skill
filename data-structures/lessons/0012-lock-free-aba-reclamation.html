Lock-free 자료구조의 안전성 검증과 재시도 비용

면접 질문·실무 상황

전역 lock을 CAS 기반 stack으로 바꾸자 처리량은 올랐지만 드문 crash가 생깁니다. 어디부터 확인합니까?

가상 C++ 작업 stack은 pop된 노드를 즉시 free합니다. 면접관은 lock 제거와 안전성 보장을 혼동하지 않고, 접근 순서를 재구성하는지 봅니다. 아래는 개념 설명용 의사코드이며 안전한 구현이 아닙니다.

repeat:
    old = atomic_load(head)
    new = old.next
until CAS(head, old, new)
free(old)

전제 개념: CAS·ABA·회수

CAS는 현재 값이 내가 기대한 값일 때만 새 값으로 바꾸는 원자 연산입니다. ‘그 사이 값이 한 번도 바뀌지 않았다’는 보장은 아닙니다. 주소 A가 제거되고 다른 노드에 재사용돼 head가 다시 A가 되면 값 비교는 같아도 노드의 의미가 달라집니다. 이것이 ABA 문제입니다.

더 먼저 발생할 수 있는 문제는 T1이 old를 읽고 멈춘 사이 T2가 노드를 제거·free한 뒤 T1이 old.next를 읽는 것입니다. CAS 자체가 원자적이어도 이미 해제된 메모리 접근은 막지 못합니다. Michael의 hazard pointer 논문은 lock-free 노드의 안전한 메모리 회수를 별도 문제로 다룹니다.

lock-free는 여러 실행 주체 중 누군가의 작업이 계속 완료되는 진행 보장입니다. 특정 스레드가 반드시 제한된 단계 안에 끝나는 wait-free와 다릅니다. 한 스레드가 계속 CAS에 실패할 수 있습니다.

답변 사고 순서

  1. stack의 불변식을 적습니다. 성공한 push/pop마다 노드가 정확히 한 번 들어가거나 나와야 합니다.
  2. 성공한 CAS를 연산이 이루어진 것으로 보는 선형화 지점 후보로 삼고, 빈 stack과 경쟁 pop을 포함해 이력을 검사합니다.
  3. 노드 읽기와 회수 사이의 경쟁을 재현합니다. hazard pointer라면 보호 게시·head 재확인·접근·보호 해제의 순서와 메모리 순서 규칙이 필요합니다.
  4. 주소 재사용 ABA와 데이터 게시 가시성을 별도로 검증합니다. 단순 tagged pointer도 카운터 wraparound·원자 폭을 검토합니다.
  5. CAS 실패/성공, 스레드별 완료 수, p99, 회수 지연·retired 노드 수를 측정합니다. race 검사가 통과해도 모든 이력의 논리적 안전성을 증명한 것은 아닙니다.

답변 예시·Trade-off·오해

즉시 free 때문에 다른 스레드가 읽는 노드를 회수했는지 먼저 보겠습니다. CAS 성공 지점과 메모리 회수 프로토콜을 나눠 검증하고, 검증된 라이브러리의 hazard pointer나 epoch 방식을 비교하겠습니다. 총 처리량뿐 아니라 특정 스레드의 기아, 재시도 수와 회수 대기 메모리도 운영 기준에 넣겠습니다.

약한 답변: ‘atomic을 썼으니 crash는 allocator 문제입니다.’ 원자 포인터와 노드 수명은 다른 계약입니다. hazard pointer는 보호 중인 노드를 확인해 회수를 미루지만 게시·스캔 비용이 있습니다. epoch 회수는 묶음 처리가 효율적이지만 오래 멈춘 참여자가 회수를 지연시킬 수 있습니다. mutex는 증명과 유지보수가 단순하지만 경합·보유 스레드 정지에 따른 대기를 감수합니다.

흔한 오해: lock-free는 재시도가 없어서 항상 빠르다. 핫한 head에서 CAS 실패와 캐시 라인 이동이 늘면 mutex나 샤딩이 더 좋을 수 있습니다.

연습과 피드백

T1이 A를 읽고 정지합니다. T2가 A를 pop해 free하고 새 노드를 같은 주소 A에 push합니다. T1의 CAS가 성공했는데도 안전하지 않은 이유를 설명하세요.

풀이 확인

주소 동일성은 노드 동일성과 같지 않습니다. T1이 읽은 next는 옛 노드에 대한 값이므로 새 구조를 잘못 연결할 수 있고, next를 읽는 시점에는 use-after-free도 가능합니다. ‘CAS가 실패할 것’은 ABA를 놓칩니다. ‘메모리 barrier만 추가’는 메모리 수명 문제를 해결하지 못합니다. 노드 보호와 회수·재사용 규칙을 검증해야 합니다.

Follow-up·자기 점검

GC 언어라면 끝인가요? 회수 방식은 달라져도 논리적 ABA·복합 연산·진행 보장 문제는 남습니다. 객체 참조와 주소 기반 구현을 구분합니다.

실패 CAS가 성공보다 20배 많다면? backoff·샤딩·락 후보를 같은 부하에서 비교하고 스레드별 공정성과 tail latency를 봅니다.
