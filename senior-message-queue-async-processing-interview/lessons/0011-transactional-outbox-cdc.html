Transactional Outbox와 CDC — DB commit에서 이벤트까지

DB commit 뒤 broker publish가 실패하면 상태는 바뀌었지만 이벤트가 없다. Outbox는 두 작업을 같은 DB transaction으로 묶는다.

오늘의 학습 결과: outbox relay·CDC·consumer dedupe의 보장 범위를 설명한다

면접 질문

주문 생성 DB commit 뒤 Kafka 이벤트 발행이 실패해 알림 서비스가 주문을 놓치는 문제를 어떻게 막겠습니까?

실무 상황: 주문 API가 DB에 주문을 쓰고 Kafka에 `OrderCreated`를 발행한다. DB commit과 broker ack는 한 원자적 transaction이 아니다.

왜 묻는가: exactly-once 구호 대신 원자화 경계, 재전송, partition key, consumer idempotency를 말하는지 평가한다.

전제 개념

dual-write는 하나의 업무 변경을 DB와 broker 두 시스템에 따로 기록하는 문제다. Outbox는 주문 row와 이벤트 row를 같은 DB transaction에서 저장하고 relay/CDC가 이벤트를 전달한다.

outbox가 broker 전달을 한 번만 보장하지는 않는다. relay가 publish 성공 뒤 offset/상태를 기록하기 전에 죽으면 중복 발행될 수 있으므로 consumer는 event id를 사용해 멱등하게 처리해야 한다.

답변 사고 순서

  1. 불변식: 주문 성공 응답과 outbox event 생성이 같은 DB commit에 묶여야 한다고 정의한다.
  2. 이벤트 계약: event id, aggregate id, type, schema version, payload와 순서를 설계한다.
  3. relay 선택: polling과 CDC의 운영·lag·보존·connector 장애 특성을 비교한다.
  4. consumer 처리: event id inbox/dedupe와 DB side effect를 transaction으로 묶는다.
  5. 복구·운영: outbox backlog, connector offset, poison event, replay와 retention을 관리한다.

케이스 풀이와 답변 예시

주문 aggregate별 순서를 유지하려면 broker key를 aggregate id로 설정한다. consumer는 event id를 처리 원장에 기록하고 업무 변경과 같은 transaction으로 commit한다.

주문 row와 outbox event를 하나의 DB transaction에 넣어 주문 commit이 성공하면 발행해야 할 사실도 남기겠습니다. CDC를 쓰면 connector offset과 outbox backlog를 추적하고, 이벤트 key는 주문 id로 두어 aggregate 순서를 유지하겠습니다. publish 후 재시작으로 중복이 생길 수 있으므로 consumer는 event id를 중복 방지 테이블과 업무 변경에 원자적으로 기록하겠습니다. schema evolution과 poison event replay도 runbook에 포함하겠습니다.

답변에서 드러나는 점: 생산자 원자성, 전달 at-least-once, 소비자 멱등성을 각각 분리한다.

Trade-off

선택얻는 점비용·위험
Polling publisher구조가 단순하고 DB만으로 시작할 수 있다.poll query·locking·짧은 polling delay와 outbox cleanup 부하가 생긴다.
CDC relayDB log를 읽어 낮은 polling 부하와 빠른 전달을 얻는다.connector·slot/WAL retention·offset 운영이 추가된다.
Kafka transactionKafka 내부 read-process-write에 원자성을 제공할 수 있다.외부 DB transaction까지 일반적으로 원자화하지 않으며 설정·운영 복잡성이 있다.

흔한 오해

Outbox와 CDC를 쓰면 end-to-end exactly-once가 보장된다.

전달 경로는 재시도와 중복이 가능한 구조다. 업무 효과를 한 번만 적용하려면 event id dedupe를 consumer transaction과 결합해야 한다.

예시 풀이와 피드백 보기

외부 API idempotency key로 event id를 사용하고 상태 조회/reconciliation을 둔다. 외부 시스템이 dedupe를 제공하지 않으면 정확히 한 번을 보장할 수 없으므로 예약·보상·중복 감지 절차를 설계한다.
