면접 질문과 실무 상황

주문 workflow가 재고 예약 → 결제 승인 → 배송 요청 순서로 진행합니다. 결제 요청이 timeout됐습니다. 즉시 재고를 풀고 결제를 재시도해도 될까요?

Day 11의 outbox는 상태와 이벤트의 누락을 줄이지만 여러 서비스의 업무 전체를 하나의 트랜잭션으로 만들지 않습니다. 면접관은 그 사이의 실패 상태를 모델링하는지 봅니다.

전제 개념

Saga는 각 서비스의 로컬 트랜잭션을 이어 업무를 진행하고, 진행할 수 없으면 보상 행동으로 업무 상태를 수습하는 방식입니다. 보상은 과거를 지우는 DB rollback이 아닙니다. 이미 발송한 상품이나 고객에게 보낸 메일은 없던 일이 되지 않습니다.

timeout은 결과를 제때 받지 못했다는 뜻입니다. 결제가 실제 성공했는지 실패했는지는 모를 수 있습니다. 이 unknown outcome을 실패로 단정하면 중복 결제·결제 성공 후 재고 해제가 생깁니다.

답변 사고 순서

  1. 불변조건을 정한다: 주문당 중복 확정 결제 없음, 배송은 확인된 결제 이후.
  2. 각 단계의 성공·실패·결과 불명·보상 중·수동 확인 상태를 기록한다.
  3. 외부 요청에 주문/단계별 멱등 key를 사용하고 결과 조회 계약을 확인한다.
  4. 같은 key 재시도나 조회로 unknown을 해소한 뒤 다음 단계/보상을 결정한다.
  5. 보상 자체도 멱등·재시도 가능하게 만들고 실패를 보상 대기 상태로 남긴다.
  6. outbox와 상태 전이의 원자성, duplicate/late 이벤트의 가드, 만료·관측·수동 복구를 설계한다.

구체적 상태와 답변 예시

InventoryReserved
  → PaymentPending
  → PaymentUnknown   # timeout, 실패 확정 아님
  → PaymentAuthorized → ShipmentRequested → Completed
  → PaymentDeclined   → InventoryReleasePending → Cancelled

결제가 성공했으나 배송이 불가능하면 승인 취소/환불과 재고 해제를 수행합니다. 승인 취소와 환불은 비용·정책이 다를 수 있어 결제 제공자의 상태 계약을 확인합니다. 이벤트는 saga_id + step_id + command_id로 상관관계를 연결하고, 현재 상태와 허용 전이를 검사합니다.

timeout을 결제 실패로 확정하지 않겠습니다. 같은 멱등 key로 결과를 조회/재요청해 결과를 해소하고 배송은 승인 확인 뒤에만 진행하겠습니다. 보상도 독립 작업으로 기록하고 실패하면 재시도·수동 복구로 이어가겠습니다. 상태 변경과 발행은 outbox로 묶고 늦은 이벤트가 취소된 주문을 다시 진행시키지 않도록 전이 조건을 검증하겠습니다.

약한 답 “모든 예외에서 이전 단계 rollback을 호출합니다”는 결과 불명과 보상 실패·되돌릴 수 없는 효과를 생략합니다.

Trade-off와 흔한 오해

  • orchestration은 흐름·timeout·감사를 한곳에서 보기 좋지만 조정자의 가용성·버전 관리가 중요합니다. choreography는 결합을 분산하지만 사건 흐름·순환·보상이 어려워질 수 있습니다.
  • 예약을 오래 유지하면 unknown 해소에 여유가 생기지만 재고 활용률이 낮아집니다. 짧은 만료는 효율적이나 늦은 결제 성공 처리가 필요합니다.
  • 자동 보상은 복구가 빠르지만 되돌릴 수 없는 업무나 비용 큰 환불은 승인·수동 단계가 필요할 수 있습니다.

Saga는 DB isolation을 업무 전체에 제공하지 않습니다. 진행 중 상태를 다른 요청이 볼 수 있으므로 예약·확정 상태와 접근 정책을 명시해야 합니다. 멱등성도 업무에 맞는 key 보존·결과 반환 계약이 있어야 의미가 있습니다.

연습과 피드백

결과 확인 전 재고를 해제했고 뒤늦게 PaymentAuthorized 이벤트가 왔습니다. 이벤트를 무조건 처리하거나 무조건 버리는 것 중 무엇이 정답인가요?

해설 보기

둘 다 충분하지 않습니다. 주문의 현재 상태를 보고 배송은 막고, 실제 결제 승인 상태를 확인한 뒤 취소/환불 등 업무 정책을 실행합니다. 버리기만 하면 고객이 돈을 낸 취소 주문이 남습니다. 늦은 결과와 보상 원장을 연결하는 답이 좋습니다.

Follow-up과 자기 점검

보상 요청도 timeout이면? 보상 결과 불명으로 기록하고 멱등 key·조회로 해소합니다. 무한 재시도 대신 기간·경고·수동 확인을 둡니다.

조정자가 중간에 재시작하면? durable 상태·timer·명령 원장에서 재개하며 이미 실행된 외부 효과는 key와 결과 확인으로 중복을 막습니다.
