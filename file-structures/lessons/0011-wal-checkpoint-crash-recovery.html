WAL과 체크포인트를 이용한 크래시 복구 설계

Day 9의 append-only 로그를 데이터 페이지 영속화 순서와 복구 시간으로 연결한다.

레슨 목록 · 이전 Day 10 · 빠른 참고

면접 질문·상황

주문 저장 성공 응답 직후 서버가 꺼졌습니다. 데이터 페이지가 아직 디스크에 없으면 주문이 사라지나요?

Day 10의 주문 저장소가 WAL을 사용한다고 가정합니다. 면접관은 ‘로그가 있으니 안전’이라는 말 대신 성공 응답의 영속화 조건과 복구 절차를 설명하는지 봅니다.

전제 개념

메모리의 수정된 페이지는 전원이 꺼지면 사라집니다. WAL은 데이터 페이지를 영속 저장하기 전에 변경을 재현할 로그를 먼저 영속 저장하는 규칙입니다. 성공한 commit에 필요한 WAL이 디스크에 남았다면 아직 안 쓴 페이지를 로그로 다시 만들 수 있습니다. 이것이 redo입니다. 파일에 write했다는 것과 저장장치가 영속 보관했다는 것은 다릅니다.

PostgreSQL WAL 설명은 이 순서를 명시합니다. 실제 엔진의 commit 모드·fsync·저장장치 내구성 설정을 함께 확인합니다. 모든 WAL 구현이 같은 undo/redo 형식을 쓰는 것은 아닙니다.

답변 사고 순서·실행 흐름

  1. 클라이언트에 성공을 반환하는 지점을 정의합니다. 강한 내구성 계약이면 commit에 필요한 로그 영속화 뒤입니다.
  2. 로그 위치와 페이지 반영 상태를 연결하고, 복구 때 로그를 중복 재생해도 결과가 유지되는 규칙을 둡니다.
  3. 체크포인트를 안전한 복구 시작점으로 기록합니다. 단순히 ‘그 시각의 전체 snapshot’이라고 가정하지 않습니다.
  4. 체크포인트 이후 필요한 WAL을 재생하고, checksum·불완전 로그·부분 페이지 쓰기를 엔진 규칙에 따라 검증합니다.
  5. 정상 종료뿐 아니라 commit 직전·직후, 페이지 쓰기 중, 체크포인트 중 강제 종료를 가상 환경에서 재현합니다. 성공 응답을 받았던 주문 집합과 복구 결과를 비교합니다.
가상 로그: 100 checkpoint의 redo 시작점
110 주문 O-1 변경
120 주문 O-1 commit (영속 저장 완료)
130 주문 O-2 변경 (commit 전 crash)

O-1은 성공한 commit을 복구해야 합니다. O-2의 최종 가시성은 엔진의 미완료 트랜잭션 처리에 따릅니다. 임의로 로그에 등장한 모든 주문을 ‘성공 주문’으로 만들면 안 됩니다.

답변 예시·Trade-off

성공 응답을 필요한 WAL 영속화 이후로 정의하겠습니다. 페이지가 아직 쓰이지 않았어도 복구 시작점에서 로그를 재생해 성공 주문을 되살립니다. 체크포인트 빈도는 평시 I/O와 복구 시간을 함께 측정하고, 복제·백업이 필요로 하는 WAL은 로컬 복구가 끝났다는 이유만으로 지우지 않겠습니다.

체크포인트를 자주 하면 재생량을 줄일 수 있지만 페이지 쓰기와 추가 WAL 비용이 커집니다. 드물게 하면 평시 I/O는 줄 수 있지만 복구 시간·로그 공간이 늘어납니다. group commit은 여러 commit의 flush 비용을 나누지만 대기 정책에 따라 지연이 생깁니다. 체크포인트 공식 문서를 비교하세요.

약한 답변·오해: ‘체크포인트 이전 WAL은 전부 삭제합니다.’ 아카이브·replica·복제 slot·백업의 보존 조건이 남을 수 있습니다. 체크포인트와 백업은 역할이 다릅니다.

연습과 피드백

재생할 WAL이 8GB이고 측정 재생 속도는 200MB/s입니다. DB 복구 목표가 30초라면 합격인가요?

풀이 확인

십진 단위 가정에서 재생만 약 40초이므로 목표를 넘습니다. 프로세스 시작·검증 시간까지 더해야 합니다. 체크포인트·재생 처리량·복구 자원을 비교하되 평시 p99와 디스크 부하도 확인합니다. ‘체크포인트만 매초 실행’은 평시 비용을 무시하고, ‘로그를 삭제해 30초 달성’은 복구 가능성을 깨뜨립니다.

Follow-up·자기 점검

WAL만 있으면 백업은 없어도 되나요? 재생의 기반 데이터와 보존 이력이 필요합니다. 매체 자체를 잃은 경우 로컬 WAL도 사라질 수 있으므로 별도 백업·아카이브가 필요합니다.

commit 응답이 안 왔으면 실패인가요? commit 후 응답 전달 전에 끊겼을 수 있습니다. 주문 ID로 결과를 조회하고 중복 요청을 막습니다.
