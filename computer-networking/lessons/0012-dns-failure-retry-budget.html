DNS 장애 전파와 클라이언트 재시도 설계

Day 11의 리전 전환을 이어서, DNS 복구 후에도 실패가 남는 이유와 재시도 예산을 계산한다.

면접 질문과 상황

DNS 레코드를 복구했는데 일부 사용자는 계속 실패합니다. TTL을 낮추고 재시도를 늘리면 해결됩니까?

가상 장애: api.example.com에 NXDOMAIN을 60초간 잘못 반환했습니다. 복구 후 권한 서버는 정상이지만 일부 리졸버는 300초의 부정 응답을 기억합니다. SDK, API 프록시, 서비스가 각각 최대 3회 시도합니다. 면접관은 DNS 계층별 상태와 재시도에 따른 부하 증가를 함께 다루는지 확인합니다.

전제 개념부터 이해하기

DNS는 이름을 주소로 바꾸는 조회입니다. 권한 서버가 원본이라면 재귀 리졸버는 조회 결과를 잠시 보관하는 안내소입니다. 성공 응답을 기억하는 것처럼 ‘이 이름은 없다’는 NXDOMAIN도 기억합니다. 이것이 negative caching입니다. 원본을 고쳐도 안내소에 남은 답은 자동으로 즉시 바뀌지 않습니다.

RFC 2308 §5에서 부정 응답의 TTL은 SOA 레코드 TTL과 SOA.MINIMUM 중 작은 값에 근거합니다. A 레코드의 TTL만 낮춰서는 이미 남은 부정 캐시를 없애지 못합니다. NXDOMAIN, 주소 종류만 없는 NODATA, 해결 과정 자체가 실패한 SERVFAIL을 구분해야 합니다. 실패 캐시와 재조회 제한은 RFC 9520도 확인합니다.

DNS가 새 주소를 반환해도 기존 TCP 연결은 예전 주소로 이어질 수 있습니다. 따라서 ‘DNS는 정상인데 요청은 실패’라는 관찰에는 연결 풀과 런타임 DNS 캐시라는 별도 가설이 있습니다.

답변 사고 순서와 계산

  1. 오류 코드, 실패 시각, 리졸버와 클라이언트 종류별 영향 범위를 나눕니다.
  2. 같은 이름과 A/AAAA 유형으로 권한 서버·재귀 리졸버·애플리케이션 결과를 비교합니다. 가상 재현에서는 dig api.example.com A의 응답 코드와 authority SOA를 확인합니다.
  3. 남은 TTL과 연결 재사용을 구분하고, 특정 캐시만 제한적으로 갱신합니다. 전체 캐시 삭제는 조회 폭증을 만들 수 있습니다.
  4. 재시도 책임을 한 계층에 모읍니다. 각 계층의 ‘3회’가 최초 시도 포함이면 최악의 하위 시도 수는 3×3×3=27입니다.
  5. 전체 deadline 안에서 최대 시도 수와 동시 요청 수를 제한하고, 지수 backoff에 무작위 jitter를 더합니다. 재시도 시점 분산은 복구 서버로 요청이 한꺼번에 몰리는 현상을 줄입니다.

가상 예산이 2초이고 한 시도 timeout이 500ms라면 3회 시도에 대기 합계 600ms를 붙이는 정책은 2.1초로 초과합니다. 연결·DNS·TLS 시간도 timeout에 포함되는지 확인한 뒤, 남은 시간으로 다음 시도의 허용 여부를 결정합니다.

강한 답변과 약한 답변

권한 서버 복구와 클라이언트 복구는 구분하겠습니다. NXDOMAIN의 SOA 기반 잔여 TTL, 런타임 캐시, 기존 연결을 순서대로 확인합니다. 재시도는 SDK에 모으고 총 deadline·동시성·시도 수를 제한합니다. 쓰기 요청은 처리 여부가 불명확할 수 있으므로 멱등 키나 결과 조회가 있을 때만 재전송하겠습니다.

약한 답변: ‘TTL을 0으로 하고 무한 재시도합니다.’ 이전 캐시를 소급 변경할 수 없고, 새 조회·요청을 늘려 DNS와 정상 서버를 다시 압박합니다.

Trade-off와 흔한 오해

짧은 TTL은 향후 변경 반영을 빠르게 하지만 조회 비용과 DNS 의존성을 높입니다. 캐시 삭제는 일부 경로의 복구를 빠르게 하지만 동시 재조회가 위험하므로 대상과 속도를 제한합니다. 재시도는 순간 오류를 숨기지만 실패가 지속되면 부하를 증폭합니다. NXDOMAIN을 매번 즉시 다시 묻는 정책은 권한 서버가 고쳐졌는지 확인하려는 의도와 달리 공유 리졸버를 압박할 수 있습니다.

연습과 즉시 피드백

앱은 NXDOMAIN을 받지만 권한 서버 조회는 정상입니다. 호출 계층은 세 곳이며 각각 최대 2회 시도합니다. 첫 완화와 최악의 시도 수를 말해 보세요.

풀이와 판단 근거

최악은 8회입니다. 권한 서버를 다시 수정하기 전에 재귀 리졸버·앱 캐시의 응답과 남은 TTL을 비교합니다. 재시도를 한 계층으로 모으고 제한합니다. ‘원본 IP로 영구 우회’는 TLS 호스트 검증·주소 변경·로드밸런싱을 깨뜨릴 수 있어 일반 해결책이 아닙니다. ‘전체 서버 재시작’은 캐시 위치를 입증하지 못하고 동시 부하를 높입니다.

Follow-up과 자기 점검

TTL 만료 후에도 실패한다면? 실제 사용 리졸버, 런타임 캐시 정책과 오래된 연결을 분리 측정합니다. stale 응답 정책도 확인하므로 만료가 모든 계층의 갱신을 보장한다고 답하지 않습니다.

결제 요청 timeout 뒤 재시도해도 되나요? timeout은 처리 실패의 증거가 아닙니다. 같은 멱등 키로 조회·재요청하고 중복 결제를 막는 서버 계약부터 확인합니다.
