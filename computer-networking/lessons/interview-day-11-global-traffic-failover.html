글로벌 트래픽 분산과 장애 격리

한 리전 장애 때 트래픽을 옮기는 일은 DNS 레코드 변경만으로 끝나지 않는다. 감지, 용량, 세션, 데이터 쓰기 경로를 함께 설계한다.

오늘의 학습 결과: 헬스체크 신호와 failover 정책의 false positive·복구 비용을 설명한다

면접 질문

한 리전의 오류율이 급증했을 때 글로벌 트래픽을 어떻게 다른 리전으로 이동시키겠습니까?

실무 상황: 서울 리전의 API가 일부 고객에게만 5xx를 반환한다. 도쿄 리전은 정상이나 여유 용량은 평시 요청의 35%뿐이고, 일부 세션과 쓰기는 서울에 고정돼 있다.

왜 묻는가: 장애 감지와 트래픽 이동의 지연, 잘못된 failover, 리전 간 데이터 제약을 함께 판단하는지 본다.

전제 개념

DNS 기반 분산은 클라이언트와 리졸버 캐시 때문에 변경이 즉시 전파되지 않는다. Anycast·프록시 기반 분산은 더 빠른 제어가 가능할 수 있지만, 헬스체크가 실제 사용자 경로와 같은지를 확인해야 한다.

헬스체크가 성공한다고 서비스 전체가 정상인 것은 아니다. 반대로 한 경로의 체크 실패만으로 리전 전체를 빼면 정상 사용자를 다른 장애 도메인으로 몰 수 있다.

답변 사고 순서

  1. 영향 범위: 실패율을 리전·AZ·tenant·API·배포 버전으로 나눠 공통 원인을 찾는다.
  2. 신호 검증: 사용자 요청과 유사한 경로의 합성 체크, 실요청 오류율, 데이터 의존성을 교차 확인한다.
  3. 용량 계산: 남은 리전의 안전한 처리량을 큐 지연·CPU·DB 한도까지 포함해 산정한다.
  4. 이동 계획: 신규 요청부터 점진적으로 옮기고, 고정 세션·쓰기 소유권·재시도 폭증을 통제한다.
  5. 복귀 조건: 복구 후 자동 복귀 대신 안정 구간과 데이터 정합성 확인을 거쳐 단계적으로 원복한다.

케이스 풀이와 답변 예시

도쿄의 남는 용량이 35%라면 서울 트래픽 전부를 즉시 옮길 수 없다. 비핵심 읽기를 제한하고, 우선순위가 높은 사용자 요청만 이동하는 admission control과 함께 failover해야 한다.

먼저 오류가 특정 배포나 데이터 경로에 국한되는지 나누겠습니다. 전체 리전 장애가 확인되면 남은 용량을 기준으로 모든 트래픽을 보내지 않고, 쓰기 기능과 비핵심 요청을 제한해 핵심 API부터 옮기겠습니다. DNS TTL은 기존 연결을 즉시 바꾸지 못하므로 연결·세션 상태를 별도로 다루고, 복귀는 오류율과 복제 지연이 안정된 뒤 작은 비율부터 진행하겠습니다.

답변에서 드러나는 점: DNS 전파와 애플리케이션 상태의 차이, 남은 용량 한도, 복귀 절차를 포함한다.

Trade-off

선택얻는 점비용·위험
DNS failover구성이 단순하고 외부 프록시 의존이 적다.TTL·리졸버·클라이언트 캐시 때문에 전환 시간이 일정하지 않다.
엣지/Anycast 라우팅정책 변경과 글로벌 분산을 빠르게 제어할 수 있다.헬스체크 경로·엣지 정책·원본 용량을 별도로 검증해야 한다.
Active-active지역 근접성과 장애 내성이 높다.쓰기 충돌·데이터 소유권·운영 복잡도가 증가한다.

흔한 오해

헬스체크가 실패하면 해당 리전의 모든 트래픽을 즉시 제거하면 된다.

체크의 실패 도메인, quorum, 연속 실패 횟수, 남은 용량을 함께 고려한다. 오판으로 트래픽을 이동시키면 정상 리전도 연쇄 과부하에 빠진다.

직접 풀어보기

헬스체크는 정상인데 실제 로그인 요청의 오류율만 20%입니다. 어떤 지표와 경로를 비교하고, failover 결정은 어떻게 보류하거나 제한하겠습니까?

예시 풀이와 피드백 보기

로그인 dependency(세션 저장소·IdP·권한 서비스)와 합성 체크가 빠뜨린 경로를 추적한다. 전 리전 failover 대신 해당 경로의 배포/의존성 완화와 제한된 우회 여부를 판단한다.

자가 피드백: 체크 결과와 사용자 체감 지표를 구분했는가? 리전 이동 시 남는 용량과 세션/쓰기 문제를 말했는가?
