async/await 심화 — 의존성 그래프와 동시 실행

Day 9 Promise 상태 전이를 async 함수의 반환·await 경계·요청 의존성에 적용한다.

레슨 목록 · 이전 Day 9 · 빠른 참고

면접 질문·상황

await를 썼는데 화면 로딩이 API 지연의 합만큼 걸립니다. 모두 Promise.all로 바꾸면 됩니까?

가상 화면은 사용자 조회 200ms, 사용자 ID가 필요한 주문 조회 300ms, 독립적인 공지 조회 150ms를 수행합니다. 면접관은 문법이 아니라 요청 의존성과 실패 범위를 설계하는지 봅니다.

전제 개념과 실행 경계

async 함수 호출은 Promise를 반환합니다. 함수 몸체는 첫 await까지 현재 실행 흐름에서 수행되고, await 이후의 계속 실행은 기다린 값의 완료에 따른 비동기 작업으로 이어집니다. await는 해당 함수의 계속 실행을 멈출 뿐 JavaScript 실행 주체 전체를 막지 않습니다. CPU 작업을 긴 반복문으로 수행하면 async라는 이름을 붙여도 UI가 멈출 수 있습니다.

ECMAScript Await와 async 함수 정의가 기준입니다. 이를 ‘스레드를 새로 만든다’고 설명하지 마세요.

async function example() {
  console.log('A');
  await 1;
  console.log('C');
}
example();
console.log('B');

결과는 A, B, C입니다. 이미 준비된 값 1이라도 await 뒤는 현재 동기 실행이 끝난 뒤 이어집니다.

답변 사고 순서와 코드

  1. 필수·선택 결과와 요청 간 데이터 의존성을 그립니다.
  2. 호출을 시작하는 시점과 await하는 시점을 구분합니다.
  3. 독립 작업만 겹치고, 실패·취소·동시성 한도를 정합니다.
  4. 전체 wall time과 서버 부하·p99를 측정합니다.
async function load() {
  const noticePromise = getNotice();
  const orderPromise = getUser()
    .then(user => getOrders(user.id));
  const [orders, notice] = await Promise.all([
    orderPromise, noticePromise
  ]);
  return { orders, notice };
}

이 예시는 둘 다 필수라는 계약입니다. 단순 순차는 650ms, 의존성을 지킨 동시 실행은 이상적인 경우 max(200+300,150)=500ms입니다. 주문과 사용자 요청은 의존하므로 독립 3개처럼 시작해 300ms가 된다고 답하면 안 됩니다. 공지가 선택 결과라면 그 실패를 별도로 처리하는 계약이 필요합니다.

답변 예시·Trade-off·흔한 오해

사용자→주문은 순차 의존을 유지하고 공지는 병렬 시작하겠습니다. 필수 결과만 Promise.all로 결합하고 선택 결과의 실패는 별도 상태로 처리합니다. 대량 목록은 동시성 상한을 둬 서버 부하와 연결 수를 통제하겠습니다. async 자체가 CPU 작업을 병렬화하지는 않습니다.

약한 답변: ‘forEach(async …)에서 전부 await하면 끝입니다.’ forEach는 callback의 Promise 완료를 기다리지 않습니다. map으로 작업을 만들고 Promise.all을 await하거나 for…of로 순차 실행합니다. 순차 처리는 한도와 순서가 단순하지만 독립 I/O 지연이 합쳐집니다. 무제한 병렬은 작고 독립적인 묶음에 유리하지만 수만 요청에서 메모리·rate limit을 압박합니다.

async 함수에서 try { return work(); }는 work의 나중 rejection을 그 catch로 잡지 못합니다. 그 경계에서 잡아야 한다면 return await work()를 사용합니다. 모든 return에 await가 필요하다는 의미는 아닙니다.

연습과 피드백

독립 API A=100ms, B=400ms입니다. await A(); await B();와 await Promise.all([A(), B()]);의 이상적 완료 시간, 실패 시 남은 작업을 말해 보세요.

풀이 확인

순차 500ms, 동시 400ms입니다. Promise.all이 reject해도 다른 underlying 요청은 자동 취소되지 않습니다. ‘all은 순서대로 호출’은 결과 배열의 입력 순서와 완료 순서를 혼동합니다. ‘await가 브라우저를 400ms 멈춘다’는 함수의 일시 정지와 실행 주체 blocking을 혼동합니다.

Follow-up·자기 점검

공지 Promise를 먼저 만들고 user만 await하다 user가 실패하면? 공지의 rejection을 관측하지 못할 수 있습니다. 위처럼 의존 체인을 만들고 즉시 함께 결합하거나 선택 실패 handler를 붙여 모든 작업의 결과를 관측합니다.

1만 API 요청이면? 무제한 Promise.all보다 제한된 worker pool과 backpressure를 사용합니다. 취소 신호의 구체적 전파는 다음 Day에서 다룹니다.
