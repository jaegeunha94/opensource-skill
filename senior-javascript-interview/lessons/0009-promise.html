Promise의 상태 전이와 실패 전파

Promise는 미래 값의 상태를 나타내지만 작업 자체를 자동 취소하거나 중단하지 않는다. 상태 머신과 실행 queue를 구분한다.

오늘의 학습 결과: Promise chaining과 병렬 실패의 의미를 설명한다

면접 질문

세 API를 병렬 호출하는 화면에서 하나가 실패했을 때 다른 요청을 멈추고 사용자에게 일관된 오류를 보이려면 어떻게 하겠습니까?

실무 상황: 검색 페이지는 profile, recommendations, permissions를 동시에 불러온다. 권한 결과는 필수이고 추천 결과는 부분 실패를 허용한다.

왜 묻는가: Promise combinator의 의미·microtask timing·실제 취소 API와 오류 처리를 구분하는지 본다.

전제 개념

Promise는 pending에서 fulfilled 또는 rejected로 한 번만 settle한다. `.then`은 새 Promise를 반환하고 handler가 던진 예외는 그 후속 Promise의 rejection이 된다.

`Promise.all` rejection은 결과를 먼저 거부하지만 나머지 underlying 작업을 취소하지 않는다. fetch 취소를 원하면 AbortController 같은 취소 신호를 작업에 전달해야 한다.

답변 사고 순서

  1. 의존성 분류: 필수 결과와 선택 결과를 구분하고 병렬·순차 관계를 정한다.
  2. 조합 선택: 모두 성공해야 하면 all, 각 결과를 수집하려면 allSettled, 첫 성공이면 race/any를 고려한다.
  3. 취소 전파: 필수 실패 시 나머지 fetch에 AbortSignal을 보내 비용을 줄일지 판단한다.
  4. 오류 경계: 사용자 재시도 가능성, 부분 결과, 로그 상관 ID를 분리한다.
  5. 수명 관리: 컴포넌트 unmount나 새 검색으로 오래된 요청이 결과를 덮지 않도록 한다.

케이스 풀이와 답변 예시

permissions 실패는 화면을 열면 안 되지만 recommendations 실패는 빈 추천으로 degraded 응답할 수 있다. Promise.all 하나에 모든 호출을 넣으면 optional 실패까지 전체 화면을 실패시킨다.

세 호출 중 권한만 필수이므로 권한과 profile을 화면 진입 조건으로 명확히 정하고 추천은 독립 실패를 허용하겠습니다. 필수 요청이 실패하면 sibling fetch에 AbortSignal을 보내되 서버가 이미 처리한 작업까지 취소된다고 가정하지 않겠습니다. 새 검색이 시작되면 이전 응답을 폐기하고, optional 실패는 별도 상태와 retry affordance로 표시하겠습니다.

답변에서 드러나는 점: Promise API의 결과 조합과 네트워크 작업의 취소 가능성을 분리한다.

Trade-off

선택얻는 점비용·위험
Promise.all모든 성공 결과를 한 번에 반환해 의존성이 단순하다.하나의 rejection이 전체 결과 흐름을 실패시키고 sibling은 계속 실행될 수 있다.
Promise.allSettled부분 성공과 실패를 모두 수집한다.필수/선택 결과를 호출자가 직접 분류해야 한다.
병렬 호출총 wall time을 줄일 수 있다.불필요한 비용·서버 부하와 취소 race가 늘어날 수 있다.

흔한 오해

Promise.race에서 timeout Promise가 이기면 원래 작업도 중단된다.

race는 반환 Promise의 결과만 먼저 settle한다. 원래 fetch/작업이 계속될 수 있으므로 AbortSignal 또는 작업 자체 취소 계약을 사용한다.

직접 풀어보기

검색 A 요청 후 검색 B를 보냈는데 A 응답이 늦게 도착해 화면을 덮습니다. stale result를 막는 방법을 설명하세요.

예시 풀이와 피드백 보기

각 실행에 증가하는 request sequence를 부여하고 현재 sequence와 일치할 때만 state를 갱신하거나, 이전 fetch를 AbortController로 취소한다. 취소가 서버 side effect rollback을 뜻하지는 않는다.
