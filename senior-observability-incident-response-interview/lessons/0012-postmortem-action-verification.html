면접 질문과 실무 상황

Day 8에서 postmortem 작성, Day 11에서 Game Day를 배웠습니다. 이번 장애에서 재시도가 DB 연결 풀을 고갈시켰고 “알림 개선·교육·재시도 수정” 티켓을 모두 닫았습니다. 한 달 뒤 같은 장애가 났다면 무엇이 빠졌습니까?

면접관은 담당자 탓을 피하는 표현뿐 아니라 관찰된 실패를 검증 가능한 시스템 변화로 바꾸는 능력을 봅니다.

전제 개념

postmortem은 영향을 받은 사용자, 사건의 시간 순서, 당시 판단에 주어진 정보, 기여 조건을 남기는 기록입니다. action item은 그 기록에서 나온 변경입니다. 티켓을 닫았다는 것은 작업 완료일 뿐, 위험이 줄었다는 증거는 아닙니다.

출력은 “timeout 코드를 배포했다”, 결과는 “의존성이 느려져도 대기열이 한도를 넘지 않는다”입니다. 둘을 연결하는 검증 조건이 필요합니다. 알림은 탐지 시간을 줄일 수 있지만 부하 증폭 자체를 막는 장치는 아닙니다.

답변 사고 순서

  1. 영향·타임라인·관측 사실과 추정을 구분한다. 로그가 없는 구간은 추정이라고 표시한다.
  2. 재현 조건을 적는다: 의존성 지연, 요청량, 재시도 횟수, 풀 크기.
  3. 예방·탐지·완화 action을 구분하고 실제 기여 조건과 연결한다.
  4. 각 action에 owner·기한·성공 기준·실험·증거 위치를 둔다.
  5. 개선 후 제한된 재시험을 하고, 기대하지 않은 데이터 손실·오류를 함께 검사한다.
  6. 재검토 날짜와 잔여 위험을 기록한다. 효과 없는 action은 닫힌 티켓이어도 다시 열어 수정한다.

구체적 action을 만들기

가상 사건: 평소 100 req/s, DB 지연 증가 시 요청당 총 시도 4회가 발생해 최대 400회/s의 시도 부하가 생겼습니다. 400이라는 수는 독립 재시도가 모두 실행된다는 단순 가정이며 실제 동시성은 timeout·취소에 따라 달라집니다.

행동검증 가능한 결과증거
전체 deadline과 retry budget 적용고정 입력 부하에서 총 시도 수가 합의 한도 안, deadline 뒤 추가 DB 작업 없음요청·시도 counter, cancellation trace
풀 앞 bounded queue/admission의존성 지연 때 대기열이 한도 안, 거부는 명시적이며 메모리 폭증 없음queue length·reject·메모리·p99
알림과 runbook 개선같은 신호에서 탐지·담당자 확인·완화 시간을 별도 목표 안에 달성훈련 타임라인과 실제 수행 기록

“교육 실시”에는 반복 가능한 상황 판단 연습을 붙입니다. 수강 인원만 측정하면 장애 대응 능력이 늘었는지 알 수 없습니다.

답변 예시와 trade-off

당시에는 DB 지연과 독립 재시도가 겹쳐 부하를 증폭했습니다. retry budget과 queue 한도를 각각 예방·완화 조치로 만들고, 같은 입력 부하와 지연 조건에서 시도 수·대기열·사용자 오류·정합성을 측정하겠습니다. 알림 변경은 감지 시간을 별도로 재시험하겠습니다. owner와 검증일을 두고 증거가 있어야 action의 효과를 인정하겠습니다.

약한 답 “담당자를 교육하고 모니터링을 강화합니다”는 어떤 실패가 달라지는지 설명하지 못합니다.

  • 강제 한도는 과부하를 억제하지만 일부 요청을 즉시 거부합니다. 무한 대기로 전체 장애가 나는 비용과 비교합니다.
  • 운영 재시험은 현실성이 높지만 영향 비용이 있습니다. 격리 부하 시험으로 선행 검증하고 운영에서는 범위·중단 조건을 제한합니다.
  • 많은 action은 포괄적이지만 실행력을 분산합니다. 기여도가 큰 몇 개에 책임과 증거를 먼저 붙입니다.

흔한 오해

“blameless이면 책임자가 없다”는 오해입니다. 사람을 사건의 단일 원인으로 비난하지 않지만 개선의 owner는 명확해야 합니다. “한 달간 장애가 없었다”는 재현 조건이 없었다면 효과 증명이 아닙니다.

연습과 피드백

action “DB 알림 threshold를 낮췄다”의 성공 기준을 “이후 장애 0건”으로 적었습니다. 더 좋은 기준과 그것이 해결하지 못하는 위험을 쓰세요.

해설 보기

동일 지연 신호에서 알림 발생까지 시간, on-call 확인 시간, 오탐 횟수·빈도와 누락을 확인합니다. threshold는 DB 지연이나 retry 증폭을 예방하지 않으므로 부하 한도 등 별도 action이 필요합니다. 발생 확률이 낮은 사건의 0건을 인과 효과로 해석하지 않은 답이 좋습니다.

Follow-up과 자기 점검

재현이 어려운 장애라면? 확인된 조건을 분리해 시험하고, 재현하지 못한 가정과 관측 보강 계획을 명시합니다. 동일 장애를 재현했다고 과장하지 않습니다.

개선이 다른 팀 소유라면? 해당 팀과 owner·우선순위·완료 조건을 합의하고 추적합니다. 문서의 “타 팀 요청”만으로 책임이 이전되지 않습니다.
