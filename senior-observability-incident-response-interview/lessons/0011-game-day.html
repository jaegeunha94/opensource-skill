Game Day — 가설·중단 조건·학습을 갖춘 장애 훈련

카오스 실험의 목표는 장애를 크게 만드는 것이 아니라, 명시한 가설과 복구 절차를 안전하게 검증하는 것이다.

오늘의 학습 결과: 훈련 범위·stop condition·성공 기준·후속 개선을 설계한다

면접 질문

리전 의존 서비스의 장애 훈련을 실제 운영 환경에서 진행하려면 어떤 안전장치와 측정 기준을 두겠습니까?

실무 상황: 서비스는 두 리전에 배포됐지만 실제 traffic failover는 해본 적이 없다. DR 문서는 있으나 최근 복구 리허설은 1년 전이다.

왜 묻는가: 실험 도구보다 blast radius·승인·stop condition·사용자 영향 관측을 우선하는지 평가한다.

전제 개념

Game Day는 팀이 장애 시나리오를 제한된 범위에서 연습해 시스템과 대응 과정을 검증하는 훈련이다. “장애를 주입했다”가 아니라 가설이 맞는지 관측하고 복구하는 것이 목적이다.

운영 자원에 대한 fault injection은 실제 고객 영향을 낼 수 있다. 작은 target, 시간 제한, 독립 stop alarm, 실험 중단 권한이 없으면 실험을 시작하지 않는다.

답변 사고 순서

  1. 가설과 scope: 예: AZ 하나의 연결 실패에도 p99와 오류율이 SLO 안에 머물고 자동 failover한다.
  2. 준비: 대상 리소스, 영향 사용자, owner, on-call, rollback, 변경 동결, 공지를 확정한다.
  3. guardrail: 오류율·queue age·데이터 무결성·비용 alarm을 stop condition으로 연결한다.
  4. 실행 관측: control group과 실험군을 비교하고 타임라인·판단·복구 지연을 기록한다.
  5. 학습 전환: 관찰 결과를 runbook/alert/action item으로 바꾸고 owner·기한·재시험일을 정한다.

케이스 풀이와 답변 예시

첫 리허설은 전체 리전이 아니라 비핵심 내부 service 또는 한 AZ의 제한된 비율부터 시작한다. 자동 복구가 실패하면 실험 중단과 수동 복구를 바로 수행한다.

우선 어떤 장애 가설을 확인하는지와 허용 사용자 영향, 종료 신호를 서비스 owner와 합의하겠습니다. 영향이 작은 대상에서 시작하고 SLO burn·queue age·데이터 오류가 기준을 넘으면 자동 stop하도록 구성하겠습니다. 실행 중에는 control 대비 오류율, 감지부터 완화까지의 시간, 담당자 handoff를 기록하겠습니다. 종료 뒤 발견 사항마다 owner·기한을 부여하고 개선 완료 후 같은 시나리오를 다시 실행하겠습니다.

답변에서 드러나는 점: 실험을 이벤트가 아니라 반복 가능한 운영 개선 루프로 제시한다.

Trade-off

선택얻는 점비용·위험
사전 운영 시뮬레이션현실성과 복구 행동을 함께 검증한다.잠재 사용자 영향이 있으므로 guardrail과 중단 권한이 필요하다.
격리된 staging fault injection실제 고객 영향 없이 스크립트를 검증한다.운영 IAM·용량·traffic과 차이가 있어 production behavior를 충분히 증명하지 못할 수 있다.
tabletop exercise저비용으로 역할과 의사결정 흐름을 점검한다.실제 자동화·alarm·복구시간은 검증되지 않는다.

흔한 오해

카오스 훈련은 장애를 랜덤으로 많이 주입할수록 효과가 크다.

가설과 가드레일 없는 주입은 위험만 늘린다. 안전한 blast radius에서 관측 가능한 불변조건을 검증하고 학습을 개선으로 연결한다.

직접 풀어보기

실험 중 API 오류율은 정상인데 queue age가 4배 늘고 DB replication lag가 증가합니다. 다음 액션은 무엇인가요?

예시 풀이와 피드백 보기

실험 설계에 queue age/replication lag stop threshold가 있다면 즉시 중단하고 복구한다. 없었다면 안전 신호 누락으로 기록하고 영향과 backlog drain을 관측한 뒤 실험을 종료한다.
