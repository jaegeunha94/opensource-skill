면접 질문과 실무 상황

Day 11에서 keyset으로 깊은 목록을 빠르게 만들었습니다. 첫 페이지를 30초 캐시하고 다음 페이지는 DB에서 읽으니 변경된 주문이 누락됩니다. 히트율 95%와 p99 개선만으로 성공입니까?

면접관은 속도 개선이 데이터 계약을 바꾸었는지 설명하는 능력을 봅니다. Day 5의 캐시 무효화를 페이지 경계에 적용하는 것이 오늘의 핵심입니다.

전제 개념

페이지는 정렬된 결과 집합의 일부입니다. keyset은 마지막 정렬 값 뒤에서 이어 읽지만 한 시점의 전체 집합을 자동 고정하지 않습니다. 캐시된 첫 페이지와 현재 DB의 두 번째 페이지는 서로 다른 시점의 조각일 수 있습니다.

목록을 둘러보는 live feed는 새 항목이 다음 새로고침에 보이는 의미를 허용할 수 있습니다. 정산 export는 합의한 시점의 모든 항목을 정확히 한 번 포함해야 합니다. 두 기능에 같은 캐시 계약을 적용하면 안 됩니다. TTL 30초도 모든 값의 최대 지연이 30초라는 보장은 아닙니다. 원본 복제 지연·갱신 실패·stale 제공이 더해질 수 있습니다.

답변 사고 순서

  1. live 목록과 snapshot export를 구분하고 허용 stale·누락·중복을 명시한다.
  2. 정렬 키의 고유성·변경 가능성, 필터·tenant·권한 범위를 확인한다.
  3. 캐시 key에 결과를 바꾸는 조건과 cursor·schema/version을 포함한다.
  4. 수정 시 기존/새 위치·첫 페이지·후속 cursor에 주는 영향을 재현한다.
  5. 필요하면 snapshot 결과 materialization/version을 사용한다. max ID 상한만으로 모든 업데이트를 고정했다고 주장하지 않는다.
  6. p99·DB work·비용과 stale age·중복·누락을 함께 비교한다.

구체적 변경 사례

점수 내림차순 목록이 A=100, B=90, C=80, D=70이고 한 페이지는 2개입니다. 캐시된 1페이지는 A/B, cursor는 (90,B)입니다. 이후 C가 110으로 바뀌면 “90보다 작은 점수”의 2페이지에는 D만 나와 C가 이 탐색에서 누락됩니다. 고유한 tie-breaker를 넣어도 변경 가능한 정렬 키 이동은 남습니다.

계약전략검증
live 탐색, 새로고침 시 최신짧은 cache, 변경 표시, 안정된 cursor약속한 stale, refresh 동작, 권한 격리
동일 시점 정산 결과snapshot/물질화한 결과 ID와 페이지 version기준 집합 대비 누락·중복 0, 금액 합계
업데이트 직후 본인 확인해당 사용자 경로 bypass/version 전환read-your-write 조건과 부하

snapshot을 장시간 DB 트랜잭션으로 유지하면 vacuum·자원 부담이 생길 수 있어 결과를 별도 생성하는 export job도 비교합니다. cursor의 서명은 변조를 막지만 현재 사용자의 접근 권한 확인을 대신하지 않습니다.

답변 예시와 trade-off

현재 p99 개선은 확인했지만 페이지의 의미가 섞였습니다. live 목록에는 허용 신선도와 새로고침 동작을 명시하고, 정산 export는 기준 시점 결과 version으로 모든 페이지를 묶겠습니다. 점수 이동·삭제·동점·권한 변경을 시험하고 누락·중복·합계와 지연·DB 부하를 함께 측정하겠습니다.

약한 답 “TTL을 줄이면 됩니다”는 다른 시점 조각과 정렬 키 이동을 해결하지 못합니다.

  • live 결과는 최신 변경을 빨리 보여주지만 세션 전체 집합은 고정되지 않습니다. snapshot은 의미가 안정적이나 생성·보관·만료 비용이 있습니다.
  • 넓은 무효화는 일관성이 단순하지만 hit rate가 낮아집니다. 정밀 무효화는 효율적이지만 관련 페이지를 놓치기 쉽습니다.
  • 권한별 캐시는 격리에 유리하지만 key 수가 증가합니다. shared cache를 쓰려면 공유 가능한 결과라는 계약이 필요합니다.

흔한 오해

keyset은 모든 동시 변경의 중복·누락을 막는다는 오해가 있습니다. 정렬 값이 바뀌면 항목이 cursor 양쪽을 이동할 수 있습니다. 캐시 hit rate가 높아도 오래되거나 권한이 잘못된 응답이면 성공이 아닙니다.

연습과 피드백

위 A/B/C/D 사례에서 정렬 키가 변하지 않는 생성 시각으로 바뀌었습니다. snapshot 없이 “모든 페이지가 동일 시점”이라고 할 수 있나요?

해설 보기

아닙니다. 정렬 위치 이동은 줄지만 삭제·필드 수정·필터 조건 변경이 남습니다. 동일 시점 요구는 결과 집합과 내용까지 고정해야 합니다. 반대로 live 목록이라면 그 정도의 고정은 필요 없을 수 있습니다. 먼저 요구를 묻는 답이 좋습니다.

Follow-up과 자기 점검

권한 철회 뒤 캐시가 남으면? 현재 권한을 확인하고 결과 key/version을 무효화하는 경계를 설계합니다. TTL만 기다리는 것은 보안 계약에 맞지 않을 수 있습니다.

실험에서 누락을 어떻게 세나? 가상 고정 입력과 변경 이력을 만들고 요구 snapshot의 정답 ID 집합·합계와 실제 페이지 결합을 비교합니다.
