대용량 페이지네이션 — OFFSET에서 keyset으로

OFFSET이 커질수록 반환하지 않을 행도 찾고 건너뛰어야 한다. 안정적인 정렬 key와 cursor 계약으로 바꿀 수 있는지 판단한다.

오늘의 학습 결과: offset/keyset pagination의 비용과 동시 업데이트 의미를 비교한다

면접 질문

수천만 행의 주문 목록에서 페이지 20,000번의 응답이 느리고 결과가 중복됩니다. 어떻게 개선하겠습니까?

실무 상황: 정렬은 `created_at DESC`뿐이고 동시 삽입이 계속된다. UI는 이전/다음 이동과 특정 페이지 번호 점프를 모두 제공한다.

왜 묻는가: cursor pagination으로 무조건 바꾸지 않고 정렬 안정성, 사용자 요구, snapshot 의미를 설명하는지 본다.

전제 개념

OFFSET pagination은 앞의 N개 행을 건너뛰고 다음 범위를 반환한다. keyset pagination은 직전 페이지 마지막 sort key보다 앞/뒤에 있는 행부터 이어서 읽는다.

keyset은 안정적이고 고유한 정렬 key가 필요하며 임의 페이지 번호 점프가 어렵다. `created_at`이 같은 행이 있으면 unique tie-breaker 없이는 중복·누락이 생긴다.

답변 사고 순서

  1. 접근 패턴: 깊은 page, next/previous, total count, snapshot consistency 요구를 확인한다.
  2. 정렬 계약: 불변 또는 안정된 정렬 키와 unique tie-breaker를 정한다.
  3. 인덱스 설계: filter와 sort를 함께 반영하는 복합 인덱스와 실제 실행 계획을 확인한다.
  4. cursor 계약: cursor에 sort values·방향·filter fingerprint·버전/서명을 넣는다.
  5. 이행: UI/API를 cursor로 단계 전환하고 결과 안정성과 p95·DB work를 비교한다.

케이스 풀이와 답변 예시

`created_at`이 같을 수 있다면 `(created_at, id)` 내림차순으로 정렬하고 다음 query는 마지막 tuple보다 작은 값을 찾는다. tenant filter가 있으면 tenant key도 index와 cursor scope에 반영한다.

먼저 사용자가 임의 page jump를 정말 필요로 하는지 확인하겠습니다. 무한 스크롤/다음 페이지가 중심이라면 `(created_at, id)`를 고유한 정렬로 정하고 동일 순서의 복합 인덱스를 추가한 keyset cursor를 적용하겠습니다. cursor는 filter와 정렬 조건에 바인딩하고 서명해 변조를 막겠습니다. total count가 꼭 필요한지 별도 확인하고 깊은 page, 동시 삽입/삭제에서 중복·누락 여부와 DB buffers를 측정하겠습니다.

답변에서 드러나는 점: 쿼리 최적화와 API pagination 의미, index order, 동시 변경의 영향을 연결한다.

Trade-off

선택얻는 점비용·위험
OFFSET/LIMIT간단하고 특정 page 번호로 이동하기 쉽다.깊은 offset에서 버리는 행 비용이 커지고 동시 변경 시 page가 흔들린다.
Keyset/cursor다음 페이지 비용이 결과 위치와 더 밀접하고 안정적이다.임의 page jump와 역방향 cursor 구현이 복잡하다.
Snapshot 기반 탐색한 번의 browsing session에서 일관된 집합을 제공한다.긴 transaction/snapshot 유지가 vacuum·resource pressure를 만들 수 있다.

흔한 오해

cursor pagination은 전체 count와 임의 페이지 번호를 공짜로 제공한다.

cursor는 순서에 따른 continuation token이다. 임의 page 접근이나 정확한 전체 count에는 다른 index·snapshot·제품 UX 결정이 필요하다.

직접 풀어보기

정렬 기준 `score DESC` 값은 같은 행이 많고 점수가 갱신됩니다. 안정된 keyset 탐색을 만들 수 있는지와 요구 변경안을 설명하세요.

예시 풀이와 피드백 보기

고유 tie-breaker인 id를 추가해 일관된 순서를 만들 수 있지만 score가 탐색 중 바뀌면 이동 누락/중복은 여전히 가능하다. browsing snapshot 또는 시간 기준 cutoff를 둘지 제품 요구와 일관성 수준을 합의한다.
