대용량 페이지네이션 — OFFSET에서 keyset으로

offset/keyset pagination의 비용과 동시 업데이트 의미를 비교한다

핵심 판단

OFFSET이 커질수록 반환하지 않을 행도 찾고 건너뛰어야 한다. 안정적인 정렬 key와 cursor 계약으로 바꿀 수 있는지 판단한다.

OFFSET pagination은 앞의 N개 행을 건너뛰고 다음 범위를 반환한다. keyset pagination은 직전 페이지 마지막 sort key보다 앞/뒤에 있는 행부터 이어서 읽는다.

검토 순서

  1. 접근 패턴: 깊은 page, next/previous, total count, snapshot consistency 요구를 확인한다.
  2. 정렬 계약: 불변 또는 안정된 정렬 키와 unique tie-breaker를 정한다.
  3. 인덱스 설계: filter와 sort를 함께 반영하는 복합 인덱스와 실제 실행 계획을 확인한다.
  4. cursor 계약: cursor에 sort values·방향·filter fingerprint·버전/서명을 넣는다.
  5. 이행: UI/API를 cursor로 단계 전환하고 결과 안정성과 p95·DB work를 비교한다.

선택 비교

선택얻는 점비용·위험
OFFSET/LIMIT간단하고 특정 page 번호로 이동하기 쉽다.깊은 offset에서 버리는 행 비용이 커지고 동시 변경 시 page가 흔들린다.
Keyset/cursor다음 페이지 비용이 결과 위치와 더 밀접하고 안정적이다.임의 page jump와 역방향 cursor 구현이 복잡하다.
Snapshot 기반 탐색한 번의 browsing session에서 일관된 집합을 제공한다.긴 transaction/snapshot 유지가 vacuum·resource pressure를 만들 수 있다.

주의할 함정

오해: cursor pagination은 전체 count와 임의 페이지 번호를 공짜로 제공한다.

실제 경계: cursor는 순서에 따른 continuation token이다. 임의 page 접근이나 정확한 전체 count에는 다른 index·snapshot·제품 UX 결정이 필요하다.

면접에서 꺼낼 사례

`created_at`이 같을 수 있다면 `(created_at, id)` 내림차순으로 정렬하고 다음 query는 마지막 tuple보다 작은 값을 찾는다. tenant filter가 있으면 tenant key도 index와 cursor scope에 반영한다.

확인 질문: 정렬 기준 `score DESC` 값은 같은 행이 많고 점수가 갱신됩니다. 안정된 keyset 탐색을 만들 수 있는지와 요구 변경안을 설명하세요.

근거와 복습

PostgreSQL 공식 문서 — LIMIT and OFFSET — OFFSET이 결과 순서와 planner 비용에 미치는 주의점을 확인한다.
