ConfigMap/Secret — 갱신 전파와 시크릿 회전 계약

설정의 저장·전달·앱 반영을 구분하고 credential 회전을 중단 없이 검증한다.

레슨 목록 · 이전 Day 9 · 빠른 참고

면접 질문과 실무 상황

DB 비밀번호 Secret을 바꿨는데 일부 Pod는 옛 비밀번호를 쓰고 일부는 새 비밀번호로 연결합니다. Secret이 base64이므로 암호화도 끝났다고 합니다. 어떤 문제가 섞여 있습니까?

Day 9의 저장소 마운트와 달리 오늘은 설정의 변경 전파와 앱이 다시 읽는 동작을 봅니다. 면접관은 객체 갱신 성공을 전체 프로세스 반영 성공으로 착각하지 않는지 평가합니다.

전제 개념

ConfigMap은 비밀이 아닌 설정, Secret은 민감 값을 취급하는 API 객체입니다. base64는 표현 인코딩으로 복호화 키 없이 되돌릴 수 있어 암호화가 아닙니다. API 접근 권한과 etcd 저장 시 암호화는 별도 설정·검증 대상입니다.

갱신에는 세 단계가 있습니다: API 객체 변경 → kubelet의 Pod 전달 → 앱 재읽기/연결 갱신. 파일이 바뀌어도 앱이 시작할 때 한 번 읽었다면 값은 바뀌지 않습니다. 외부 secret manager도 이 전달·회전 계약을 대신 설계해주지는 않습니다.

답변 사고 순서

  1. env·일반 volume·subPath·CSI 등 소비 방식을 목록화한다.
  2. 객체 버전과 각 Pod의 적용 버전, 앱의 재읽기 동작을 값 노출 없이 확인한다.
  3. 전파 지연과 rollout/reload 전략을 정한다. 즉시 동시 반영을 가정하지 않는다.
  4. 신구 credential의 중첩 기간·새 연결 검증·옛 연결 drain·폐기 순서를 DB와 합의한다.
  5. RBAC·namespace·Pod 생성 권한·etcd encryption at rest·감사/로그 노출을 함께 확인한다.
  6. 회전 실패 시 허용된 중첩 기간 안의 복구와 전체 적용 확인을 시험한다.

전달 방식의 차이와 회전 예시

소비 방식갱신필요한 앱 동작
환경변수실행 중 자동 변경 안 됨새 Pod로 교체
일반 projected volumekubelet 동기화·캐시 전파에 따라 나중에 반영다시 열어 읽기/reload, 적용 검증
subPath mountSecret/ConfigMap 변경을 자동 전달받지 못함사용 방식 변경 또는 Pod 교체
immutable 객체data를 수정하는 방식 사용 불가새 이름 객체와 Pod template 변경

가상 DB가 두 credential을 일정 기간 허용한다고 가정합니다. 새 credential 생성 → 새 Secret 버전 전달 → 새 연결 성공 확인 → 모든 Pod의 적용 버전 확인 → 옛 연결 drain → 옛 credential 폐기 순서입니다. DB가 중첩 credential을 지원하지 않으면 별도 계정·프록시·정지 창 같은 대안을 검토해야 합니다.

적용 버전은 예를 들어 비밀이 아닌 credential_version=v2로 보고합니다. 비밀번호 자체나 저엔트로피 비밀의 해시를 로그로 남기지 않습니다. readiness가 단순 프로세스 생존만 보면 새 DB 인증 실패를 숨길 수 있습니다.

답변 예시와 trade-off

일부 Pod의 env 값과 volume 소비 방식부터 나누겠습니다. 환경변수는 객체 변경만으로 바뀌지 않으므로 rollout이 필요합니다. 파일 마운트는 전파 이후 앱의 재읽기와 연결 풀 교체까지 검증하겠습니다. DB가 지원하는 중첩 기간 동안 새 연결을 확인한 뒤 옛 credential을 폐기하겠습니다. base64와 저장 암호화를 구분하고 API/Pod 생성 권한도 검토하겠습니다.

약한 답 “Secret apply 뒤 모든 Pod가 자동 갱신됩니다”는 env·subPath·앱 상태를 놓칩니다.

  • env+rollout은 반영이 명확하지만 교체 비용과 신구 버전 공존이 있습니다. live reload는 중단을 줄이지만 재읽기 오류·연결 수명 관리가 어렵습니다.
  • 외부 manager는 중앙 회전·감사를 돕지만 접근·연결·CSI/controller 가용성과 전달 지연이 추가됩니다.
  • 신구 credential 중첩은 안정성을 높이지만 옛 비밀의 유효 시간이 늘어납니다. 짧고 측정 가능한 폐기 조건을 둡니다.

흔한 오해

Secret read 권한만 막으면 충분하다는 오해가 있습니다. 같은 namespace에서 Pod를 만들 수 있는 권한이 Secret을 소비하게 만들 수 있습니다. encryption at rest는 API로 허용된 읽기나 앱 로그 유출을 막지 않습니다. 현재 release/deprecation 자료를 확인했으며 설정 전달의 안정적 계약을 중심으로 작성했습니다.

연습과 피드백

Secret 파일이 새 값으로 바뀌었습니다. 앱은 시작 때 읽고 DB pool은 연결을 30분 유지합니다. 지금 옛 credential을 폐기해도 될까요?

해설 보기

안 됩니다. 파일 변경은 앱 적용과 새 연결 성공의 증거가 아닙니다. 앱 reload/rollout, 새 pool 연결 확인, 옛 pool drain과 모든 replica의 적용 버전을 확인합니다. 기존 연결이 유지되는지 여부도 DB 인증 정책에 달려 있으므로 “연결은 영원히 안전하다”고 가정하지 않습니다.

Follow-up과 자기 점검

전파에 몇 초가 걸리나요? 고정 숫자로 보장하지 않습니다. kubelet sync 주기와 캐시/watch 지연·구성을 확인하고 앱 반영 시간을 실측합니다.

회전 중 외부 manager가 끊기면? 기존 전달 값 사용·만료·새 Pod 시작 실패 정책을 명시합니다. 만료된 credential을 무제한 사용하는 것으로 장애를 숨기지 않습니다.
