Kubernetes 스토리지 — PVC 바인딩부터 장애 복구까지

PVC가 Bound라고 애플리케이션의 저장 요구가 모두 해결된 것은 아니다. access mode·topology·백업·재연결 동작을 확인한다.

오늘의 학습 결과: workload의 durability·attachment·failover 요구에 맞게 storage 경로를 설계한다

면접 질문

stateful database를 여러 node에 배치하면서 zone 장애와 Pod 재스케줄링을 견디는 스토리지를 어떻게 설계하겠습니까?

실무 상황: PVC는 동적 provisioning을 사용한다. CSI volume은 특정 zone에 있고 StatefulSet Pod가 다른 zone으로 reschedule되면 attach가 실패할 수 있다.

왜 묻는가: Kubernetes API 객체 관계뿐 아니라 storage topology, access mode의 의미, reclaim·snapshot·복구시간을 이해하는지 본다.

전제 개념

PVC는 사용자의 저장 요청이고 PV는 실제 제공된 저장 자원이다. StorageClass와 CSI provisioner가 어떤 저장소를 만들지 연결하고, Pod가 PVC를 mount한다.

`ReadWriteOnce`는 한 node에서 read-write mount를 허용한다는 access mode이지, 한 Pod만 접근하거나 DB writer가 한 개라는 분산 lock 보장이 아니다. 데이터 보호는 애플리케이션 복제와 backup 계획이 맡는다.

답변 사고 순서

  1. 데이터 계약: 내구성, IOPS·latency, 확장, 동시 attach, snapshot consistency 요구를 정한다.
  2. topology 확인: zone/node 제약과 `WaitForFirstConsumer`, Pod affinity, CSI driver 제한을 함께 본다.
  3. 수명 정책: StorageClass reclaimPolicy, PVC 삭제, StatefulSet retention을 명시한다.
  4. 복구 흐름: attach/detach, fencing, restore, volume expansion 실패 시 runbook을 만든다.
  5. 실제 훈련: node/zone failover와 snapshot restore 시간을 측정하고 데이터 일관성을 확인한다.

케이스 풀이와 답변 예시

zone 고정 block volume을 쓰는 DB는 Pod가 임의의 zone으로 옮겨갈 수 없다. scheduler가 Pod topology를 알고 volume을 provision하도록 binding mode를 정하고, zone 손실 때 replica promote와 volume 재연결의 순서를 검증한다.

먼저 DB가 요구하는 RPO/RTO와 volume 성능·attach 제약을 확인하겠습니다. CSI driver의 topology와 reclaim policy를 검증하고, zone-bound volume이면 `WaitForFirstConsumer` 및 StatefulSet 배치 규칙을 일치시키겠습니다. RWO를 분산 write lock으로 오해하지 않고 DB replication과 fencing으로 단일 writer를 보호하겠습니다. snapshot 복구와 zone 장애 실험에서 attach 시간, 데이터 손실, replica promotion까지 측정하겠습니다.

답변에서 드러나는 점: PVC 상태만 확인하지 않고 scheduler부터 CSI, 데이터 복구까지 전체 lifecycle을 설명한다.

Trade-off

선택얻는 점비용·위험
Network block volume낮은 지연과 block device semantics를 제공한다.zone attachment와 단일 writer/failover 제약이 있을 수 있다.
Shared file storage여러 Pod가 파일을 공유하기 쉬울 수 있다.파일 lock semantics, metadata 성능, 비용과 consistency를 확인해야 한다.
Local PVnode-local 지연이 낮다.node 장애 시 재배치가 어렵고 data replication을 애플리케이션이 책임져야 한다.

흔한 오해

PVC가 여러 Pod에서 mount되면 저장 데이터도 자동으로 안전하게 공유된다.

access mode와 실제 backend semantics는 CSI driver별로 다르다. 동시에 쓰는 애플리케이션의 locking·consistency와 복구 전략을 확인한다.

직접 풀어보기

Pod가 Pending이고 PVC는 Pending입니다. `WaitForFirstConsumer` StorageClass인데 Pod spec에 `nodeName`이 지정돼 있습니다. 원인과 조치를 설명하세요.

예시 풀이와 피드백 보기

nodeName은 scheduler를 우회해 PVC binding과 topology-aware provisioning을 막을 수 있다. nodeSelector/affinity로 placement를 표현해 scheduler가 consumer 정보를 활용하도록 한다.
