Kubernetes 스토리지 — PVC 바인딩부터 장애 복구까지

workload의 durability·attachment·failover 요구에 맞게 storage 경로를 설계한다

핵심 판단

PVC가 Bound라고 애플리케이션의 저장 요구가 모두 해결된 것은 아니다. access mode·topology·백업·재연결 동작을 확인한다.

PVC는 사용자의 저장 요청이고 PV는 실제 제공된 저장 자원이다. StorageClass와 CSI provisioner가 어떤 저장소를 만들지 연결하고, Pod가 PVC를 mount한다.

검토 순서

  1. 데이터 계약: 내구성, IOPS·latency, 확장, 동시 attach, snapshot consistency 요구를 정한다.
  2. topology 확인: zone/node 제약과 `WaitForFirstConsumer`, Pod affinity, CSI driver 제한을 함께 본다.
  3. 수명 정책: StorageClass reclaimPolicy, PVC 삭제, StatefulSet retention을 명시한다.
  4. 복구 흐름: attach/detach, fencing, restore, volume expansion 실패 시 runbook을 만든다.
  5. 실제 훈련: node/zone failover와 snapshot restore 시간을 측정하고 데이터 일관성을 확인한다.

선택 비교

선택얻는 점비용·위험
Network block volume낮은 지연과 block device semantics를 제공한다.zone attachment와 단일 writer/failover 제약이 있을 수 있다.
Shared file storage여러 Pod가 파일을 공유하기 쉬울 수 있다.파일 lock semantics, metadata 성능, 비용과 consistency를 확인해야 한다.
Local PVnode-local 지연이 낮다.node 장애 시 재배치가 어렵고 data replication을 애플리케이션이 책임져야 한다.

주의할 함정

오해: PVC가 여러 Pod에서 mount되면 저장 데이터도 자동으로 안전하게 공유된다.

실제 경계: access mode와 실제 backend semantics는 CSI driver별로 다르다. 동시에 쓰는 애플리케이션의 locking·consistency와 복구 전략을 확인한다.

면접에서 꺼낼 사례

zone 고정 block volume을 쓰는 DB는 Pod가 임의의 zone으로 옮겨갈 수 없다. scheduler가 Pod topology를 알고 volume을 provision하도록 binding mode를 정하고, zone 손실 때 replica promote와 volume 재연결의 순서를 검증한다.

확인 질문: Pod가 Pending이고 PVC는 Pending입니다. `WaitForFirstConsumer` StorageClass인데 Pod spec에 `nodeName`이 지정돼 있습니다. 원인과 조치를 설명하세요.
