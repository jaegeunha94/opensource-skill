Workers와 Redirect/Transform Rules — 요청 경로와 마이그레이션

주소 이동·내부 재작성·프로그래밍 로직을 구분하고 규칙 충돌을 요청 단위로 검증한다.

면접 질문과 실무 상황

옛 Page Rule이 old.example.com/docs/*를 새 도메인으로 이동시킵니다. URL Rewrite와 Worker를 추가한 뒤 일부 요청이 엉뚱한 경로로 이동합니다. 어떤 기능에 어떤 책임을 두고 어떻게 이전하겠습니까?

Day 7의 origin 선택 위에 오늘은 엣지 요청 처리의 경계를 얹습니다. 면접관은 대시보드 순서 암기보다 브라우저가 보는 URL·origin이 받는 요청·규칙의 종료 여부를 구분하는지 봅니다.

전제 개념

Redirect는 3xx와 Location으로 클라이언트에게 새 URL로 요청하라고 말합니다. Rewrite는 요청을 내부에서 바꾸므로 브라우저 주소가 그대로일 수 있습니다. Worker는 코드를 실행해 응답·외부 호출·복잡한 분기를 만들 수 있습니다.

규칙은 한 목록의 숫자 순서만으로 결정되지 않습니다. 기능별 phase가 있고, Redirect 같은 종료 action은 일치하면 평가를 끝냅니다. 현재 문서에서 Single Redirect는 URL Rewrite보다 앞서고 Bulk Redirect보다 앞섭니다. 같은 phase의 비종료 변경은 뒤 규칙이 덮을 수 있지만, 같은 phase에서 평가에 쓰는 필드 값은 phase 내 변경을 즉시 반영한다고 가정하지 않습니다.

답변 사고 순서

  1. 원래 요청의 scheme·host·path·query·method와 최종 요구를 기록한다.
  2. 단순 주소 이동은 Single/Bulk Redirect, 내부 path/header 수정은 Transform, 동적 외부 데이터·복잡한 응답은 Worker로 책임을 정한다.
  3. Page Rules의 각 setting을 대응 제품으로 나눈다. 예전 “첫 Page Rule 일치”를 새 제품 전체에 그대로 적용하지 않는다.
  4. 공식 phase 목록·신규 Rules와 Page Rules의 우선 관계·Worker route 범위를 확인한다.
  5. 대표 URL과 경계 URL을 Cloudflare Trace 및 실제 요청으로 비교하고, 한 번의 이동·query·method 요구를 확인한다.
  6. 좁은 hostname/path부터 이전하고 이전 규칙 비활성화·되돌림 순서를 기록한다.

구체적 이전 사례

요구책임검증
옛 docs 주소를 새 공개 문서로 이동Single Redirect; 대규모 정적 대응 목록이면 Bulk 검토path suffix·query 보존 여부·새 URL loop 없음
공개 URL /help를 origin의 /support로 전달URL Rewrite브라우저 주소 유지, origin 요청 경로 일치
서명 확인 후 지역별 외부 API 응답 조합Workerroute·실행 한도·실패 응답·캐시 격리

가상 입력 https://old.example.com/docs/install?lang=ko의 목표를 https://new.example.com/docs/install?lang=ko로 정했다면, scheme/host/path/query 각각을 assertion으로 둡니다. 모든 query를 무조건 전달하면 민감한 토큰을 새 도메인에 넘길 수 있으므로 이 요구를 먼저 확인합니다.

읽기 문서의 영구 이동과 POST API 이동은 다릅니다. 301/302는 클라이언트에 따라 POST가 GET으로 바뀔 수 있고 307/308은 method 보존을 요구합니다. method와 body가 새 대상에서 안전하게 처리되는지도 따로 확인합니다. Worker를 추가했다고 앞서 종료된 Redirect를 고칠 수 있는 것은 아닙니다.

답변 예시와 trade-off

먼저 대표 요청의 원본과 목표 URL을 나누겠습니다. 단순 이동은 Redirect에 남기고 내부 rewrite와 동적 Worker 로직을 분리하겠습니다. 신규 Rules가 기존 Page Rules와 겹치는 경우의 우선순위와 종료 action을 확인하고, Trace로 일치 규칙을 본 뒤 실제 Location·method·origin 로그로 검증하겠습니다. 좁은 범위에서 이전하고 구 규칙 제거와 rollback을 함께 준비하겠습니다.

약한 답 “Worker에서 모든 것을 처리합니다”는 단순 기능에도 실행·관측·운영 비용을 얹습니다.

  • 선언형 Rules는 단순하고 관리가 쉽지만 지원 표현식·기능·플랜의 한계가 있습니다. Worker는 유연하지만 코드·배포·오류·비용 관리가 추가됩니다.
  • 영구 redirect는 캐시·SEO에 유리하지만 잘못된 결과가 클라이언트에 오래 남을 수 있습니다. 시험 구간에는 임시 이동의 의미도 검토합니다.
  • query 전체 보존은 호환성을 돕지만 비밀·불필요한 변형을 전달할 수 있습니다. 허용 query 계약을 정합니다.

흔한 오해와 자료 확인

Transform은 브라우저 주소를 바꾸는 기능이라는 오해가 있습니다. 또한 새 Rules와 Page Rules가 항상 순차로 누적 적용되는 것도 아닙니다. 현재 공식 migration guide·execution order·changelog를 확인했으며 과거 Page Rules 설계를 신규 설정의 기본값으로 재사용하지 않았습니다. Trace는 규칙 판단 증거이고 실제 클라이언트의 캐시·origin 응답까지 대체하지 않습니다.

연습과 피드백

Single Redirect가 /old를 /new로 이동시키고 URL Rewrite가 /old를 /internal로 바꿉니다. “rewrite를 목록 아래로 옮기면 redirect 대상이 /internal이 된다”는 제안이 맞나요?

해설 보기

아닙니다. 기능의 phase 순서를 목록 위치로 뒤집을 수 없고 일치한 Single Redirect는 종료 action입니다. 목표가 내부 전달이면 Redirect를 제거/범위 제외하고 Rewrite를 설계해야 합니다. 주소 이동이면 Redirect 자체의 목표를 바꿔 검증합니다. 두 책임을 구분한 답이 좋습니다.

Follow-up과 자기 점검

redirect loop를 어떻게 찾나? 각 단계의 Location, scheme/host, origin의 redirect와 TLS 모드를 추적하고 최종 URL이 다시 이전 조건에 일치하는지 검사합니다.

Worker와 Rules가 복잡하게 섞이면? 공식 경로와 subrequest 처리 조건을 따로 확인하고, 원본 요청과 Worker 발신 요청을 별도로 추적합니다. 같은 phase 체계를 무조건 재실행한다고 가정하지 않습니다.
