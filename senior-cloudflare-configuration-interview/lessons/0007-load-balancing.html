Cloudflare Load Balancing — health monitor와 steering

로드밸런서는 설정한 건강 신호를 정책에 따라 라우팅으로 바꾼다. probe가 실제 사용자 경로를 대표하는지 확인해야 한다.

오늘의 학습 결과: monitor·pool threshold·traffic steering을 장애 조건과 연결한다

면접 질문

두 origin pool 중 한 곳에서 로그인 오류가 일부 지역에만 발생합니다. Cloudflare health monitor와 steering을 어떻게 구성하겠습니까?

실무 상황: 기본 monitor는 origin IP로 직접 probe하고, 실제 요청은 Cloudflare WAF와 인증 경로를 지난다. fallback pool은 평시 요청을 받을 용량이 제한돼 있다.

왜 묻는가: probe와 사용자 트래픽 경로의 차이, quorum·threshold·fallback 동작을 이해하는지 본다.

전제 개념

monitor는 endpoint 응답을 주기적으로 검사하고 pool은 여러 endpoint를 묶는다. traffic steering 정책은 pool 건강과 구성에 따라 사용자를 어느 endpoint에 보낼지 결정한다.

origin 직접 probe가 통과해도 WAF·TLS·인증 또는 실제 hostname 경로에서 실패할 수 있다. monitor 응답 코드를 넓게 허용하면 실제 애플리케이션 오류를 건강하다고 오판한다.

답변 사고 순서

  1. 요청 경로: 사용자 요청과 health probe가 통과하는 DNS·TLS·WAF·origin 단계를 비교한다.
  2. probe 설계: 핵심 read-only 경로, 예상 상태코드·응답 body, timeout을 정의한다.
  3. 판정 안정화: region quorum, consecutive up/down, pool health threshold로 순간 오류에 흔들리지 않게 한다.
  4. steering 선택: active-passive와 active-active를 용량·세션·데이터 locality에 맞춘다.
  5. fallback 점검: 모든 primary pool unhealthy, monitor 미설정, fallback 용량 초과 상황을 리허설한다.

케이스 풀이와 답변 예시

로그인 오류가 특정 지역에서만 나는지 probe region을 일치시키고, 실제 서비스 요청 경로를 probe가 통과하도록 할지 검토한다. 동시에 health endpoint가 DB 장애를 숨기지 않는지 정의한다.

먼저 로그인 사용 경로와 현재 probe 경로의 차이를 확인하겠습니다. region별 정상 요청 오류율을 기준으로 health endpoint를 설계하고, 짧은 transient 실패에는 consecutive threshold를 둬 flapping을 막겠습니다. active-passive는 DR 용량과 세션 지속성에 적합한지, active-active는 공유 데이터의 쓰기 소유권을 감당할 수 있는지 비교하겠습니다. fallback은 마지막 보호 수단으로 두고 실제 용량과 오류 응답을 함께 훈련하겠습니다.

답변에서 드러나는 점: 제품 옵션 나열 대신 health 판정의 정확도와 routing consequence를 연결한다.

Trade-off

선택얻는 점비용·위험
직접 origin probe구성과 부하가 단순하다.WAF·Cloudflare routing 등 사용자 경로의 실패를 발견하지 못할 수 있다.
경로 재현 probe실제 서비스 경로에 가까운 신호를 얻는다.추가 처리량·인증 설정·probe 의존성 관리가 필요하다.
Active-active steering지역별 지연과 사용 가능한 용량을 활용한다.stateful session과 write conflict를 설계해야 한다.
Active-passive failover주/대기 구조가 단순하고 전환을 제어하기 쉽다.평시 자원 활용률이 낮고 전환 용량의 실제 준비가 필요하다.

흔한 오해

monitor가 healthy면 사용자 요청도 정상이다.

monitor는 정의된 probe만 증명한다. 사용자 요청의 인증·cache·WAF·경로·의존성을 대표하는지 검증한다.

예시 풀이와 피드백 보기

fallback을 capacity-free라고 가정하지 않는다. 정적 degraded page/제한된 읽기, rate limit, retry-after, 예상 복구 안내를 설계하고 health가 회복될 때까지 overload를 막는다.
