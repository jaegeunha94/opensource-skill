면접 질문·상황

여러 서버에서 같은 방에 메시지를 보내고 연결이 끊겼다 돌아와도 순서와 중복을 어떻게 다룹니까?

가상 서비스는 동시 연결 100만, 초당 메시지 5만 개, 평균 본문 1KB입니다. 일일 원본 본문은 대략 4.32TB이며 복제·인덱스·fanout 비용은 별도입니다. 면접관은 WebSocket 연결 수와 영속 메시지 계약을 분리하는지 봅니다.

전제 개념

WebSocket은 연결 위에서 양방향 메시지를 주고받는 통신 수단입니다. 한 연결의 전송 순서가 여러 sender·여러 서버·재접속 전체의 업무 순서를 정해 주지는 않습니다. ‘서버가 받음’, ‘영속 저장됨’, ‘수신 단말에 전달됨’, ‘사람이 읽음’이라는 ack 의미를 먼저 구분합니다.

오늘의 계약은 대화방별 순서와 영속 저장 후 전송자 ack, 재접속 때 중복 없이 화면 복구입니다. 모든 방의 전역 순서는 요구하지 않습니다. 메시지 ID는 재시도 중복 제거, 방별 sequence는 순서·누락 복구에 사용합니다. 단말 시계는 순서 권한으로 쓰지 않습니다.

답변 사고 순서·경로

  1. 송신자는 client_message_id와 room_id를 보냅니다. 서버는 참여 권한을 확인합니다.
  2. 방 소유 partition/처리기가 순서를 정하고 동일 client_message_id의 재시도는 같은 결과로 처리합니다.
  3. 메시지와 room sequence를 영속 저장하고, 그 계약이 완료된 후 sender에게 저장 ack를 보냅니다.
  4. 온라인 수신자에게 gateway로 fanout합니다. 느린 단말의 송신 buffer에 상한을 두고 끊기면 cursor 기반 복구로 전환합니다.
  5. 재접속 단말은 마지막 연속 수신 seq를 보내고, 서버는 이후 메시지를 페이지로 줍니다. 단말은 ID로 중복 제거하고 gap이 있으면 조회합니다.
단말의 마지막 연속 seq: 40
실시간으로 먼저 도착한 seq: 42
복구 조회: after=40 → 41, 42, 43
화면 적용: 41, 42, 43 (42는 한 번만 표시)

42를 받았다고 cursor를 바로 42로 올리면 41을 누락할 수 있습니다. Kafka의 partition 순서·전달 문서는 로그 순서 계약을 이해하는 근거입니다. 실제 room sequence 설계는 이 가상 요구에서 도출한 예시이며 Kafka만 쓰면 자동 완성되는 기능은 아닙니다.

답변 예시·Trade-off·오해

WebSocket gateway는 연결을 유지하고 방별 메시지 순서는 영속 처리 경로가 담당하게 하겠습니다. 같은 client_message_id를 재시도해도 메시지는 한 번 저장하고, 저장 ack와 전달·읽음 상태를 구별합니다. 재접속은 마지막 연속 seq 이후를 조회해 gap과 중복을 복구합니다.

약한 답변: ‘WebSocket이 TCP라 순서는 해결됩니다.’ 서로 다른 연결과 장애 후 재전송의 업무 순서는 별도입니다. 방별 단일 순서 권한은 단순하지만 초대형 방이 hot partition이 됩니다. 전체 fanout은 빠르지만 거대 방의 비용이 커집니다. 느린 수신자 buffer 무제한 유지는 전달을 시도하지만 gateway 메모리를 고갈시킵니다. 제한·재접속 조회는 자원을 지키지만 복구 지연을 만듭니다.

오해: at-least-once 전달이면 사용자가 중복 메시지를 보게 해야 한다. 전달 중복을 ID 기반 저장·표시 계약으로 숨길 수 있습니다. 부작용까지 exactly-once라는 확대 해석은 피합니다.

연습·피드백

메시지 저장 후 sender ack 전에 gateway가 죽었습니다. 송신자가 같은 client_message_id로 재전송하면 어떻게 처리합니까?

풀이 확인

이미 저장된 ID의 message_id·seq를 찾아 같은 결과로 ack합니다. 새 ID와 seq로 다시 저장하면 중복이 생깁니다. ‘ack가 없으니 미저장’은 결과 불명확성을 무시합니다. ‘재전송 금지’는 저장 전 실패 때 메시지를 잃으므로 조회·재시도 계약이 필요합니다.

Follow-up·자기 점검

방 소유 서버가 바뀌면? fencing epoch와 복구된 마지막 sequence로 두 소유자가 동시에 번호를 배정하지 못하게 합니다.

읽음은 어디까지 보장하나요? 단말 표시·사용자 확인 중 의미를 합의하고 room별 read cursor로 압축할 수 있습니다. push 알림 성공을 읽음으로 세지 않습니다.
