뉴스 피드 / 타임라인 — fanout 비용과 최신성 설계

뉴스피드는 단순히 게시물을 정렬하는 API가 아니다. 팔로우 수 편중과 새 글 반영 지연이 fanout 방향을 결정한다.

오늘의 학습 결과: fanout on write/read와 하이브리드 경계를 workload로 선택한다

면접 질문

월간 사용자 1억 명 규모의 홈 피드를 설계하고, 유명인의 새 글이 빠르게 보이게 해보세요.

실무 상황: 대부분 사용자는 팔로우 300명 이하이지만 일부 유명인은 수천만 명의 follower가 있다. 피드는 개인화 랭킹과 차단/삭제 반영도 요구한다.

왜 묻는가: 요구사항·fanout·storage·cache·ranking 경계를 확장성 및 최신성 요구에 맞춰 설명하는지 본다.

전제 개념

fanout on write는 게시 시점에 follower별 inbox를 채우고, fanout on read는 피드 요청 때 팔로우한 계정의 게시물을 모은다. 전자는 읽기가 빠르고 후자는 쓰기 작업이 적다.

유명인까지 모든 follower에 write fanout하면 폭발적인 작업이 생긴다. 반대로 모든 계정을 read-time merge하면 follow graph와 후보 집합이 커져 p99가 나빠진다.

답변 사고 순서

  1. API와 SLO: 새 글 반영 시간, feed p99, page size, 삭제·차단 반영 시간을 정의한다.
  2. 규모 추정: 활성 사용자·write rate·follower distribution·읽기/쓰기 비율을 계산한다.
  3. fanout 정책: 일반 계정은 write, 초대형 계정은 read 또는 hybrid로 처리한다.
  4. 후보와 랭킹: 후보 생성·중복 제거·차단 필터·ranking을 분리하고 pagination cursor를 설계한다.
  5. 일관성·캐시: 삭제 tombstone, cache invalidation, late event와 retry를 고려한다.

케이스 풀이와 답변 예시

일반 사용자는 글 발행 시 제한된 follower inbox에 id를 넣고, 유명인은 read path에서 별도 후보로 merge한다. 요청 시 두 후보군을 합치고 최신 차단·삭제 정책을 적용한다.

먼저 feed의 freshness와 p99, 삭제/차단 반영 SLA를 합의하겠습니다. follower 분포가 heavy-tail이므로 단일 fanout 전략을 강제하지 않고 일반 계정은 write fanout, celebrity는 read-time merge하는 hybrid를 시작점으로 두겠습니다. inbox에는 게시물 본문보다 id와 정렬 키를 저장하고, pagination은 안정된 `(rank/time, post_id)` cursor를 사용하겠습니다. queue lag·celebrity 후보 비용·캐시 hit와 삭제 반영 지연을 관찰해 전략 경계를 조정하겠습니다.

답변에서 드러나는 점: 단일 아키텍처 답을 암기하지 않고 분포와 사용자 약속으로 분기를 정한다.

Trade-off

선택얻는 점비용·위험
Fanout on Writefeed read가 빠르고 사용자별 후보를 미리 준비한다.follower가 많은 계정의 write amplification과 queue lag가 커진다.
Fanout on Read게시 시 비용이 낮고 최신 원본을 읽는다.요청 시 follow graph 조회·merge가 커져 tail latency가 늘어난다.
Hybrid일반/celebrity 분포를 각각 효율적으로 처리한다.두 경로의 중복 제거·정렬·삭제 정책을 일관되게 유지해야 한다.

흔한 오해

피드의 모든 데이터는 사용자마다 완전히 materialize하면 읽기 문제가 사라진다.

write amplification, 저장 공간, 최신성 backlog가 생긴다. 유명 계정·새 사용자·재랭킹 요구에서 materialization 비용이 커질 수 있다.

직접 풀어보기

유명 계정이 5천만 follower에게 동시에 글을 올립니다. 모든 inbox에 게시물 본문을 복제하지 않고 노출하는 경로를 설명하세요.

예시 풀이와 피드백 보기

celebrity 게시물은 fanout-on-read 후보로 유지하고 사용자의 일반 inbox 후보와 request-time merge한다. 후보 수와 랭킹 비용을 제한하고 캐시하되 삭제·차단 필터를 최신 정책으로 적용한다.

자가 피드백: 사용자 수만 말하지 않고 follower 분포와 읽기/쓰기 경로의 비용을 계산했는가?

  2. 차단 직후 이미 inbox/cache에 들어간 게시물은 언제 숨겨야 합니까?
  3. 랭킹 모델이 바뀌었을 때 기존 feed materialization은 어떻게 재생성합니까?
