Metadata와 Provenance — 답변 근거를 원본까지 추적하기

각 chunk의 출처·버전·위치·변환 기록을 모델 출력까지 보존한다

핵심 판단

답변에 문서 제목 하나를 표시하는 것으로는 근거를 재현하기 어렵다. 원본 버전과 변환 과정이 연결돼야 한다.

provenance는 데이터가 어디서 왔고 어떤 변환을 거쳐 현재 값이 되었는지 기록하는 것이다. RAG에서는 답변 문장 → retrieved chunk → parsed artifact → 원본 파일의 연결을 보존한다.

검토 순서

  1. 원본 identity: source system, stable document id, version/ETag, content hash, ACL snapshot을 기록한다.
  2. 변환 lineage: parser/OCR/model 버전, 설정, 실행 id, 오류와 page/section/table 위치를 기록한다.
  3. chunk identity: chunk id를 source version·transform version·location에 연결한다.
  4. 답변 추적: 응답에서 사용한 chunk id와 검색 score/filter, prompt/model version을 저장한다.
  5. 변경·삭제: 새 버전 색인과 기존 버전 폐기, 권한 변경·삭제 전파를 검증한다.

선택 비교

선택얻는 점비용·위험
간단한 source URL만 기록저장 공간과 구현이 작다.같은 URL의 수정 이후 답변을 재현하지 못하고 권한 변경 추적이 어렵다.
불변 source version + 변환 manifest답변 재현과 parser 변경 비교, 감사가 가능하다.저장 비용과 version lifecycle·삭제 정책이 필요하다.
원문 전체 복제검색과 장애 복구에서 독립성이 커진다.저작권·개인정보·ACL drift와 중복 저장을 관리해야 한다.

주의할 함정

오해: 문서 제목과 페이지 번호를 인용하면 답변을 검증할 수 있다.

실제 경계: 문서가 수정되거나 parser가 페이지를 다르게 나눌 수 있다. 답변 당시의 version과 추출 위치, 변환 run을 함께 보존한다.

면접에서 꺼낼 사례

사용자가 “정책 4.2절” 인용을 누르면 현재 파일의 같은 page가 아니라 답변을 만들 당시 source version과 section으로 연결돼야 한다. 원본이 갱신됐으면 이전 인용을 과거 버전 표시 또는 최신 문서로 유도한다.

확인 질문: 검색 결과에는 정확한 문서 제목이 있지만 source version hash가 없습니다. 감사 질문에 답할 수 없는 지점을 설명하고 최소 metadata를 제안하세요.
