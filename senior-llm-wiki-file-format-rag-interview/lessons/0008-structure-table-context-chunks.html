문서 구조 기반 Semantic Chunking — 표의 의미와 근거 경계

표의 헤더·단위·각주를 보존하며 검색 단위와 답변 근거 단위를 분리한다.

레슨 목록 · 이전 Day 7 · 빠른 참고

면접 질문과 실무 상황

정책 PDF의 표에서 “50”만 검색되어 모델이 환급액을 50원이라고 답했습니다. 실제 단위는 만원이고 각주에 지급 제외 조건이 있습니다. 500토큰씩 overlap을 늘리면 해결될까요?

Day 7에서 provenance를 보존했습니다. 오늘은 그 원본의 의미를 어느 경계까지 묶어 검색할지 정합니다. 면접관은 문서 포맷을 평문으로 만든 뒤 이미 잃은 의미를 검색 튜닝으로 해결하려 하는지 봅니다.

전제 개념

structure-aware chunking은 제목·문단·표·코드 같은 파서가 찾은 구조를 경계로 씁니다. embedding 의미 유사도 변화로 자르는 semantic chunking과 같은 말은 아닙니다. 둘은 조합할 수 있지만 구조 추출의 오류를 먼저 확인해야 합니다.

표 셀의 의미는 행 이름·열 헤더·단위·범위·각주에서 나옵니다. 계층형 chunk는 작은 검색 단위와 더 넓은 parent section을 연결하는 방식입니다. 작은 행이 잘 검색돼도 답변 context에는 해석에 필요한 범위를 다시 가져와야 합니다.

답변 사고 순서

  1. 파싱 결과에서 제목·표 구조·헤더·병합 셀·단위·각주가 남았는지 원본과 비교한다.
  2. 질문이 한 행 조회인지 행 간 비교인지, 조건 해석인지 분류한다.
  3. 표는 행 단위 내용에 헤더·단위를 연결하고, 전체 표/section parent를 보존한다.
  4. 검색 child와 context parent를 원본 버전·좌표·ACL에 바인딩한다. parent 확장이 권한을 넓히지 않게 확인한다.
  5. contextual retrieval의 보충 설명은 검색 보조로 취급하고 원문 사실·인용과 구분한다.
  6. 정답 근거 coverage·조건 누락·citation과 토큰·비용을 실제 포맷별 gold 질문으로 비교한다.

표를 구체적으로 재구성하기

대상지원액 (만원)각주
일반 고객50이미 지원받은 경우 제외
우대 고객80동일 조건
# 설계용 chunk 표현 예시, 실제 parser 출력 포맷은 아님
child: 대상=일반 고객; 지원액=50; 단위=만원;
       적용 조건=이미 지원받은 경우 제외
parent: 정책 v3 > 지원 기준 > 표 2
source: 원문 v3, page=4, table=2, row=1
context_note: 이 표는 고객 유형별 지원 한도와 제외 조건을 다룸

“50만 원”의 금액을 반환하려면 단위가 필요하고, “이전에 받았는데 가능한가?”에는 각주가 필요합니다. 고객 유형 간 차이는 두 행과 같은 표의 공통 조건이 필요합니다. 잘못 추출된 각주를 모델로 추정해 채우지 말고 파싱 오류로 분류합니다.

현재 Unstructured 문서는 partition 뒤 element를 묶는 chunking, table 별도 취급과 큰 표 분할, by_title 경계를 설명합니다. 도구의 옵션 단위가 문자 수라면 모델의 토큰 한도와 같다고 가정하지 않습니다. 최신 release에는 표 병합/분할 관련 수정도 있어 parser 버전 변경 후 표 회귀셋을 다시 확인해야 합니다.

답변 예시와 trade-off

먼저 원본 표와 추출 구조를 비교해 단위·헤더·각주 유실을 확인하겠습니다. 검색용 행 chunk에 해석 필드를 붙이고 전체 표/section을 parent로 연결하겠습니다. 질문 유형에 따라 필요한 행과 조건을 context로 확장하되 ACL과 version을 유지하겠습니다. contextual 설명은 원문 인용과 분리하고 금액·조건·비교 질문에서 정확성과 토큰 비용을 함께 측정하겠습니다.

약한 답 “overlap을 100으로 올립니다”는 단위·각주가 구조적으로 연결되지 않은 결함을 가립니다.

  • 행 chunk는 정확한 항목 검색에 유리하지만 공통 조건·비교를 놓치기 쉽습니다. 큰 표는 맥락이 넓지만 noise와 비용이 큽니다.
  • 헤더 반복은 의미를 보존하지만 중복 토큰을 늘립니다. parent 확장은 중복을 줄일 수 있으나 조회와 조립이 복잡합니다.
  • 생성한 context note는 검색에 도움을 줄 수 있지만 추정 오류와 새 임베딩 비용이 생깁니다. 원문 기반 검증과 별도 표시가 필요합니다.

흔한 오해

chunk를 짧게 하면 항상 검색이 좋아진다는 오해가 있습니다. “50”처럼 의미가 사라진 조각은 유사도 점수가 높아도 근거가 부족합니다. 파일명·source URL만으로 parent와 child의 같은 버전을 증명할 수도 없습니다.

연습과 피드백

“우대와 일반의 지원액 차이는?”에 우대 행만 검색됐습니다. 그럴듯한 30만원 답을 모델이 만들었지만 일반 행은 context에 없습니다. 어떤 개선과 평가가 필요할까요?

해설 보기

같은 표의 비교 대상 행과 단위·공통 조건을 추가 검색/parent 확장으로 가져옵니다. gold 질문에서 필요한 양쪽 근거가 들어온 비율과 실제 차이·인용을 검사합니다. 답의 숫자가 우연히 맞아도 근거 완전성이 부족한 사례로 기록합니다.

Follow-up과 자기 점검

한 section 안에 권한이 다른 표가 있다면? parent를 통째로 확장하지 않습니다. 허용 element만 조립하고 구조 metadata가 ACL보다 우선하지 않게 합니다.

PDF와 XLSX에 같은 전략을 쓰나? XLSX의 셀 좌표·수식/표시값과 PDF의 읽기 순서·OCR 오류가 다릅니다. 보존할 의미 계약은 같아도 파싱·회귀 검증은 포맷별입니다.
