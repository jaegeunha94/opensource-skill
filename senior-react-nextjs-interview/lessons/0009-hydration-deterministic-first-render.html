Hydration 심화 — 서버와 첫 클라이언트 렌더를 맞추기

Day 8의 실패 격리에 더해, 서버 HTML과 첫 렌더의 불일치 원인을 재현하고 제거한다.

레슨 목록 · 이전 Day 8 · 빠른 참고

면접 질문·상황

배포 후 가격 옆 날짜에서 hydration 오류가 납니다. suppressHydrationWarning으로 해결하면 될까요?

가상 상품 화면은 렌더 중 현재 시각과 localStorage 통화를 읽습니다. 서버는 기본 통화 KRW, 브라우저는 USD입니다. 면접관은 경고 제거와 첫 화면의 결정적 일치를 구별하는지 봅니다.

전제 개념

서버 HTML은 먼저 볼 수 있는 화면이고, hydration은 클라이언트 React가 그 화면을 자신의 트리와 연결하는 과정입니다. 클라이언트의 첫 렌더가 같은 입력·구조를 만들어야 기존 DOM을 믿고 연결할 수 있습니다. 사용자 선호로 나중에 바뀌는 것은 정상 업데이트지만, 첫 렌더부터 다른 값이면 불일치입니다.

React hydrateRoot는 불일치를 버그로 다루라고 안내합니다. 시간·난수·서버와 브라우저의 로케일, 잘못된 태그 중첩, 브라우저 확장이나 외부 스크립트의 DOM 변경이 후보입니다. Next.js 진단 문서로 원인 목록을 확인하세요.

답변 사고 순서와 수정 예

  1. 서버가 실제 보낸 HTML, hydration 직전 DOM, 첫 클라이언트 렌더 입력을 나눠 비교합니다.
  2. 시간·통화·로케일·feature flag가 어디서 정해지는지 추적합니다.
  3. 요청에서 정한 값을 직렬화해 첫 클라이언트 렌더에도 전달합니다. 요청 간 개인화 데이터 캐시 혼합은 별도 확인합니다.
  4. 브라우저 전용 선호는 일치하는 초기값으로 시작하고 hydration 후 정상 상태 변경으로 반영합니다.
  5. 통화 변경 때 가격 의미·레이아웃 이동·느린 기기의 두 번째 렌더 비용을 검증합니다.
'use client';
function Currency({ initialCurrency }) {
  const [currency, setCurrency] = useState(initialCurrency);
  useEffect(() => {
    const saved = localStorage.getItem('currency');
    if (saved === 'KRW' || saved === 'USD') setCurrency(saved);
  }, []);
  return <span>{currency}</span>;
}

useState·useEffect import를 생략한 컴포넌트 예입니다. initialCurrency는 서버와 브라우저가 공유한 동일 값입니다. 서버에서 쿠키 기반 선호를 이미 알 수 있으면 그 값을 사용해 나중 화면 전환도 줄일 수 있습니다.

답변 예시·Trade-off·오해

먼저 초기 통화와 시간의 입력을 서버·브라우저에서 비교하겠습니다. 동일한 요청 값으로 첫 렌더를 맞추고, 브라우저에서만 알 수 있는 선호는 hydration 후 반영합니다. 경고를 숨기는 대신 가격·화면 구조가 맞는지 검증하고, 필요한 영역만 브라우저 전용으로 제한하겠습니다.

공통 seed는 첫 화면을 보존하지만 직렬화·개인화 캐시 관리가 필요합니다. 두 단계 렌더는 브라우저 선호를 반영하지만 깜빡임·추가 렌더가 있습니다. 해당 부분 SSR 제외는 초기 내용과 SEO·로딩 경험을 바꾸므로 지도·편집기처럼 브라우저 전용 기능에 한정해 검토합니다.

약한 답변: ‘경고를 모두 suppress합니다.’ 한 단계의 불가피한 차이를 위한 탈출구이며 값 정합성을 복구하는 기능이 아닙니다. 오해: use client는 서버 HTML을 만들지 않는다. Next.js 첫 진입에서는 Client Component도 서버에서 HTML을 미리 만들 수 있으므로 render 중 window 참조는 여전히 문제입니다.

연습·피드백

서버 HTML은 ‘10:00’, 브라우저 첫 렌더는 ‘10:01’입니다. 전 페이지 SSR 제거, 동일 timestamp prop 전달, 전역 경고 억제 중 가장 작은 수정은?

풀이 확인

동일 timestamp를 전달하고 포맷의 로케일까지 맞추는 것이 작은 수정입니다. 이후 시계 갱신은 정상 상태 업데이트로 수행합니다. 전 페이지 SSR 제거는 불필요하게 초기 화면을 잃고, 전역 억제는 다른 가격·구조 불일치를 숨깁니다. 시간 문자열만 같아도 DOM 중첩이 다르면 해결되지 않으므로 구조도 확인합니다.

Follow-up·자기 점검

확장 프로그램이 DOM을 바꿨다면? 확장 없는 브라우저와 서버 원문을 비교해 앱의 초기 입력 오류와 구별합니다. 특정 복구 경로만 격리하며 오류 수집에서 민감정보를 제거합니다.

오류가 특정 사용자에서만 난다면? cookie·locale·개인화 캐시 키를 비교합니다. 재현 입력을 익명화해 테스트하며 전체 페이지 suppress로 덮지 않습니다.
